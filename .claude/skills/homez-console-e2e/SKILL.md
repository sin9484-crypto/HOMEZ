# HOMEZ Console E2E 자동화 안전 수칙

2026-09-14 온채널 첫 실사용 검증 + 쿠팡 등록 검증 라운드에서 실제로 발생한
시간 낭비·오판단 사례를 근거로 만들었다. 매 항목은 "무엇을 잘못했는가 →
그래서 무엇을 먼저 한다"로 구성한다.

## 1. 화면이 막히면 원인부터, 우회 금지

**실수**: Listing Wizard 4단계가 막히자 원인을 코드로 확인하지 않고
"채널별 판매 방식"이라는 다른 화면으로 옮겨가 문제를 풀려 했다. 그 화면은
전혀 다른(더 원시적인) 별도 시스템이었다.

**규칙**:
- 화면에 표시된 오류 문구를 먼저 그대로 검색한다(`Grep`으로 console.js에서
  그 문구 또는 관련 i18n 키를 찾는다).
- 그 문구를 만드는 함수가 실제로 무엇을 조회/요구하는지 router→service→
  model까지 따라가 확인한다.
- 그 요구사항을 충족시키는 게 목표다. **다른 화면·다른 경로로 옮겨서
  "우회"하지 않는다** — 같은 목표를 달성하는 것처럼 보여도 전혀 다른 테이블·
  전혀 다른 성숙도의 코드일 수 있다.

## 2. 새 기능을 제안하기 전에 기존 구현부터 전수 검색

**실수**: 화면이 요구하는 필드를 채울 저장소가 없다고 판단해 "새 Model·
Migration을 만들자"고 제안했다. 실제로는 그 필드를 실시간으로 실제 외부
API에서 조회해 채우는 기존 코드(`coupang_logistics_provider.py`,
`CoupangLiveProductProvider`)가 이미 있었다 — 더 우월한 설계였다.

**규칙**: 새 코드를 제안하기 전에 반드시:
1. 문제가 된 필드명·개념명 그대로 `Grep`으로 해당 Domain 전체를 검색한다.
2. 비슷한 이름의 Provider/Service/Adapter 파일이 있는지 파일 목록을
   확인한다(`*_provider.py`, `*_client.py`, `*_adapter.py` 패턴).
3. 그 화면에 대응하는 라우터 엔드포인트를 찾아, 그 엔드포인트가 실제로
   무엇을 호출하는지 끝까지 따라간다(다른 도메인 파일로 이어지더라도).
4. 위 3단계를 거치고도 정말 없다고 확인됐을 때만 신규 코드를 제안한다 —
   그리고 "무엇을 검색했고 무엇이 없었는지"를 근거로 함께 제시한다.

## 3. 화면 요소 가시성은 CSS로 판정한다, `.hidden` 속성이 아니다

**실수**: `element.hidden`(DOM attribute) 값으로 "어느 화면이 떠 있는가"를
판단했다가, 이 앱의 실제 전환 메커니즘이 CSS class/`display` 기반이라는
것을 몰라 "모든 화면이 동시에 열려 있다"는 잘못된 결론을 내리고 페이지를
불필요하게 재시작했다.

**규칙**:
- 어느 요소가 "실제로 화면에 보이는가"를 판정할 때는 항상
  `getComputedStyle(el).display !== 'none' && getComputedStyle(el).visibility !== 'hidden'`
  을 쓴다. `.hidden` 프로퍼티나 `[hidden]` 속성 존재 여부만으로 판단하지
  않는다(프레임워크/코드베이스마다 표시·숨김 메커니즘이 다르다).
- `document.querySelector('main').textContent`처럼 컨테이너 전체 텍스트를
  읽는 방식은 숨겨진 형제 요소의 텍스트까지 섞여 나올 수 있다 — 반드시
  "현재 보이는 요소"를 먼저 특정한 뒤 그 요소의 `innerText`(CSS 인식)를
  읽는다. `textContent`는 CSS 표시 여부를 무시한다는 점을 기억한다.
- 클릭이 아무 효과가 없어 보이면, 재시도하기 전에 반드시:
  1. `read_console_messages`/`read_network_requests`로 실제 요청·에러가
     있었는지 확인한다.
  2. 화면에 이미 뜬 토스트·오류 문구(`.toast`, `[class*="toast"]` 등)를
     직접 조회한다 — 이유가 이미 화면에 적혀 있을 수 있다(예: "제한
     모드입니다" 안내를 놓치고 "버그인가?"로 오판했던 사례).
  3. 그래도 원인이 안 보이면 그 버튼의 핸들러 함수를 코드에서 직접 읽는다.

## 4. 대용량/이진 데이터는 Read로 직접 읽지 않는다

**실수**: 이미지 파일을 base64로 인코딩한 뒤 그 텍스트 파일을 `Read` 도구로
직접 읽어 대화 컨텍스트를 크게 낭비했다.

**규칙**:
- 이미지·바이너리 파일의 내용을 확인할 목적이 아니라면(즉 브라우저에
  전달만 하면 되는 경우) 그 파일을 **절대 Read로 열지 않는다**.
- 브라우저에 파일을 주입해야 하면: (a) 같은 오리진(HOMEZ 서버 자신이
  서빙하는 경로)에 두고 fetch하거나, (b) CORS 헤더(`Access-Control-Allow-
  Origin: *`)를 붙인 임시 로컬 서버(`http.server` 커스텀 핸들러 등)를
  띄워 그 URL을 브라우저 JS의 `fetch()`가 직접 받게 한다 — 텍스트로
  변환해 도구 호출 인자에 넣지 않는다.
- 이미지 자체의 내용을 실제로 봐야 하는 경우(예: 진짜 상품 사진인지
  확인)는 `Read` 대신 브라우저로 그 이미지 URL에 `navigate`한 뒤
  `computer` 스크린샷으로 직접 본다.

## 5. 세션·토큰은 오래 걸리는 작업 중간에 만료될 수 있다

**규칙**: 여러 단계에 걸친 브라우저 작업 도중 클릭이 반응하지 않거나
"인증이 필요합니다"가 보이면, 먼저 `localStorage.getItem(<token key>)`
존재 여부와 `loggedIn`(예: 운영자 메뉴 버튼 존재)을 확인한다. 토큰이
사라졌으면 재로그인을 요청하고, 그 전에 하던 작업은 다시 확인 없이
이어가지 않는다(중간 상태가 저장됐는지 다시 조회해 확인한다).

## 6. 실제 상태는 항상 DB 재조회로 증명한다, 화면 표시만으로 단정하지 않는다

이 프로젝트의 기존 원칙(`homez-core`, `homez-migration-safety`)과 동일하게,
브라우저 화면에 "성공"처럼 보여도 반드시 실 DB를 읽기 전용으로 재조회해
실제 행이 생겼는지·상태값이 기대한 값인지 확인한 뒤에만 완료로 보고한다.

## 7. 진행 전 자가 점검 체크리스트

막힌 화면을 우회하려는 충동이 들 때, 다음을 스스로 먼저 묻는다:

- [ ] 이 오류 문구를 코드에서 직접 찾아봤는가?
- [ ] 이 문제를 푸는 기존 코드가 있는지 Grep으로 찾아봤는가?
- [ ] "새로 만들자"고 제안하기 전에 위 두 가지를 다 했는가?
- [ ] 지금 보는 요소가 실제로 화면에 보이는 게 맞는지 CSS로 확인했는가?
- [ ] 큰 파일을 다룰 때 Read로 직접 읽지 않을 방법을 먼저 생각했는가?

이 문서는 **계획**이다. 실제 쿠팡 등록·주문·발주·결제·취소·환불, 외부 API 호출, 원본 DB 쓰기를 실행하지 않았고, 이 문서가 그 어느 것의 승인도 아니다. 새 계획 플랫폼이 아니라 기존 문서를 **현재 상태(원본 Migration 적용 완료·가드 구성·코드 커밋 후)에 맞춰 갱신**한 것이다.

## 1. 합격 기준 (확정된 출시 기준 원문)

개인 베타 시작 조건 중 이 계획의 대상(299행): "**실제 상품 2건의 지정된 전체 과정과 긴급 중지 검증**".
- **상품 1(정상)**: 정상 주문 → 주문 수집 → 매입 연결 → 결제 → 발주 → 배송 → 수령 → 정산 → 최종 손익.
- **상품 2(반품)**: 주문 → 반품 신청 → 매입처 반품 → 고객 환불 → 판매채널·매입처 환불 대조 → 최종 손익.
- **긴급 중지**: 실제 결제 **전에** Fake 환경에서 먼저 검증. 중지 시 등록·가격변경·결제·발주는 멈추고 조회·백업·진단은 유지.
- 규칙(284~297행): 승인 없이 등록·주문·결제·발주·취소·환불 금지, 동작·대상·횟수·예상 영향을 설명하고 승인 후 **한 번씩** 실행, 배송지 원문 사용 전 별도 승인, 같은 주문을 반복 처리해도 결제·발주 각 1회, 결과불명 시 자동 재시도 금지, 결제·발주·개인정보 노출·중복 처리 결함 불허.
- 12개 오류 상황 전체 통과는 **시작 조건이 아니라 기능별 자동모드 개방 조건**(290~302행). 이번 검증은 **자동모드를 열지 않고** 수동·반자동으로만 진행한다. 중복 주문·결제, 타임아웃, 결과불명 시험을 통과하지 않은 기능은 자동모드로 열지 않는다.

## 3. 계획을 좌우하는 사실 (갭, 구현은 이번에 하지 않음)

- **G-A 쿠팡 송장 등록 연동 없음**(8번): 공급처 송장을 얻어도 쿠팡에는 사람이 WING에서 등록해야 한다 — 하지 않으면 고객 배송 상태가 진행되지 않을 수 있다(추론).
- **G-B 쿠팡 정산 조회 없음**(10번): 정산은 사람이 WING 값을 읽어 HOMEZ에 입력하고 HOMEZ가 대조한다. **쿠팡 정산 시점·주기는 미확인**이며 수 주가 걸릴 수 있어(추론) 최종 손익 단계가 일정의 병목이 될 수 있다.
- **G-C 쿠팡 반품·환불 처리 연동 없음**(11·13번): 반품 승인·환불은 쿠팡·사람이 처리하고 HOMEZ는 기록·대조한다.
- **G-D 온채널 취소·반품 API 없음**(12번): 사람이 온채널에서 처리.
- 결과적으로 **이 검증이 입증하는 것은 "HOMEZ가 자동으로 처리한다"가 아니라 "실제 거래 사실을 HOMEZ가 정확히 기록·대조·손익 계산한다"는 범위**다. 자동 연동이 필요하다는 판단이 서면 별도 구현 과제이며 이번 계획에 포함하지 않는다(→ 결정 D-2).

## 5. 단계 계획 (각 단계는 이전 단계 통과·승인 후, 한 번에 하나)

모든 단계 공통: 직전 원본 지문 대조 → 보존 백업(기동 전, `mode=ro`+`backup()`) → 가드 켠 상태(필요한 외부 호출 단계만 해당 연결에 한해 가드 설정을 별도 승인 후 조정) → 한 동작씩 승인 → 결과 기록. 값은 비밀·개인정보 없이 상태·개수·ID만 남긴다.

### Phase 0 — 외부 호출 없는 사전 점검 (읽기·테스트만)
| 단계 | 내용 | 통과 기준 |
|---|---|---|
| 0-1 | 원본 상태 재측정(SHA·이력 77·모드·EStop·연결 상태, 설치판 불변) | 기준선 일치 |
| 0-2 | **긴급 중지 Fake 검증**(기준 295~296행): 기존 테스트(`test_automation_safety.py`·`test_coupang_live_submission.py`·`test_coupang_order_materialization.py` 등)의 등록·가격·결제·발주 차단과 조회·백업·진단 유지를 **대상 테스트만** 재실행해 결과 기록(전체 회귀 반복 금지) | 차단·유지 모두 통과 |
| 0-3 | **실결제 전 필수 안전시험 대상 확인**: 중복 주문·결제, 타임아웃, 결과불명이 Fake로 통과했는지 목록화(자동모드 개방 조건과 구분) | 미통과 항목은 자동모드 금지로 기록 |

### Phase 1 — 결정 (사용자): D-1~D-6 확정, D-3 선택에 따른 문의 발송 또는 위험 수용 기록.

### Phase 2 — 등록 준비 (원본 쓰기, 단계마다 승인)
2-1 상품 상세 재조회(온채널, 외부 GET 1회·재시도 없음)로 가격·재고·배송비·옵션 최신화 — 승인 → 2-2 속성 비교 해소(`resolve_run`, 근거 확보 후) → 2-3 판매신청 `NEEDS_REVIEW` 검토 해제 또는 재확인(자동 재신청 금지, 재신청은 별도 승인) → 2-4 Wizard 저장·사전검사 통과(18%·이슈 2건) → 2-5 8단계 승인(재인증). 각 단계의 증거: DB 행 변화·감사 로그.

### Phase 3 — 쿠팡 등록 (외부 POST **1회**)
전송 직전 점검 → 사용자 승인 → POST 1회 → 응답 분류(성공/거절/**결과불명**). **결과불명이면 자동 재시도 없이 중단**하고 쿠팡 쪽 상태를 읽기로 확인한 뒤 사용자가 판단. 성공 후 `sellerProductId` 저장, 쿠팡 판매 가능 상태 읽기 확인.

### Phase 4 — 주문 → 수집 → 연결 (상품 1)
4-1 **사용자가 쿠팡에서 직접 주문**(D-3 충족 후, 배송지는 앱의 보호된 입력 경로) → 4-2 시험 전용 수집 경로 `test-budget-plan` 미리보기 확인 후 `trigger`(연결 1개·ACCEPT·GET 최대 2회, 두 번째는 같은 구간 재조회) — 기대: 신규 1·중복 1·`orders` 1행·`order_channel_fulfillments` 1행(Phase 7B §3-3 표와 대조) → 4-3 SKU/옵션 연결(`supplier_option_links` 저장은 외부 확인 조회 동반 → 승인) → 4-4 구매 작업·마진 18% 게이트 확인.

### Phase 5 — 발주·결제 (온채널, 상품 1)
5-1 직전 점검(읽기): 온채널 포인트 확인·상품 가격·재고·배송비 재조회, 판매신청 접수 확인, 총액 = 매입가+배송비 확인, EStop 비활성, 모드 확인 → 5-2 **실결제 전 EStop 실환경 확인(선택, 승인 필요)**: EStop을 켜서 발주 버튼 차단·조회 유지를 확인하고 해제(원본 안전 설정을 바꾸므로 별도 승인, 되돌림 기록) → 5-3 사용자 재인증 → `submit_order(confirm_real_submission=True)` **1회**, 중복 요청 시도는 하지 않는다 → 5-4 결과 분류. **결과불명이면 재시도·재결제 금지**, 온채널 주문 조회 GET(승인)로 확인 후 사용자 판단.

### Phase 6 — 배송·송장 (상품 1)
온채널 `lookup_tracking` 조회(승인) → **G-A: 사용자가 WING에서 송장 등록** → 쿠팡 배송 상태 읽기 확인 → HOMEZ 배송 기록(`shipments`) 입력·대조. 증거: 송장·택배사 일치, 상태 이벤트 순서.

### Phase 7 — 수령·정산·최종 손익 (상품 1)
사용자 수령·구매확정 → **G-B: 정산 시점이 될 때까지 대기**(시점은 WING 안내로 확인, 미확인) → 사용자가 WING 정산 값을 읽어 `settlements`에 입력 → HOMEZ 대조·차이 분석 → 최종 손익 = 판매가 − 쿠팡 수수료 − 매입가 − 배송비 − 기타, 위저드 경제성(25%·3,224.60원)과 비교해 차이 원인 기록. **여기까지가 상품 1 완료**.

### 게이트 G — 상품 2 결정 (상품 1 결과 후)
상품 1에서 드러난 G-A~G-D 부담·오류·비용을 바탕으로 D-1을 확정하고 상품 2 트랙 승인.

### 상품 2 트랙
등록(필요 시 Phase 2~3 반복 또는 같은 등록 재사용) → Phase 4~6 동일(주문·수집·연결·발주) → **반품 신청(사용자, 쿠팡 정책에 맞는 실제 사유 — 허위 사유 금지)** → G-C: WING에서 반품 처리 → HOMEZ `return-orders` 기록 → G-D: 온채널 반품(사람) → 고객 환불(쿠팡) → `refunds` `mark-executed` 기록 → **판매채널·매입처 환불 대조**(금액·시각·수수료·왕복 배송비) → 최종 손익(반품 왕복 약 6,000원 등 비용 포함, 과거 값·최신 아님).

## 6. 공통 통제·중단 규칙

- **중단 조건**: 직전 지문 불일치, 예상 밖 DB 변화, 오류 코드, 결과불명, 가드·통제 미확인, 금액이 승인 범위 초과, 정책 회신 부정적. 원인 확인 전 재시도·강제 교체·사이드카 삭제 금지.
- 결제·발주는 **같은 주문당 각 1회**. 결과불명 시 **자동 재시도 없음**.
- 외부 호출은 **단계별 승인 범위 안의 횟수·대상**만(Phase 7B 방식: 호출 예산을 먼저 표로 제시). 자동모드 개방 없음, 모드·자격증명·설정 불변.
- **호출 예산은 실행 경로의 코드로 확인한 값만 제시한다**(Phase 7A 선례: 승인 1회 대 실제 6회). 버튼·API가 내부에서 몇 번 호출하는지 실행 전에 코드와 미리보기(`plan`)로 확인하고, 시험 전용 경로처럼 서버가 횟수를 강제하는 경로를 우선 쓴다. 승인 범위를 넘을 가능성이 있으면 실행하지 않는다.
- 실제 자격증명을 읽는 단계는 가드 설정을 그 단계에 한해 조정해야 하므로 **단계마다 가드·FAKE 어댑터 구성의 변경 범위를 먼저 승인**받는다(현재 기동 구성은 Credential Manager를 차단하므로 그대로는 실호출이 불가능 — 직접 확인).
- 복구: 단계마다 직전 보존 백업, 실패 시 확정된 파일 복귀 절차(앱 정상 종료·실패 상태 보존·검증된 백업으로 교체·재대조). 외부 거래(등록·주문·결제)는 DB 복귀로 되돌려지지 않음을 승인 시 명시.
- 증거 규칙: 개인정보·자격증명 미기록, WING·온채널 화면 값은 사용자가 읽어 알리고 HOMEZ 입력값과 대조.

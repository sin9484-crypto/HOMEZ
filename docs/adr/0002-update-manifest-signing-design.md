# ADR 0002 — 서명된 업데이트 매니페스트 검증 설계 (구현은 V7)

- 상태: 설계만 확정, 구현 보류(V7 "Live Gate")
- 날짜: 2026-08-12
- 작성 배경: Gate Y-4(업데이트 공지 시스템). 이번 세션은 외부
  네트워크 호출이 금지되어 있어, 실제로 원격 서버에서 매니페스트를
  가져와 서명을 검증하는 코드는 구현하지 않는다 — 대신 그 설계만
  여기 남기고, 지금은 관리자가 수동으로 업데이트 공지를 등록하는
  `app/domains/update`(`UpdateNotice`)만 구현했다.

## Context

`app/domains/update`는 현재 "관리자가 새 버전을 수동으로 등록하면
사용자에게 공지가 뜬다"까지만 한다. 진짜 자동 업데이트 확인(주기적
으로 원격 서버를 조회해 새 버전 여부를 판단)은 신뢰할 수 없는
네트워크 응답을 검증 없이 그대로 믿으면 안 되므로, 서명 검증이
선행되어야 한다. 이 문서는 그 검증 메커니즘의 설계를 확정한다 —
구현은 V7에서, 실제 배포 서버·서명 키 인프라가 준비된 뒤에 한다.

## 위협 모델

- **중간자(MITM) 위협**: 업데이트 서버로의 요청이 가로채여 악성
  매니페스트로 바뀌는 경우.
- **손상된 CDN/스토리지 위협**: 매니페스트는 정상이지만 실제 실행
  파일이 별도 스토리지에서 변조된 경우.
- **재생(Replay) 위협**: 예전에 유효했던(지금은 취약점이 발견된) 구
  버전 매니페스트를 다시 제공해 강제로 다운그레이드시키는 경우.

## 설계

### 1. 매니페스트 형식

```json
{
  "manifest_version": 1,
  "app_version": "6.6.0",
  "min_supported_version": "6.0.0",
  "release_notes_url": "https://.../release-notes/6.6.0",
  "artifacts": [
    {
      "platform": "windows-x64",
      "url": "https://.../HomezSetup-6.6.0.exe",
      "sha256": "<64자리 hex>",
      "size_bytes": 123456789
    }
  ],
  "issued_at": "2026-09-01T00:00:00Z",
  "expires_at": "2026-12-01T00:00:00Z"
}
```

`min_supported_version`은 다운그레이드 재생 공격 방지용이다 —
클라이언트는 자기 버전이 이보다 낮으면 "긴급 업데이트 필요"로
표시한다. `expires_at`이 지난 매니페스트는 거부한다(오래된 서명이
영구히 재생되는 것을 막는다).

### 2. 서명

- 알고리즘: **Ed25519**(RSA보다 서명/키가 작고, Python
  `cryptography` 패키지가 이미 지원 — 이 저장소 requirements에
  추가 의존성 최소화).
- 서명 대상: 매니페스트 JSON을 `json.dumps(data, sort_keys=True,
  separators=(",", ":"))`로 canonical 직렬화한 바이트열(공백 차이로
  서명이 갈리지 않게 — 이 저장소 다른 곳의 fingerprint 계산과 동일
  원칙).
- 매니페스트 파일은 `{ "payload": {...}, "signature": "<base64>" }`
  형태로 서명을 함께 포함해 배포한다.
- **개인키는 이 저장소에 절대 두지 않는다** — 서명은 별도의, 이
  코드베이스와 분리된 오프라인/CI 서명 절차에서만 수행한다. 이
  코드베이스에는 **공개키만** 상수로 내장한다
  (`app/domains/update/manifest_public_key.py`, 향후 구현 시).

### 3. 클라이언트 검증 절차 (V7에서 구현할 순서)

1. HTTPS로 매니페스트 URL을 가져온다(인증서 검증은 기본 활성 —
   `verify=False` 금지).
2. `signature`를 base64 디코드하고, 내장된 공개키로 `payload`의
   canonical 직렬화 바이트열에 대해 검증한다. 실패 시 **전체 응답을
   즉시 폐기**하고 아무 것도 표시하지 않는다(fail-closed — 서명
   실패를 "업데이트 없음"으로 조용히 넘기지 않고, 검증 실패 자체를
   `notification_center`에 WARNING으로 남긴다).
3. `expires_at`이 지났으면 폐기.
4. `app_version`을 `app.domains.update.service.parse_semver()`로
   파싱(이미 구현됨, 재사용).
5. `min_supported_version` > 현재 실행 버전이면 severity를 강제로
   `required`로 취급.
6. 검증을 통과한 매니페스트만 `UpdateNoticeService.create_notice()`
   (이미 구현됨)를 통해 시스템에 반영한다 — 즉 V7의 "자동 확인"은
   결국 지금 구현한 수동 등록 API의 **신뢰할 수 있는 입력원**이
   되는 것이지, 별도 저장 경로를 새로 만들지 않는다.
7. 실행 파일 다운로드 시 `sha256`을 재계산해 일치 확인(설치 전
   무결성 재검증 — 서명 검증과는 별개의 방어선).

### 4. 배포 주기/신뢰 앵커 갱신

- 공개키 로테이션이 필요해지면, 코드에 "현재 키" + "이전 키(유예
  기간 동안만 허용)" 두 개를 동시에 내장해 무중단 전환한다.
- 신뢰 앵커(공개키) 자체를 원격에서 갱신하는 기능은 만들지 않는다
  — 그 갱신 경로 자체가 새로운 공격 표면이 되기 때문이다. 키
  로테이션은 항상 앱 자체의 새 릴리스로만 배포한다.

## 이번 세션에서 하지 않은 것 (명시)

- 실제 HTTPS 요청 코드(`httpx`/`requests` 등) — 미구현.
- Ed25519 키 생성·서명 스크립트 — 미구현(서명은 이 코드베이스
  바깥에서 수행되는 절차이므로 이 저장소가 서명 도구를 가질
  필요도 없다. 검증만 이 저장소의 책임).
- 공개키 내장 상수 파일 — 미구현(실제 배포 키가 아직 없으므로
  플레이스홀더를 넣는 것도 오해를 부를 수 있어 보류).
- 자동 주기 확인(스케줄러) — 미구현.

## 지금 구현된 것과의 연결점

- `app/domains/update/model.py::UpdateNotice` — 검증된 매니페스트가
  최종적으로 도착할 테이블(변경 없음).
- `app/domains/update/service.py::parse_semver()` — 버전 비교 로직
  재사용 대상(변경 없음).
- `app/domains/notification_center` — 서명 검증 실패를 사용자에게
  알릴 채널(변경 없음, 이미 구현됨).

## 부록(Gate 8, 2026-08-15) — 설치 실패 시 이전 버전 안전 폴백 설계

**상태: 설계만, 구현 없음(실제 자동 업데이트 메커니즘 자체가 아직
없으므로 이 부록도 그 위에서만 의미를 가진다 — V7 Live Gate에서
자동 업데이트 확인/다운로드를 실제로 구현할 때 함께 구현 대상).**

Gate Y-6이 PyInstaller `onedir`(디렉터리 통째 배포, 단일 exe로
합치지 않음) 방식을 채택했다는 사실(`homez.spec`) 자체가 이 설계의
전제다 — onedir이면 "버전 = 디렉터리"로 표현할 수 있어, 실행 파일을
덮어쓰는 방식보다 훨씬 안전하게 되돌릴 수 있다.

1. **설치 레이아웃**: `%LOCALAPPDATA%\HOMEZ\versions\<semver>\`에
   각 버전을 독립 디렉터리로 설치한다(기존 버전을 지우지 않음).
   현재 실행 버전은 `%LOCALAPPDATA%\HOMEZ\current`가 가리키는
   디렉터리로 결정한다(Windows에서는 심볼릭 링크 대신 NTFS Junction
   또는 단순 텍스트 포인터 파일 + 런처가 그 경로를 읽어 실행하는
   방식 중 하나를 택한다 — 심볼릭 링크는 기본 권한으로 생성이
   막혀 있는 Windows 환경이 흔해 Junction/포인터 파일 쪽이 실무적
   으로 더 안전하다).
2. **설치 절차**: 신규 버전 디렉터리에 압축 해제 → 무결성
   재검증(ADR 본문 3-7과 동일한 sha256 비교) → **아직 `current`
   포인터를 바꾸지 않은 상태에서** 신규 버전을 한 번 헬스체크
   방식으로 기동해본다(예: `--self-check` 같은 별도 플래그로 앱을
   잠깐 띄워 `app.main` import + DB 연결 + Migration 진단까지만
   해보고 종료 — 실제 사용자 세션을 시작하지 않는다) → 통과해야만
   `current` 포인터를 새 버전으로 원자적으로 전환한다.
3. **실패 시 폴백**: 신규 버전의 헬스체크가 실패하면 `current`
   포인터를 아예 바꾸지 않고 설치를 중단한다 — 사용자는 계속 이전
   버전을 쓴다(포인터 전환이 유일한 "커밋 지점"이므로, 그 전에는
   무엇을 해도 이전 버전에 영향이 없다). 포인터 전환 **이후**에
   문제가 발견되면(예: 실제 사용 중 크래시가 반복됨), 사용자가
   수동으로(또는 향후 자동 크래시 감지가 생기면 그 트리거로) `current`
   포인터를 직전 버전 디렉터리로 되돌리는 것만으로 롤백이
   끝난다 — 파일을 다시 받거나 설치 프로그램을 다시 돌릴 필요가
   없다.
4. **보존 정책**: 기본 최근 2개 버전(현재 + 직전 1개)만 디스크에
   보존, 그 이전 버전 디렉터리는 다음 성공적인 업데이트 시점에
   정리한다(백업 도메인의 `DEFAULT_RETENTION_KEEP_COUNT`와 동일하게
   "조회 후 결정" 원칙 — 자동 삭제가 필요하면 별도 승인 후 구현).
5. **DB Migration과의 상호작용(중요)**: 새 버전이 새 Migration을
   포함하면, 그 Migration이 실제로 적용된 뒤에는 이전 버전 실행
   파일로 롤백해도 **DB 스키마는 그대로 새 버전 상태로 남는다**(이
   저장소의 Migration은 전진 전용 설계 — 자동 downgrade 없음, `docs/
   V6_EXECUTION_LEDGER.md`의 Migration 관련 원칙과 일치). 따라서 이
   폴백은 "실행 파일 문제"만 되돌리고, "Migration까지 이미 적용된
   뒤에 발견된 문제"는 되돌리지 못한다 — 그래서 3번의 헬스체크가
   중요하다(Migration Restricted Mode 진단까지 포함해, 실제 사용자가
   쓰기 시작하기 전에 문제를 잡는 것이 최우선 방어선이고, 실행파일
   롤백은 그 다음 방어선일 뿐이다).

## 2. 원본 보호 — 가드는 설치판을 보호하지 않는다(직접 실측)

- **개발용 Python 가드는 패키징 실행을 보호하지 않는다.** 탐침 앱(HOMEZ 아님, 스크래치 PyInstaller 빌드)을 같은 `PYTHONPATH` 가드 환경변수로 실행하자 `sys.flags.no_site=1`, `sys.flags.ignore_environment=1`, `sitecustomize` 미로드, 가드 로그 파일 **생성 안 됨**. 같은 환경변수로 일반 파이썬을 돌린 양성 대조는 `GUARD_ACTIVE`가 기록됐다. → 같은 PyInstaller 방식(Python 3.13, PyInstaller 6.16.0)으로 만드는 HOMEZ 빌드도 같은 이유로 가드 밖일 것으로 판단한다. **HOMEZ 빌드·기존 `Homez.exe` 자체는 실행하지 않아 직접 확인한 것은 아니다**(탐침 앱의 실측) — 단계 c의 `GUARD_ACTIVE` 양성 대조가 HOMEZ 빌드에서의 확인이다.
- **대안(검증용 빌드 전용)**: `tools/packaged_guard_hook.py`를 PyInstaller **런타임 훅**으로 넣는다. 환경변수 `HOMEZ_PACKAGED_GUARD_FILE`이 있을 때만 가드 파일을 앱 코드보다 먼저 실행한다. 탐침으로 검증한 결과(합성 보호 파일 사용, 실제 DB 아님):
  | 시나리오 | 결과 |
  |---|---|
  | 훅 + 가드 파일 지정 | 보호 파일 **차단**, `GUARD_ACTIVE`, `ATTEMPT_BLOCKED` 기록 |
  | 훅은 있으나 환경변수 없음 | 허용(옵트인 — 릴리스 빌드에는 훅을 넣지 않는다) |
  | 훅 없음 + `PYTHONPATH` 가드 | 허용(**보호 안 됨**) |
  | 가드 파일 경로 없음 / `NO_INSTALL=1` / 보호 대상 비어 있음 | **시작 거부**(종료코드 97/98) — 보호 없이 계속 실행하지 않음 |
  테스트 `tests/test_packaged_guard_hook.py` 3건 + 변조 3건 확인. **한계**: 훅 논리는 테스트로 고정했지만 **HOMEZ 실제 빌드에 훅을 넣은 상태는 아직 검증하지 않았다**(단계 c의 `GUARD_ACTIVE` 양성 대조가 그 검증이다). 가드의 기존 한계(ctypes 직접 Win32 호출, 비파이썬 자식 프로세스 내부, SQL `ATTACH`)는 그대로다.
- **보조 방어(가드가 없어도 성립하는 것)**: ① 데이터 루트·`LOCALAPPDATA`를 스크래치로 덮어써 앱이 원본 경로를 계산하지 않음(앱은 개발 모드의 저장소 루트가 아니라 패키징 모드 경로 계약을 쓴다 — 직접: `config.py`/`paths.py`) ② ~~자격증명 이름공간 `HOMEZ_TEST`가 사본의 실제 항목 읽기를 막는다~~ → **68차 정정: 막지 못한다.** `HOMEZ_DATA_ROOT`는 **새로 만드는** 자격증명 대상명에만 `HOMEZ_TEST:`를 붙이고(`store_connection/service.py:313,573`), **읽을 때는 DB에 저장된 참조 문자열을 그대로 대상명으로 쓴다**(`coupang_collection_service.py:124`, `listing_wizard_router.py:297,324,443`, 업무 DB 사본의 `HOMEZ:store_connection:<uuid>`·`homez_channel_connection_N`). 고정 대상명을 읽는 경로도 있다(`public_hosting.py`, 네이버 데이터랩·매입처 기본 참조). 따라서 사본을 연결한 격리 앱은 이름공간 설정만으로는 **실제 운영 자격증명을 읽을 수 있다.** 필요한 대책은 아래 "자격증명 격리 3중 조치"다. ③ 죽은 프록시로 HTTP(S) 외부 호출 즉시 실패(원시 소켓은 막지 못함) ④ 실행 전후 **원본 두 DB·백업 폴더·Credential Manager 대상명 목록의 지문 비교** ⑤ 이 PC가 MSIX 가상화 환경에서 도구를 실행하므로 `%LOCALAPPDATA%` 경로 별칭 혼동을 피하려 스크래치(비가상화 경로)만 쓴다.
- **자격증명 격리 3중 조치(승인안의 필수 조건)**: ① **작업 사본 무력화** — 앱이 연결하는 *작업 사본*에서만 `store_connections.credential_reference`와 `purchase_channel_connections.credential_reference`를 해석 불가능한 가짜 참조로 바꾼다(원본·"순수 백업 사본"은 수정하지 않는다) ② **가드가 Credential Manager 접근을 차단** — 패키징 탐침(68차 실측, HOMEZ 아님)에서 훅이 활성화되면 `advapi32` `CredReadW` 심볼 조회가 `ATTEMPT_BLOCKED`로 차단되고 로그에 남는다(호출 이전에 차단). 비라우팅 주소 `192.0.2.1:9` 접속도 `socket.connect` 시점에 차단·기록됐다 ③ **죽은 프록시**(보조, 원시 소켓·네이티브 접근은 막지 못함). 가드의 활성이 확인되지 않으면 사본을 연결하지 않는다.
- **가드가 막지 못하는 것(기록)**: 네이티브 코드·C 확장이 직접 여는 파일/소켓, ctypes로 심볼을 미리 해석해 둔 호출, 비파이썬 자식 프로세스(PowerShell 등) 내부 동작, SQL `ATTACH DATABASE`. `GUARD_ACTIVE` 로그만으로 모든 접근이 차단된다고 결론 내리지 않는다. **보호를 보장할 수 없는 동작은 실행하지 않는다**(예: 외부 서비스에 접속하는 기능 화면의 조회·전송 버튼, 자격증명 설정 화면, 자동 수집 수동 실행).
- **남는 위험(사실)**: 읽기 접근은 사후 지문으로 증명할 수 없다. 가드(훅)가 `GUARD_ACTIVE`로 활성화되고 로그에 차단 시도가 남는 것이 읽기 접근에 대한 유일한 관측 수단이며, 훅이 활성화되지 않으면 앱을 실행하지 않는다(단계 c 중단 조건).

## 3. 백업·복원 대조 기준 — 바이트 해시는 유일한 조건이 아니다

`tools/db_logical_compare.py`(읽기 전용, 셀 값 미출력, 테스트 8건 + 변조 4건 확인)가 두 DB를 다음으로 대조한다. 바이트 SHA-256은 **참고 기록**만 하며 합격 조건이 아니다(백업 방식에 따라 같은 데이터도 바이트가 달라진다 — 테스트로 입증: `VACUUM INTO` 사본은 바이트가 다르나 논리 동일).
1. 양쪽 `PRAGMA integrity_check` = ok, `foreign_key_check` 위반 수 동일
2. 스키마(`sqlite_master`) 동일
3. `schema_migrations`(파일명, 체크섬) 집합·건수 동일 — 단계 d 이후에는 "원본 + 신규 1건"인지 별도 확인
4. 테이블별 **행 수와 행 내용 지문** 동일
5. 논리 참조(FK 제약이 없는 `*_id` 관계) 고아 행 수 동일
6. 핵심 행 확인(참고 기대값 — 원본과의 동일성이 합격 기준이고 아래는 사람이 읽는 점검표): `listing_wizards#1`의 브랜드 3상태 `OFFICIAL_BRAND`, `company_channel_policy_settings` 최소마진 0.18, `store_connections` 1건·`CONNECTED`, 매입처 연결 2건, 판매신청 기록 1건(`NEEDS_REVIEW`), 제출 이력 0건, 옵션 연결 0건
적용 후(d 이후) 원본과의 차이는 **신규 테이블 1개·인덱스 4개·Migration 이력 1행·일반 사용 흔적**만 허용하며 그 밖의 차이는 불일치로 본다.

## 4. 승인이 필요한 이유와 빌드 환경 선택(기술 근거)

**승인이 필요한 항목**: 원본 DB 읽기(b), 패키징 앱 실행(c~f, 로컬 서버·창), 사본 Migration 적용(d, 사본에만). 빌드 환경에 따라 외부 네트워크(PyPI 다운로드)가 추가된다.

**빌드 환경 — 먼저 네트워크 없이 가능한지 확인한 결과(직접 확인)**
- 문서 절차(`HOMEZ_INSTALLER_OPERATIONS.md`)는 "깨끗한 venv에서 빌드"를 요구한다. 그 이유(기록)는 요구사항 선언 누락을 잡는 것이다(과거 `email-validator`·`python-multipart`가 개발 venv에만 있어 깨끗한 환경에서 실패).
- **잠금 파일이 없다.** `requirements.txt`는 최상위 20개를 정확한 버전으로 고정하지만 **하위 의존성은 고정하지 않는다** — PyPI에서 새로 설치하면 하위 의존성이 개발 venv와 다른 버전으로 풀릴 수 있다(임의 업그레이드가 됨).
- **선언된 의존성의 폐포(requires 재귀, 표식·extras 평가)는 85개이고 전부 개발 venv에 설치**돼 있다. 개발 venv 90개 중 폐포 밖은 5개(`cryptography`, `passlib`, `pip`, `py-spy`, `pyjwt`)뿐이다. 폐포 85개의 파일은 19,292개·619MB, 스크래치 드라이브 여유 약 104GB.
- pip 캐시에는 휠이 1개뿐이라 `pip install --no-index`로 오프라인 설치는 **불가능**하다. 반면 `python -m venv`는 번들된 pip 휠(`ensurepip`, 26.1.2)로 **오프라인 생성 가능**하다.

| 선택 | 내용 | 네트워크 | 검증 능력과 한계 |
|---|---|---|---|
| **1 (권장) 폐포 복사 venv** | 새 venv를 오프라인으로 만들고, **선언된 의존성 폐포 85개만** 개발 venv의 동일 버전 그대로 복사(`RECORD` 기준, 콘솔 스크립트 제외). 만든 뒤 `pip check`, 폐포 목록·버전 대조, `import app.main` 확인 | **없음** | 폐포 밖 5개가 섞이지 않고 버전이 개발 venv와 같다. **요구사항 선언 완전성**(선언에 없는 패키지 의존 시 import 실패)을 검증한다. 한계: pip가 해결한 설치가 아니라 "같은 버전 복사"이므로 PyPI 가용성·pip 해결 과정은 검증하지 않는다 |
| 2 PyPI 정확 버전 설치 | 새 venv에 폐포 85개를 **정확한 버전으로만**(`--no-deps` + 고정 목록, 최신 버전·업그레이드 없음) PyPI에서 다운로드·설치. 다운로드 범위 = 그 85개 휠(약 수백 MB, 정확한 크기는 미확인) | **PyPI 다운로드만**(업무 API 아님) | 문서 절차에 가장 가깝다. 한계: 같은 버전의 PyPI 휠이 개발 venv의 설치본과 바이트 동일한지는 보장되지 않음(해시 대조 필요) |
| 3 개발 venv 그대로 | 현재 개발 venv로 빌드 | 없음 | 폐포 밖 5개가 번들 분석에 끼어들 수 있고 요구사항 선언 완전성을 검증하지 못한다(문서 절차와 다름) |

**승인된 PyPI 다운로드와 금지된 업무 API 호출은 다르다.** 선택 2를 고르더라도 승인되는 것은 패키지 저장소 다운로드뿐이며 쿠팡·온채널·기타 업무 API 호출은 승인 범위가 아니다.

**자원 위험(사실)**: 이 PC는 물리 메모리 4GB에 사용률 83~92%였다. HOMEZ 전체 번들 분석은 탐침 앱보다 훨씬 무겁다 → 빌드가 실패하거나 매우 느릴 수 있다. 중단 규칙: 빌드 실패·20분 무진행이면 원인을 기록하고 **재시도 루프 없이** 보고한다. 예상 소요(추정): 빌드 환경 구성·빌드 15~30분, 사본 생성 1~2분, 격리 앱 검증 20~40분(로그인 대기 별도), 복원·대조 5분.

## 5. 사용자가 직접 해야 하는 동작 (이 한 가지뿐)

## 7. 원본 전환 전에 확정해야 하는 것 — 과거 UNKNOWN 제출 이력 (독립 조건, 사본 검증을 멈추지 않는다)

**현재 상태(사실):** 설치판 DB의 제출 10건 중 **UNKNOWN 1건**(부직포 행주, 외부 반영 여부 미확정)이 있고 저장소 DB의 제출 이력은 0건이다. 중복등록 방지는 DB 하나 안의 `(company_id, listing_id)`와 부분 유니크 인덱스 기준이라 저장소 DB는 그 사건을 모른다. 지금의 "그 상품을 저장소 DB에서 다시 등록하지 않는다"는 **임시 운영 제한이지 영구적 중복 방지 구현이 아니다.** 설치판 DB와 그 이력은 덮어쓰지 않고 보존한다(이번 승인안은 설치판 DB를 읽지도 않는다).

**기존 기능으로 처리 가능한 범위(직접 확인):**
| 필요한 일 | 기존 기능 | 한계 |
|---|---|---|
| UNKNOWN 해소(쿠팡 쪽 실제 상태 대조) | `submission_reconciliation_service`(`preview_reconciliation` → `apply_reconciliation`, append-only 기록, 라우터 `/reconciliation/...`) | **같은 DB 안의 제출 건만** 다룬다. 설치판 DB에는 이 기능의 테이블을 만드는 Migration(`20260830_01`)이 **대기 중(36건 중 하나)** 이라 지금은 쓸 수 없다. 대조는 쿠팡 **읽기 조회**(외부 호출)를 동반한다 — 이번 묶음에 포함되지 않음 |
| 설치판 DB를 안전하게 쓸 수 있게 만들기 | Migration 러너(대기 36건 단위 승인), 사본 리허설 절차(기존 `UPGRADE_PREP` §5-2) | 설치판 DB 변경은 별도 승인(D). 사본에서 먼저 리허설 가능 |
| 이력을 업무 DB(저장소 DB)로 옮기기 | **없다.** 이관·가져오기 기능을 `app/` 전체에서 찾지 못했다(검색어: import/transfer/migrate_history 등) | 새 기능이 필요하다 — 이번 범위 밖이며 승인 없이 만들지 않는다 |
**원본 전환(D) 전에 선택해야 할 방안(이번에 선택을 요구하지 않음):** (1) 설치판 DB를 사본에서 먼저 업그레이드·정합화 리허설한 뒤, 승인된 순서로 설치판 DB 자체를 정합화해 UNKNOWN을 해소하고 "그 상품은 업무 DB에서 재등록하지 않는다"를 운영 규칙으로 유지(코드 보호 없음) (2) 이력을 업무 DB로 옮기는 최소 이관 경로를 별도 승인 하에 신규 개발 (3) 등록 전 점검에 설치판 이력 대조(상품명·판매자코드)를 추가하는 신규 개발. 어느 쪽이든 **승인 없이 이관하거나 상태를 바꾸지 않는다.**

## 8. 실제 상품 준비 항목(별도 목록, 완료된 결정은 다시 묻지 않음)
정상 거래 1건(주문→배송→수령→정산→최종 손익)과 반품 거래 1건(주문→양쪽 환불 대조→최종 손익)이 기존 출시 조건이다. 아직 남은 상품 준비 항목: 구성수량 확정(옵션 라벨 "본품"이 개수를 말하지 않음 → 속성 비교 `QUANTITY` 해소와 옵션 연결 `units_per_sale` 두 곳), 옵션 연결(vendorItemId 확인), 판매신청 `NEEDS_REVIEW`(발주는 `SUBMITTED`만 통과), 경제성 미입력(포장비·`tax_basis_rate` — 두 값의 합이 판매가의 약 7.0%·902.6원 이하여야 18% 유지), 속성 비교 해소, 승인·운영 모드(`RECOMMEND_ONLY`→`OPERATOR_APPROVAL`). 완료된 WING ID·브랜드·18%·업무 DB 결정은 포함하지 않는다.

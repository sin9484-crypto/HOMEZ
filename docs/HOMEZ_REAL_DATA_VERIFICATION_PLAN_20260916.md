# HOMEZ 실데이터 2건 검증 계획 (2026-09-16)

- 작성 배경: 개인 베타 진입 전 잔여 작업 Phase 9
- **이 문서는 계획만 담는다 — 어떤 단계도 실행하지 않았다.** 실제
  주문 감지, 실제 발주, 실제 결제, 실제 환불은 이 세션에서 전혀
  수행하지 않았다.
- 각 단계마다: 실행 API(또는 화면 조작) / 예상 변경 데이터 / 금전
  영향 / 개인정보 사용 여부 / 중단 조건 / 복구 방법 / 사용자 승인
  지점을 명시한다.
- 두 테스트 모두 **회사 실 계정, 실제 쿠팡 판매계정, 실제 매입처
  계정, 사용자 본인 자택 배송지**를 전제로 한다 — Fake Provider가
  아니라 실제 외부 API·실제 금전이 오간다.

## 0. 공통 전제 조건 (두 테스트 모두 시작 전에 확인)

| 항목 | 확인 방법 | 통과 기준 |
|---|---|---|
| Migration 제한 모드 | `is_restricted_mode()` | False(비활성) |
| EmergencyStop | `SafetyService.is_emergency_stop_active()` | False |
| 공식 업무 DB 확정 | Phase 8 문서(`HOMEZ_OFFICIAL_DB_SELECTION_20260916.md`) 기준 사용자 승인 | 승인 완료, 최신 백업 존재 |
| 쿠팡 판매계정 연결 | `StoreConnection`(marketplace_code=COUPANG, connection_status=CONNECTED) | 실제 자격증명으로 연결 확인 완료 |
| 매입처 연결 | `PurchaseChannelConnection` 실제 조회 성공 이력 | 최근 조회 성공, consecutive_failure_count=0 |
| 자동화 모드 | `FunctionCode`별 모드 | 전부 사용자가 원하는 값(자동/반자동/수동)으로 명시 확인 — 기본값 MANUAL 유지 권장(테스트 중에는 각 단계를 직접 확인하며 진행) |
| 예산 승인 | 이번 테스트에 쓸 최대 지출 한도 | 사용자가 사전에 구두/문서로 동의한 금액 |

**중단 조건(공통)**: 위 표 중 하나라도 통과하지 못하면 테스트를
시작하지 않는다. 진행 중 EmergencyStop이 활성화되거나 Migration
제한 모드에 들어가면 그 시점에서 즉시 중단하고, 이미 진행된 단계의
상태만 기록한다(강제 롤백하지 않는다 — 실제 주문/결제는 외부
시스템에도 흔적이 남으므로 함부로 되돌리면 오히려 불일치가 생긴다).

## 테스트 2 — 자택 배송 후 반품(손실 검증)

손실액이 정확히 계산되는지 확인한다. **사용자 본인의 자택을 배송지로
써서 실제 소비자 역할을 겸한다** — 제3자 고객 데이터를 쓰지 않는다
(개인정보 원칙 유지, 사용자 본인 동의하에 본인 정보만 사용).

**주의(정직 공개)**: `refund` 도메인이 실제 판매채널 환불 API와
연동돼 있는지, 아니면 여전히 Fake Provider 전용인지는 이 문서
작성 시점에 코드로 재확인하지 않았다 — 실행 직전에 반드시
`app/domains/refund/`의 실제 Provider 연결 상태를 다시 확인해야
한다(추측으로 "연동돼 있다"고 단정하지 않는다). 연동이 안 돼
있다면 2-6은 "실제 채널 화면에서 수동으로 환불 처리 후 결과만
HOMEZ에 기록"하는 방식으로 대체해야 한다.

## 공통 종료 조건

- 두 테스트 모두 12번(혹은 8번) 단계까지 도달하고 실제 순이익/
  손실액 대조표가 나오면 "완료"로 본다.
- 완료 여부와 무관하게, 중단된 시점의 상태·원인·다음 조치를
  반드시 기록한다(중단 = 실패로 단정하지 않는다 — 외부 요인일 수
  있다).
- 두 테스트 모두 완료된 뒤에만 자동 모드(AUTOMATIC) 확대를 검토한다
  — 이번 Phase의 완료 판정 기준과 동일.

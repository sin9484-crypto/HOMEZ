## 0. 이 문서와 현재 진행 중이던 작업의 관계

이 문서는 **기록 전용 지시**로 받았다 — "현재 진행 중인 작업은 그대로
유지하고 완료까지 진행한다"는 명시적 조건에 따라, 이 문서를 쓰는
시점에 진행 중이던 다른 작업(NAVER API HUB 실연동 + 오늘 발견한
confirm-dialog 버그 수정, 전체 회귀 테스트)을 중단하지 않았다. 전체
회귀 테스트는 이 문서 작성과 동시에 백그라운드에서 계속 실행 중이며,
완료되면 별도로 결과를 보고한다. 이 문서의 내용을 이유로 결제·발주
기능을 성급하게 구현하지 않는다(사용자 명시).

## 1. 확정 목표 [확정]

HOMEZ에서 사용자가 매입처·계정·결제수단·운영 조건을 설정하면,
HOMEZ가 **판매 주문 수집 → 매입 → 결제 → 배송 → 취소·환불 → 정산
대조**까지 연결해 처리하는 통합 운영을 목표로 한다.

- 정상 주문마다 사용자가 쇼핑몰을 직접 방문해 반복 구매하는 흐름은
  최종 목표를 충족하지 않는다.
- **최초 인증**(계정 연결·본인확인 등, 사람이 한 번은 반드시 개입해야
  하는 절차)과 **자동 처리가 불가능한 예외**(품절·가격변동·정책위반·
  결과불명확 등)는 명확히 구분한다 — 이 둘은 "실패"가 아니라 설계상
  당연히 사람이 개입하는 지점이다.
- 지원 범위는 **국내 위탁판매·국내 구매대행·해외구매대행·병행수입**을
  함께 고려한다. 온채널 한 곳만 전제로 전체 구조를 설계하지 않는다.

**현재 구현 상태**: `app/domains/retail_purchase/`가 이 목표의 일부
(국내 위탁판매용 "동일상품 매칭 구매")를 FAKE Provider로 전 과정
시연·검증 가능한 상태로 구현했다(`docs/HOMEZ_V7_RETAIL_PURCHASE_
SAFETY_GUIDE.md` 1절 참고). 실제 매입처 중 어느 하나도 서면 계약·
공식 API 연동이 완료되지 않아 **실 구매는 아직 어떤 매입처에서도
실행되지 않는다.** 해외구매대행·병행수입을 위한 별도 흐름(관세·통관·
환율 등)은 코드베이스에 아직 존재하지 않는다(미착수).

## 2. 함께 활용할 네 가지 방식 [확정 — 방식 자체 / 제안 — 기존 코드 매핑]

네 가지는 **배타적 선택지가 아니다.** [확정] 구매 실행 방식과
결제수단은 **별도로 모델링**한다 — 예: "구매대행 업체 연결" 방식으로
발주하면서 결제수단은 "구매용 가상카드"를 쓰는 조합이 가능해야 한다.

| # | 방식 | 정의 | 기존 코드상 대응(제안, 재해석 여지 있음) | 현재 상태 |
|---|---|---|---|---|
| 1 | HOMEZ 자체 구매대행 | HOMEZ가 관리하는 구매 계정으로 구매·결제·후속 처리를 직접 수행 | `CorporateProcurementProvider`("기업구매·후불 계약") | 인터페이스만 존재, 미계약([외부확인필요]: 계약·자금·증빙·환불 책임) |
| 2 | 구매대행 업체 연결 | 외부 구매대행 업체에 주문을 전달하고 결제·배송·환불 결과를 수집 | `ProcurementGatewayProvider` | 인터페이스만 존재, 미계약([외부확인필요]: 실제 제휴·API, 지원 매입처) |
| 3 | 사용자 매입처 계정 연결 | 사용자가 최초 로그인·인증, 이후 HOMEZ가 검증된 절차로 구매 수행 | `OfficialMarketplacePurchaseProvider`("대형 쇼핑몰 공식 구매/파트너 API")로 잠정 대응 — **[제안] 다만 이 Provider는 원래 "쇼핑몰의 공식 파트너 API"를 뜻해왔고, "사용자 개인 계정으로 로그인"과는 신원이 다르다. 후자를 별도 Provider 코드로 분리할지, 자격증명 소유자(HOMEZ vs 사용자) 필드로만 구분할지는 미확정 — 아래 3.1 참고** | 인터페이스만 존재, 미계약 |
| 4 | 구매용 가상카드 | 위 방식들에서 쓸 결제수단 | `VirtualCardProcurementProvider` | 인터페이스만 존재, 미계약([외부확인필요]: 발급 가능 국가·사업자 조건·계약, 일반 가상계좌와 구분) |

[확정] 카드·PayPal은 기본 결제 연결 검토 대상으로 유지한다.
[확정] 계좌·가상계좌·공급처 예치금은 지원 매입처에 맞춰 추가한다
(전체를 한 번에 설계하지 않고 매입처가 늘 때마다 확장).

또한 `DirectSupplierProvider`("고정 공급처 자동 발주")가 이미 존재
하는데, 이는 위 4가지 중 어디에도 정확히 속하지 않는 **B2B 직접
발주** 개념에 가깝다 — 이 Provider는 **`docs/HOMEZ_PROJECT_STATE.md`
에 이미 기록된 "사용자 확정 보류(수익화 모델 별도 검토)" 항목**이며,
이번 목표 기록으로 그 보류를 해제하지 않는다(사용자 명시 — §6 참고).

### 2.1 구매 실행 방식 × 결제수단 분리 모델링 [제안, 미착수]

현재 `PaymentAccountReference`(`app/domains/retail_purchase/model.py`)는
"Provider별 결제계정 1개"를 전제로 한 구조로 보인다(정확한 스키마는
Migration diff로 재확인 필요). 사용자 확정대로 "구매 실행 방식"과
"결제수단"을 별도 축으로 모델링하려면, 최소한 다음을 구분해야 한다.

- **구매 실행 방식**(누가/어떻게 발주를 넣는가): 방식 1~3 중 하나.
- **결제수단**(그 발주에 어떤 돈이 쓰이는가): 카드/PayPal/계좌/
  가상계좌/공급처 예치금/구매용 가상카드 중 하나 이상.

이 분리 자체는 Model/Migration 변경이 필요한 설계 작업이다 —
**[제안]**일 뿐 아직 착수하지 않았고, §6의 순서("현재 작업 완료 →
공통 매입 장부·상태 처리 감사 및 보완")에 따라 실제 Model 설계는
뒤에 온다.

## 3. 사용자 경험 — "매입 운영 설정" [확정 — 요구사항 / 제안 — 기존 UI와의 관계]

[확정] "매입 운영 설정" 화면에서 다음을 관리하도록 설계한다.

1. 매입처와 연결 계정
2. 기본·대체 구매 방식
3. 지원 결제수단과 연결 상태
4. 건별·일별 매입 한도
5. 최소 예상이익과 가격 상승 허용 범위
6. 배송기한
7. 자동 실행 범위와 예외 처리 조건

[확정] 카드 한 번 등록으로 모든 쇼핑몰 결제가 가능하다고 가정하지
않는다. 매입처별 최초 인증이 필요하면 설정 과정에서 정확히 안내한다.
[확정] 사용자의 기존 실제 결제 최종 승인 조건은 유지한다 — **이번
목표 설정은 실제 결제·발주 실행 승인이 아니다.**

### 3.1 기존 화면과의 관계(현재 구현 상태)

콘솔의 "구매 실행 연결" 화면(`app/web/console.js`, "매입예산·정책"
버튼)이 이미 회사별 자동구매 정책 화면을 갖고 있고, 아래 항목은
사용자가 요구한 7개 중 상당 부분과 **이미 겹친다**(`docs/HOMEZ_V7_
RETAIL_PURCHASE_SAFETY_GUIDE.md` 2절 표 기준):

| 사용자 요구 항목 | 기존 화면에 있는가 | 비고 |
|---|---|---|
| 건별·일별 매입 한도 | 있음 | "최대 매입가격·1회 최대 구매금액", "일별·월별 구매한도, 동시 구매 건수" |
| 최소 예상이익 | 있음 | "최소 순이익·최소 마진율" |
| 가격 상승 허용 범위 | 있음 | "가격 상승 허용률" |
| 자동 실행 범위와 예외 처리 조건 | 있음 | "자동 실행 여부", "승인 필요 금액 기준", "결과 불명확(UNCERTAIN) 처리정책" |
| 매입처와 연결 계정 | 부분적으로 있음 | "허용 구매처"(체크리스트)는 있으나, 방식 1~4를 반영한 "연결 계정" 단위 관리는 아직 없음 |
| **기본·대체 구매 방식** | **없음** | §2.1의 분리 모델링이 선행돼야 함 |
| **지원 결제수단과 연결 상태** | **없음** | 위와 동일 |
| **배송기한** | **없음** | 정책 테이블에 배송기한 항목 자체가 없음 |

**결론(제안)**: "매입 운영 설정"은 완전히 새로운 화면이 아니라
기존 "구매 실행 연결 → 매입예산·정책" 화면의 **확장**으로 설계하는
것이 기존 구조 우선 원칙에 맞는다. 다만 실제 화면 설계는 §6 순서에
따라 후속 작업이며, 이번 문서는 그 설계가 반영해야 할 목표만
기록한다.

## 4. 공통 거래 처리 기준 [확정]

```text
판매 주문 → 상품·옵션 매칭 → 가격·재고·배송 확인
  → 구매 방식 선택 → 주문·결제 → 배송 → 취소·환불 → 손익 대조
```

- [확정] 전체 과정에 **판매 주문·공급처 주문·결제·배송·환불 식별자를
  연결**한다(하나의 판매 건에서 끝까지 추적 가능해야 함).
- [확정] 총매입비에는 **배송비·대행료·결제비용·환율** 등 해당 비용을
  반영한다(단순 상품가만으로 매입비를 계산하지 않는다).
- [확정] **결제 성공과 주문 성공을 별도로 확인**한다 — 하나가
  성공했다고 다른 하나도 성공했다고 가정하지 않는다.
- [확정] 결과가 불명확하면 재결제나 대체 매입처 구매를 **바로
  실행하지 않는다.** 기존 거래를 조회·대조한 뒤 재시도 여부를
  결정한다.

**현재 구현 상태(2026-09-07 순서 4번 감사로 확정)**: 상세 감사 결과는
`docs/HOMEZ_V7_PROCUREMENT_LEDGER_AUDIT_20260907.md` 참고. 매입 관련
도메인은 `source`/`purchase`/`purchase_task`/`retail_purchase` 4개로
갈라져 있고, 이 목표가 요구한 "전 과정 식별자 연결"은 **어느
경로로도 완전히 충족되지 않는다** — 가장 연결이 잘 된 경로
(`purchase`)는 실거래에 쓰이지 않고, 실거래가 쓰는 경로
(`purchase_task`)는 주문 쪽으로 되돌아오는 연결이 없다. 정산
(`MarketplaceSettlement`)에는 두 경로 모두 연결되지 않는다.
`purchase_task`/`retail_purchase`는 UNCERTAIN 처리를 완전히
구현했지만 `purchase`는 그 개념 자체가 없어 네트워크 타임아웃도
곧장 재시도 가능한 FAILED로 처리된다. 중복 구매 방지도 `purchase`만
품목 단위로 견고하고 나머지 두 경로는 가드가 없다. 이 감사는 코드를
바꾸지 않았다 — 실제 보완은 Model/Migration 수준 결정이 필요해
별도 승인을 기다린다(감사 문서 §8).

**보완 진행(2026-09-07, 사용자 승인 후 완료된 부분)**: "purchase_task
중심" 방향 확정 후, OrderItem↔purchase_task 역방향 연결(신규
`purchase_task_id` 컬럼, 실제 homez.db 적용 완료)과 품목 단위 중복
매입 방지를 구현·테스트·적용 완료했다. 매입→배송 연결은 기존
`shipment` 도메인을 그대로 재사용(신규 파이프라인 없음). 정산 연결·
Route A UNCERTAIN·`retail_purchase` 중복가드는 사용자 지시로 보류
— 상세는 `docs/HOMEZ_V7_PROCUREMENT_LEDGER_AUDIT_20260907.md` §9
참고.

## 6. 우선순위와 착수 조건 [확정]

### 6.1 후속 개발 순서(확정)

```text
현재 작업 완료
  → 공통 매입 장부·상태 처리 감사 및 보완
  → 확보한 공식 API의 실제 지원 범위 연결
  → 국내 쇼핑몰 계정 기반 구매 흐름 검증
  → 외부 구매대행 업체 연동
  → 자체 구매대행·가상카드의 적용 조건 확보 및 확장
```

이 순서는 `docs/HOMEZ_V7_REQUIRED_WORK_SCOPE.md`의 "6. 자동 매입"
항목(이미 확정된 작업 순서 — 상품등록 안정화 → DB 기준 확정 →
주문 수집 → **자동 매입** → 배송·취소·반품 → 정산·손익 → …)의
"자동 매입" 단계를 더 세분화한 것이다. 기존 문서의 전체 순서를
바꾸지 않는다.

### 6.2 착수 조건(확정)

- [확정] **외부 조건에 막힌 항목만 보류**하고, 다른 승인된 작업은
  계속 진행한다 — 예를 들어 "구매대행 업체 연결"이 실제 업체
  계약 대기 중이어도, 계약과 무관한 공통 장부·상태 처리 감사는
  계속할 수 있다.
- [확정] **가격·재고 Model/Migration, 실제 SKU 연결 등 기존
  명시적 보류는 이번 목표 설정만으로 해제하지 않는다**(위 §2의
  `DirectSupplierProvider` 보류, `docs/HOMEZ_PROJECT_STATE.md`의
  가격·재고 감시 보류 등 전부 유지).
- [확정] **반복 재설치는 하지 않는다** — 최종 통합 테스트 시에만
  진행한다.
- [확정] **Cursor는 사용하지 않는다.**

## 7. 완료 기준과 보고 원칙 [확정]

- 화면·코드·Fake 테스트만으로 완료를 선언하지 않는다.
- 매입처별로 **실제 주문·결제·배송·취소·환불까지 확인한 범위**를
  구체적으로 명시한다(어느 매입처가 어느 단계까지 실제로
  검증됐는지).
- 목표 기록 작업과 기존(병행) 작업의 결과는 **각각 구분해서
  보고한다** — 이 문서가 그 기록이고, 병행 작업(NAVER API HUB 등)의
  결과는 `docs/HOMEZ_PROJECT_STATE.md`의 해당 날짜 절에 별도로
  있다.

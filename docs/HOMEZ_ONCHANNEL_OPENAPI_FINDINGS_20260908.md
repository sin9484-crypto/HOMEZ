# 온채널 OpenAPI 실제 기술 문서 확보(2026-09-08)

item 6/7(V7 통합 매입) 내내 "공식 기술 문서 없음"으로 보류했던 항목이
해제됐다. 사용자가 실제 문서 URL을 공유해 원문 스펙을 직접 확보했다.

- 문서 URL: `https://api.onch3.co.kr/openapi#/공급사%20-%20주문`
  (Swagger UI, 로그인 없이 공개 접근 가능 — 읽기 전용 확인)
- 원본 OpenAPI 3.0 스펙(JSON) 다운로드 경로:
  `https://api.onch3.co.kr/openapi/api-docs-openapi.json`
- 이 저장소에 원문 그대로 보존: `docs/HOMEZ_ONCHANNEL_OPENAPI_SPEC_20260908.json`
  (203,615 bytes, `info.title="온채널 OpenAPI"`, `info.version="0.1"`)
- 확보 방법: WebFetch(정적 fetch)는 SPA라 실패, Claude Browser 탭에서
  실제 렌더링 후 Network 탭에서 Swagger UI가 내려받는 원본 JSON
  요청을 찾아 그 URL을 다시 서버사이드(Python `urllib`)로 직접
  다운로드했다. 이 세션이 실제 자격증명(JWT)으로 호출한 적은
  없다 — 이 문서 자체는 인증 없이도 공개 조회된다.

## 핵심 발견 — "seller"가 HOMEZ의 역할이다

온채널 용어로 **"판매사"(seller) = 온채널의 공급망에서 상품을 사서
자기 채널에 파는 쪽 = HOMEZ**, **"공급사"(supplier) = 온채널에
상품을 등록하는 제조사/벤더**다. 그래서 HOMEZ가 실제로 쓸 API는
`seller/*` 그룹이다(`supplier/*`는 무관 — 반대 방향).

| Method | Path | 설명 | HOMEZ 관련성 |
|---|---|---|---|
| GET | `/openapi/seller/product` | 상품 리스트(옵션·재고 포함) | 매입 후보 조회 |
| GET | `/openapi/seller/product/{code}` | 상품 상세(카테고리·출고지·옵션가 등) | 매입 후보 상세 |
| POST | `/openapi/seller/product/apply` | 판매신청 — **주문 전에 이 상품을 먼저 "판매신청"해야 하는 것으로 보임**(전제조건, 미검증) | 매입 전 필수 단계 후보 |
| GET | `/openapi/seller/order` | 주문 리스트(최대 30일 범위 조회) | 발주 이력 조회 |
| GET | `/openapi/seller/order/{code}` | 주문 상세(수령인정보·배송정보 포함) | 발주 결과 확인 |
| POST | `/openapi/seller/order/regist` | **주문 생성(발주)** | 실제 매입 실행 — 금전적 결과 발생 |

인증: 전 엔드포인트 `BearerAuth`(JWT, `Authorization: Bearer <token>`)
— HOMEZ가 이미 Windows Credential Manager에 저장해 둔 값과 동일한
방식.

### `POST /openapi/seller/order/regist` 요청 스키마(발주 = 실제 매입 실행)

필수: `product_code`, `recv_name`, `recv_tell`, `recv_mobile`,
`zipcode`, `address`, `options`(`[{id, qty}]`). 선택:
`address_detail`, `comment`, `sale_code`(외부주문번호 — HOMEZ 쪽
멱등키로 쓸 수 있음), `site_name`. 응답: `{result: {order_code}}`.

**주의**: 이 요청 바디에 **고객의 실제 이름·전화번호·주소(PII)를
그대로 담아 온채널 서버로 전송**해야 한다 — 위탁배송 구조상
불가피하지만, 그대로 진행해도 되는지는 이 세션이 판단할 사안이
아니다(개인정보 제3자 제공 관련 사업 판단 필요, 사용자 확인 필요).

### 공통 오류 스키마

모든 실패 응답이 `{status, meta, error:{code, message}}` 형태로
일관됨 — `HttpStatus`뿐 아니라 바디의 `error.code`/`error.message`도
같이 확인해야 실제 원인을 알 수 있다.

## 이번 세션이 하지 않은 것

- 실제 JWT로 **어떤 실제 호출도 시도하지 않았다**(읽기 전용
  상품/주문 조회 포함) — 이 문서 확보 자체는 인증 없이 끝났고,
  실제 인증 호출은 사용자 확인 후 진행 예정.
- `product/apply`(판매신청)가 정말로 `order/regist`(발주)의
  전제조건인지는 스펙만으로는 확정할 수 없다(문서에 명시적 설명
  없음) — 실제 호출 없이는 검증 불가, 첫 실 호출 시 함께 확인
  필요.

| 잔액 부족 처리 | **미확인** | 공통 오류 스키마(400/401/403/404/409)에 "잔액부족" 전용 코드가 없다 — 400(Validation)으로 뭉뚱그려 올 가능성이 있으나 실제 호출 없이는 확정 불가. |
| 주문 중복 방지 키 지원 여부 | **미확인(중요)** | `sale_code`(외부주문번호)는 **선택 필드**다 — 서버가 이 값의 중복을 실제로 검사·거부하는지 스펙에 명시돼 있지 않다. 온채널 쪽에 별도 멱등성 보장이 없다면, HOMEZ 쪽에서 "이미 보낸 주문인지" 판단하는 책임을 전부 떠안아야 한다. |
| 타임아웃 후 기존 주문을 찾는 방법 | **확인된 위험(구멍 발견)** | `GET seller/order`(리스트, 최대 30일 범위)·`GET seller/order/{code}`(상세)로 조회는 가능하다. **그러나 두 응답 스키마 어디에도 `sale_code`(HOMEZ가 보낸 외부주문번호)가 되돌아오지 않는다** — 즉 "이 주문이 방금 그 타임아웃난 요청과 같은 것인지"를 `sale_code`로 재대조할 문서화된 방법이 없다. 실제로는 `product_code`+`recv_info`+금액+생성시각 근접도로 정황 매칭하는 수밖에 없어 보이며, 이는 본질적으로 모호하다(비슷한 주문이 여러 건이면 오판 가능). |
| 취소 가능 상태와 환불 처리 | **확인됨(API로는 불가)** | 18개 엔드포인트 어디에도 취소 API가 없다(§ "핵심 발견" 표 참고). 다만 `order.status` 값 중 4번("취소반품")·5번("부분환불")이 존재해 그 상태 자체는 도달 가능하다 — 즉 취소·환불은 (아마도 온채널 웹 화면이나 상대측 처리로) 발생할 수 있지만, **HOMEZ가 API로 취소를 "요청"할 방법은 이 스펙에 없다.** |

**가장 중요한 실무적 함의**: `sale_code` 조회 불가 발견 때문에, "결과
불명 상태에서 자동 재시도하지 않는다"는 이 세션의 기존 원칙이
선택이 아니라 **필수**가 된다 — 재시도 전에 방금 보낸 주문이 실제로
성공했는지 확인할 신뢰할 만한 방법이 지금 스펙 기준으로는 없다(주문
리스트를 훑어 정황 매칭하는 것은 오판 위험이 있어 자동화하지
않는다). 발주 기능을 실제로 만들 때는 이 구멍을 먼저 온채널 측에
직접 문의해서 메꿔야 한다(예: "sale_code로 주문 조회하는 별도
엔드포인트가 있는지", "생성 응답을 못 받았을 때 어떻게 중복 결제를
피하는지").

## 재조사(2026-09-08, "3번 다시 조사해라" 지시) — 스펙 필드 단위 재확인

사용자 지시로 원본 스펙을 `paths`/`components.schemas`까지 전부
다시 훑었다(1차 조사 때는 `responses` 블록만 얕게 확인했다 — 이번엔
`parameters`·`requestBody`·`components.schemas` 전체, 그리고 각
operation의 `summary`/`description`까지 확인). **터미널 출력이
Windows 코드페이지로 한글을 깨뜨리는 문제가 있어, 매번 UTF-8로
파일에 직접 써서 Read 도구로 다시 확인하는 방식으로 교정했다** —
1차 조사 과정에서 이 문제로 필드 설명 하나(`prd_char1`)를 순간
잘못 읽을 뻔했으나, 재확인 후 실제로는 "미성년자 판매금지 여부"

남기지 않는다.

**새로 확인된 것(구조적 사실, 추정 아님)**:

- `GET /openapi/seller/order`(주문 리스트)의 `parameters`를 전부
  확인한 결과 `page`/`page_size`/`start_at`/`end_at`/`status` 5개뿐
  이다 — **`sale_code`로 필터링하는 파라미터 자체가 스펙에 없다**.
  이전엔 "응답에 `sale_code`가 없다"까지만 확인했는데, 이번에
  "요청 파라미터로도 걸러낼 방법이 없다"는 것까지 확인했다.

  **2026-09-08 후속 정정** — 위 결과를 "재조회가 구조적으로
  불가능하다"로 단정했던 이전 표현을 정정한다. 실제로 확인한
  사실은 "공개된 스펙 문서에 `sale_code` 기반 재조회 파라미터가
  없다"는 것뿐이다 — 이는 "문서화된 안전한 주문 대조 방법을
  아직 확인하지 못했다"는 뜻이지, "어떤 방법으로도 불가능함을
  증명했다"는 뜻이 아니다(예: 스펙에 없는 다른 조회 경로,
  온채널 측 안내, 또는 향후 스펙 갱신으로 방법이 생길 가능성이
  남아있다 — 없음의 증명과 확인하지 못함은 다르다). 질문 4번은
  "공식 답변 필요" 항목으로 그대로 유지한다.
- `sale_code` 필드 자체의 스펙 설명은 `"외부주문번호"`
  (예시 `"ORD-20260408-00001"`)뿐이고, 유일성·중복 검사 관련
  문구는 어디에도 없다 — 질문 3번은 스펙만으로 확정할 수 없다는
  결론이 그대로 유지된다(추가로 밝혀진 단서 없음).
- `GET /openapi/common/member/point`(회원 포인트조회)의 응답
  스키마는 `result`가 `type: array, items: {type: object}` 뿐이고
  실제 필드 정의가 스펙에 전혀 없다 — **이 API가 반환하는 값의
  구조 자체가 문서화돼 있지 않다는 것이 확정적 사실**이다(내가
  더 찾지 못한 게 아니라, 스펙 자체에 없다). 그래서 질문 2번
  (예치금/결제 방식)은 실제로 호출해서 응답을 보지 않는 한 스펙만
  으로는 원천적으로 답이 나올 수 없다.
- `components.schemas.product.status`(상품 상태) enum을 새로
  확인했다: `1=판매전, 2=판매, 3=판매중단, 4=일시품절, 5=품절`.
  **정황상**(직접 확인 아님) "판매신청 승인 전 상품은 상태값
  1(판매전)에 머물 가능성"을 시사하지만, `order/regist`가 이
  상태값을 실제로 검사해서 발주를 막는지는 스펙 어디에도 명시돼
  있지 않다 — 질문 1번은 여전히 "미확인"이되, 이 정황 근거를
  추가로 남긴다.
- `product/apply`·`order/regist` 두 operation 모두 `description`
  필드가 `null`이다(요약 제목만 있고 부연 설명 자체가 스펙에
  없다) — 놓친 설명 텍스트가 있었던 게 아니라 애초에 존재하지
  않는다.

**결론**: 질문 1~4는 여전히 미확인이지만, "왜 미확인인지"(스펙에
그 정보 자체가 없다는 사실)를 이번 재조사로 더 정확히 확인했다.

다음 단계는 실제 호출(포인트 조회, 소액 테스트 발주) 또는 온채널
직접 문의 둘 중 하나뿐이다.

## 정정(2026-09-11, 반자동 완료 라운드 Phase 3 재감사) — "배송비
확인 API 없음"은 스펙 전수조사 누락으로 인한 오판정이었다

**이전 결론이 틀렸다.** 2026-09-08~10 세션들은 스펙을 "shipping",
"delivery", "fee" 같은 **영문 키워드**로만 훑었다. 그런데
`GET seller/product/{code}` 응답의 `result.extends_info` 객체 안에
배송비 필드가 실제로 존재한다 — 영문 키 이름(`send_price` 등)이
"ship/deliver/fee" 패턴에 안 걸려서 그 전수조사에서 빠졌을 뿐,
한글 `description`에는 "배송비"가 명시돼 있었다. 이번 라운드에서
스펙 JSON 전체를 재귀적으로 순회해(키워드 매칭이 아니라 모든
description 필드를 직접 읽는 방식으로) 다시 확인해 찾아냈다.

`extends_info` 스키마(원문):

| 필드 | 타입 | description | 예시 |
|---|---|---|---|
| `send_type` | string | 배송비 타입(개별 배송비, 수량별 배송비) | "개별 배송비" |
| `quantity` | integer | 수량별 배송비 기준 수량(개별 배송비 시 1) | 1 |
| `send_price` | integer | 기본 배송비 | 105 |
| `jeju_send_price` | integer | 제주도 배송비 | 105 |
| `etc_send_price` | integer | 도서산간 배송비 | 105 |

또한 `GET seller/order/{code}`(발주 후 주문 상세) 응답에
`sum_delivery_price`(배송비 합계, integer) 필드도 있다 — 이것은
발주 **후** 실제 청구된 배송비 합계다(발주 전 조회 아님).

**그래도 여전히 자동으로 신뢰해 Gate D를 통과시키지 않는다.** 이유
3가지(코드에도 동일하게 기록 — `onchannel_client.py::
OnchannelShippingInfo`, `channel_adapter.py::ChannelShippingInfo`
docstring 참고):

1. `extends_info`의 사전 제시값과 실제 발주 후 `sum_delivery_price`
   가 항상 일치한다는 것을 **실제 주문으로 검증한 적이 없다**(가격
   필드와 마찬가지로 상품 상세 조회 시점과 발주 시점 사이에 값이
   바뀔 수 있는 "가격 인상" 류 드리프트 위험이 배송비에도 있을 수
   있음 — 미확인이면 확인된 것처럼 단정하지 않는다).
2. `send_type="수량별 배송비"`일 때 `quantity` 구간을 넘는 수량에는
   정확히 어떤 계산 규칙이 적용되는지 스펙에 명시돼 있지 않다(예:
   2배수마다 추가 부과인지, 최초 구간 초과분에 한 번만 적용인지
   등 — 추측하지 않는다).
3. `jeju_send_price`/`etc_send_price`가 적용되는 정확한 우편번호
   범위를 HOMEZ가 보유하고 있지 않다 — 배송지 주소만 보고 "제주/
   도서산간 여부"를 자동 판정하지 않는다(오판정하면 실제보다 적은
   금액으로 발주해 포인트 부족·발주 실패로 이어질 위험).

**실제로 반영한 것**: `onchannel_client.py::get_product()`가
`extends_info`를 파싱해 `OnchannelShippingInfo`로 노출하고,
`channel_adapter.py::OnchannelChannelAdapter.lookup_product()`가
이를 `ProductLookupResult.shipping_info`로 그대로 전달한다(신규
테스트 3개, `tests/test_onchannel_client.py`). 이 값은 Phase 5의
배송비 수동 입력 화면에서 사용자에게 "온채널 API 제안값"으로
참고 표시하는 용도로만 쓴다 — 자동 채택하지 않는다. Gate D
(`order_submission_service.py::_verify_point_balance_or_block`)의
"배송비 미확인이므로 항상 차단" 로직 자체는 이번 라운드에서는
변경하지 않는다(위 3가지 불확실성이 남아 있는 한 그대로 유지가
안전한 선택).

**교훈**: 스펙 전수조사를 "예상 키워드로 grep"하면 그 키워드와
안 겹치는 실제 필드를 놓친다 — 이후 유사한 계약 조사에서는 항상
스키마 트리를 재귀적으로 전부 순회하고 description을 직접 읽는
방식을 우선한다.

## [High] IA-001: 승인 금액 예약 부재와 실행 직전 한도 누락

근거:

- `app/domains/purchase_task/order_approval_service.py:271`, `:290`: 승인 시 CONSUMED 금액만 합산한다.
- 같은 파일 `:409`, `:431`: ACTIVE/실행 중/결과불명 금액은 집계하지 않는다.
- 같은 파일 `:455`: 실행 직전 재검증은 승인 만료와 상품가/배송비 변경만 검사한다.
- `app/domains/purchase_task/order_submission_service.py:605`: 이 재검증 뒤 실제 잔액이 필요 금액보다 많은지만 검사하며 일간/월간 한도는 재검사하지 않는다.

격리 재현 결과:

```text
two_approvals ['ACTIVE', 'ACTIVE'] total 26000 limit 20000.0
second_still_executable ACTIVE prior_spend 13000
```

일간/월간 한도 각각 20,000원, 상품가 10,000원 + 배송비 3,000원의 서로 다른 작업 두 건을 순차 승인했다. 둘 다 ACTIVE가 됐다. 첫 승인을 CONSUMED로 전환한 뒤에도 둘째 승인 재검증이 통과했다. 경쟁 스레드 없이도 재현된다. 실제 외부 전송은 실행하지 않았다.

영향: 잔액이 충분하면 승인 유효기간 안의 여러 작업이 사용자 총액 한도를 초과할 수 있다. RESULT_UNKNOWN이 실제로 성공한 경우에도 그 금액은 다른 작업의 한도에서 빠진다. 동일 작업 UNKNOWN 차단은 별도 작업의 총액 초과를 막지 못한다.

수정 방향: 회사별 영속 금액 예약을 조건부 갱신/DB 트랜잭션으로 확보하고, 승인·실행 중·결과불명을 포함한다. 전송 직전에 최신 정책과 예약 유효성을 검증한다. 외부 호출을 DB 트랜잭션에 오래 묶는 방식은 피한다.

재검증: 순차 이중 승인, 두 Session/두 프로세스, 한도 변경, UNKNOWN, 재시작, 예약 해제 및 만료를 검증해야 한다.

## [High] IA-002: 성공 승인 수정으로 소비 집계 소실

근거:

- `order_approval_service.py:131`: `confirm_shipping_cost()`는 기존 CONSUMED 상태도 PENDING_SHIPPING_COST로 덮어쓴다.
- `router.py:1013`의 배송비 저장 경로는 회사 소유 작업 존재를 검사하지만 완료 상태 수정 금지는 없다.
- 소비 집계는 현재 CONSUMED 상태의 변경 가능한 승인 행에 의존한다.

격리 재현 결과:

```text
spent_before_after_reconfirm 13000 0
```

성공 처리된 승인의 배송비를 같은 금액으로 다시 확인했을 뿐인데 일간 집계가 13,000원에서 0원이 됐다. 공급처 주문 취소나 환불은 없었다. 서비스 직접 호출 재현과 라우터 경로의 정적 확인이며 실제 HTTP/외부 발주 재현은 아니다.

영향: 성공 주문 이력 자체가 삭제되는 것은 아니지만 한도 집계가 실제 지출보다 작아진다.

수정 방향: 소비 사실은 불변 금액 장부/발주 시도와 연결하고 승인 편집과 분리한다. CONSUMED 행 재사용을 차단하고 승인 버전은 별도 기록한다.

재검증: 성공 후 배송비 재확인/재승인/무효화로 누적 소비가 감소하지 않는지 확인한다. 실제 환불의 금액 해제는 별도 명시적 사건으로만 처리한다.

## [High] IA-003: 최신 잔여 포인트 정책 미강제

정적 근거: `finalize_approval()`은 전달받은 current_points로 최소 잔여 포인트를 평가한다. 실제 전송 경로 `order_submission_service.py:615` 이후는 최신 포인트가 이번 상품가+배송비 이상인지만 검사한다. 최신 잔액에서 최소 잔여 기준을 뺀 값, 승인 뒤 바뀐 회사 정책은 검사하지 않는다.

재현 조건 예시: 최소 잔여 30,000원, 필요 금액 13,000원으로 승인한 뒤 다른 거래로 실제 잔액이 20,000원이 되면 단순 잔액 검사에는 통과하지만 실행 후 7,000원만 남는다. 이 항목은 코드 경로 확인이며 해당 숫자로 전체 Fake 전송 재현은 아직 하지 않았다.

수정/재검증: 최종 금액 예약과 같은 게이트에서 최신 잔액·최소 잔여·설정 버전을 검사하고, 승인 당시 스냅샷만으로 허용하지 않는다.

### [Critical] IA-004: 처리 중인 동일 작업이 새 키로 중복 발주됨

- 근거: `order_submission_service.py:142`의 `compute_idempotency_key()`는 기존 시도 개수+1을 키에 넣는다. 첫 IN_FLIGHT 행이 생긴 뒤 두 번째 요청이 들어오면 키가 달라진다.
- `:320`은 미해소 UNKNOWN만 차단하고 IN_FLIGHT 작업을 차단하지 않는다. `:620`의 키 UNIQUE는 서로 다른 키를 막지 못한다.
- 격리 재현: 기존 `OrderApprovalGateIntegrationTestCase`의 임시 DB, InMemoryCredentialStore, 상품/포인트/판매신청/발주 Fake를 사용했다. Gate D는 mock하지 않았으며 유효 승인 행은 기존 fixture처럼 삽입했다. 첫 Fake 전송 내부에서 첫 요청이 완료되기 전에 같은 작업·상품·옵션으로 두 번째 제출을 호출했다. 두 제출 모두 키를 서버가 계산했다.

```text
OVERLAPPING_SAME_TASK SUCCEEDED SUCCEEDED fake_sends 2 different_keys True
```

이것은 스레드 부하 시험이 아니라 첫 요청 IN_FLIGHT 저장 이후 둘째 요청 진입이라는 실행 순서를 결정적으로 재현한 시험이다. 첫 승인 CONSUMED 처리 전에 둘째 요청도 ACTIVE 승인을 읽는다. 실제 온채널 호출은 0회다.

수정 방향: 회사/업무 주문 단위로 하나의 실행 소유권을 DB에서 원자적으로 확보한다. 시도 순번 증가는 명시적으로 재시도 가능한 종결 상태에서만 허용하고 IN_FLIGHT/성공/미해소 UNKNOWN에는 금지한다. 승인 자체도 원자적으로 실행 점유해야 한다. 옵션 변경이나 순서 변경으로 같은 업무 주문을 다시 보낼 수 없는지 검증한다.

### [High] IA-005: 승인된 상품과 다른 상품도 동가이면 제출 가능

- 근거: 승인 조회 키는 회사·연결·작업뿐이며 `order_approval_service.py::revalidate_before_submission()`의 입력에는 상품/옵션/수취인 지문이 없다. 상품가 합계만 비교한다.
- 같은 격리 fixture에서 승인 상품은 `CH-APPROVED-OTHER`, 제출 상품은 기존 합성 `CH1234567`로 두고 가격 합계를 같게 했더니 전체 제출 서비스가 Fake 발주까지 도달했다.

```text
DIFFERENT_PRODUCT SUCCEEDED fake_sends 1
```

수정 방향: 상품·옵션·수량·배송비·수취정보와 관련 정책 버전에 승인을 결합한다. 민감 원문을 일반 로그나 승인 장부에 복제하지 말고 서버에서 정규화한 지문 등으로 대조한다. 동일 총액의 다른 상품/옵션/주소 및 승인 후 변경을 거부하는 테스트가 필요하다.

검증 공통: import 전 DATABASE_URL=메모리 SQLite, socket 연결 금지, 기존 fixture 임시 파일 및 가짜 자격증명만 사용. 실행 종료 코드 0, Fake 호출 수 직접 확인, cleanup/teardown 수행. 전면 감사와 전체 회귀 완료를 뜻하지 않는다.

### [Medium] IA-006: ACTIVE 합산 수정의 동일 승인 재요청 회귀

수정본에서 같은 승인에 `finalize_approval()`을 한 번 더 호출하면 자신의 기존 ACTIVE 예약액과 이번 필요 금액을 중복 합산한다. 한도 20,000원, 단일 주문 13,000원으로 재현했다.

```text
initial ACTIVE reserved 13000
reapprove rejected PENDING_SHIPPING_COST reserved_after 0
```

원인은 `finalize_approval()`의 `spent + required` 계산과 `_sum_reserved_amount()`에서 현재 승인 제외/증분 계산이 없는 조합이다. 더블 클릭·응답 유실 후 재요청에 기존 정상 승인까지 PENDING으로 바뀌고 예약 합계가 사라진다. 실행 중 예약 보존 문제와 결합할 수 있지만 이번 재현은 재승인 경로 자체만 검증했다.

수정 방향: 동일 승인/버전 재요청은 멱등하게 반환하거나 변경 전후 차액으로 원자적으로 처리한다. 변경 거부가 기존 유효 승인을 파괴하지 않아야 한다. 실제 실행 중인 금액은 승인 UI 상태와 무관하게 보존한다.

### 보고서 해석 정정

## 전수 감사 재개 결과 (2026-09-14)

### [Critical] IA-007: Provider 성공 저장 후 승인 소비 실패 시 재발주 가능

`order_submission_service.py::_finalize_attempt()`가 온채널 성공과 주문번호를 먼저 별도 commit하고, 이후 `PurchaseOrderApprovalService.mark_consumed()`가 다시 commit한다. 두 작업은 하나의 복구 가능한 상태전이로 묶이지 않는다. `mark_consumed()`에서 장애를 주입한 격리 재현 결과:

```text
CRASH_GAP SUCCEEDED ORDER-VIA-APPROVAL sends 1
CRASH_RETRY SUCCEEDED sends 2 keys_differ True
```

첫 시도는 DB에 SUCCEEDED와 주문번호가 남았는데 승인 소비만 실패했다. 같은 작업 재호출은 기존 성공을 차단하지 않고 새 키를 생성해 두 번째 Fake 발주를 보냈다. 실제 외부 호출은 없다.

수정 방향: 성공/주문번호를 최우선 영구 증거로 삼아 같은 업무 주문의 후속 제출을 영구 차단한다. 승인 소비·한도 장부 반영은 성공 기록을 기준으로 재구축 가능해야 한다. 성공 이후 로컬 후처리 실패를 발주 실패처럼 재시도하지 않는다.

### [Critical] IA-008: 결과불명 주문을 실제 생성으로 확정한 뒤 재발주 가능

`_has_unresolved_unknown_attempt()`은 UNRESOLVED/STILL_UNCLEAR만 막는다. `resolve_unknown_attempt(... ORDER_CONFIRMED ...)`는 주문번호를 기록하지만 시도 상태는 RESULT_UNKNOWN이며 승인 소비/성공 업무 주문 잠금을 만들지 않는다. 격리 재현:

```text
CONFIRMED_UNKNOWN_RETRY SUCCEEDED sends 1
```

이미 온채널 주문이 존재한다고 사람이 확정한 뒤 같은 업무 주문을 다시 제출하자 Fake 발주가 새로 실행됐다. ORDER_CONFIRMED는 재시도 가능 상태가 아니라 성공과 동일한 종단 차단이어야 하며 소비/예약 장부에도 반영돼야 한다.

### [High] IA-009: 제품의 기본 자동결제 한도가 사용자 확정 기준과 다름

공식 운영기준 `HOMEZ_USER_OPERATION_SETTINGS.md:87-89`는 건당 50,000원, 일 100,000원, 월 500,000원이다. 실제 최종 발주 기본값 `purchase_task/constants.py:697-706`은 각각 100,000원, 300,000원, 3,000,000원이다. 문서보다 건당 2배, 일 3배, 월 6배까지 허용한다. 화면에 저장된 명시 설정이 있으면 그 값이 우선하지만 미설정 상태에서 안전 기본값이라는 코드 설명은 사용자 결정과 일치하지 않는다.

### [High] IA-010: 결제수단 기본값 변경에 재인증이 없음

`payment/router.py` 상단은 결제수단 변경이 모두 비밀번호 재확인을 요구한다고 설명한다. 등록/비활성화에는 토큰 검사가 있지만 `/methods/{method_id}/set-default`에는 `X-Recent-Auth-Token` 입력과 `_require_recent_auth()` 호출이 없다. 현재 Provider는 Fake뿐이므로 실제 결제가 실행되는 직접 위험은 아직 없지만 실제 Provider 연결 전에 반드시 닫아야 한다.

### [High] IA-011: 결제·환불 Provider 연결 전 트랜잭션 설계 공백

- 결제수단 등록은 Provider 토큰을 Credential Store에 먼저 저장하고 DB 행을 나중에 commit한다. DB 실패 시 비밀 토큰 고아가 남는다.
- 기본 결제수단 변경은 기존 기본값 해제를 먼저 commit하고 새 기본값을 별도 commit한다. 두 번째 실패 시 기본값이 사라진다.
- 환불 실행은 외부 Executor 호출 후 조건부 DB 전이/commit한다. 응답 후 장애나 동시 실행이면 외부 환불 성공 여부와 로컬 상태가 갈리고 재호출 위험이 생긴다.

현재 모두 Fake라 실금전 피해는 발생하지 않지만 실제 Provider로 교체하기 전에 시도 장부, 멱등성 키, UNKNOWN, 복구 절차가 필요하다.

### [High] IA-012: 전체 회귀 명령이 실제 OS 자격증명 저장소를 변경함

`tests/test_windows_credential_store.py:34` 이하 테스트는 Windows에서 실제 `WindowsCredentialStore.save/read/delete()`를 호출한다. UUID 테스트 target을 정리하도록 설계됐지만, 테스트 도중 실제 OS 공유 자원에 쓰고 중단/프로세스 종료 시 잔존 가능하다. 따라서 `unittest discover` 전체 회귀를 “자격증명 무접촉”이라고 보고할 수 없다.

이번 독립 감사에서 전체 회귀를 시작했으나 이 사실을 정적 점검으로 확인한 즉시, 해당 파일에 도달하기 전에 이 감사 소유 프로세스를 Ctrl-C로 중단했다. 출력상 AI 학습 테스트 구간까지 진행됐고 실패 표시는 없었으나 완료 수치는 없다. 실제 자격증명 테스트 실행 전이므로 이 감사로 생성한 Credential target은 없다. 향후 전체 회귀는 OS 통합 테스트를 명시적으로 분리하거나 격리 저장소를 주입해야 한다. 실제 DB를 읽는 테스트도 별도 목록으로 분리해야 한다.

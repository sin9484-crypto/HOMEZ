## 왜 10개를 이번 라운드에서 구현하지 않았는가

11개 항목을 전수 조사한 결과, 이들은 "기존 안전장치에 게이트 하나
추가"가 아니라 **각각 독립적인 신규 기능**이었다 — 상당수는 이
저장소에 아직 없는 인프라를 전제로 한다:

- **캐싱 계층 부재**: `app/domains/cache/`(service.py/memory.py/
  redis.py)가 전부 0바이트 빈 스텁이고 어디서도 쓰이지 않는다.
  7-8·8-5·8-6은 전부 이 계층(또는 동등한 대체 설계)이 있어야
  일관되게 구현할 수 있다 — 없는 채로 각 호출부마다 따로 만들면
  중복되고 서로 다른 동작을 하는 3~4개의 임시방편이 생긴다.
- **스케줄러 작업이 사실상 없음**: `app/domains/scheduler/jobs.py`
  전체에 등록된 작업은 주간 백업 리허설 1개뿐이다. 7-16(휴면
  공급처 점검)·10-17(일간 회수확인)은 반드시 주기 실행 인프라가
  필요한데, 이 저장소에는 "매일 실행되는 작업"이라는 개념 자체가
  아직 없다.
- **외부 데이터 출처 미정**: 10-17("판매중지 또는 회수 대상 여부")은
  실제로 어떤 외부 API/데이터셋을 조회할지가 전혀 정의돼 있지
  않다 — 이런 공식 소스(예: 정부 리콜 정보 API)를 추측으로 골라
  연동을 만드는 것은 "확인되지 않은 값을 채우지 않는다"는 이 감사
  전체의 원칙과 정면으로 어긋난다. 사용자가 실제 데이터 출처를
  지정해야 시작할 수 있다.
- **모델에 비교 대상 필드 자체가 없음**: 10-4가 요구하는
  상품명/옵션/수량/크기/제조사/원산지 비교는 `ProductCandidate`
  모델에 해당 필드가 아예 없어서, 비교 로직 이전에 Model 확장(+
  Migration)부터 필요하다. 10-5(나란히 표시 UI)는 10-4가 먼저
  있어야 의미가 생긴다.
- **이미 있는 게이트가 실행 경로에 배선되지 않음**: 8-19가 요구하는
  `check_virtual_stock_allows_auto_order()`는 이미 구현·테스트
  완료 상태지만, "표시 재고 수치를 어디서 읽어올지"가 이 저장소
  어디에도 연결돼 있지 않다(자체 docstring이 이미 이 사실을
  인정하고 있음) — 실제로 배선하려면 판매채널 리스팅에 "표시 재고"
  필드부터 추가해야 한다.

이런 항목들을 이번 라운드 안에 전부 급하게 구현하면, 정확히 이
감사가 막으려는 것과 같은 문제(제대로 설계·검증되지 않은 안전
기능이 오히려 오작동해 실제 업무를 잘못 막거나, 막아야 할 것을
못 막는 상황)를 만들 위험이 크다. 그래서 **8-16(가장 독립적이고,
기존 알림 인프라만으로 완결 가능)만 이번 라운드에서 완성**하고,
나머지 9개는 각각 필요한 선행 설계를 아래에 정리해 다음 라운드가
바로 시작할 수 있게 한다.

## 8-16 구현 내역(완료)

- `PurchaseChannelConnection.consecutive_failure_count`(신규 컬럼,
  Migration `20260915_04`) — 실제 조회(lookup_product 등) 실패마다
  증가, 성공하면 0으로 리셋.
- 임계치(`CONSECUTIVE_LOOKUP_FAILURE_NOTIFY_THRESHOLD = 3`, 문서에
  구체적 횟수가 없어 추측하지 않고 조정 가능한 상수로 둠)에
  "처음" 도달하는 순간에만 활성 SUPER_ADMIN 전원에게 알림
  (`SUPPLIER_LOOKUP_REPEATED_FAILURE`, 신규 이벤트 카탈로그 항목).
- 회귀 중 실제 결함 발견: idempotency_key를 카운터 값만으로 만들면
  스트릭이 리셋된 뒤 같은 값을 다시 지나가면서 두 번째 알림이
  "중복"으로 조용히 스킵됐다 — 알림 발생 시각(마이크로초)을 함께
  넣어 수정.
- 테스트: 서비스 레벨 카운터 증가/리셋 2건 +
  `RepeatedLookupFailureNotificationTestCase`(임계치 도달시 알림,
  같은 스트릭 반복 알림 안 함, 새 스트릭 재알림) 3건 + Migration
  테스트 4건, 관련 테스트 전부 통과 확인.

## 남은 9개 항목 — 다음 라운드를 위한 선행 설계 메모

각 항목마다 "무엇이 없어서 못 만들었는지"와 "다음에 시작할 때
먼저 정할 것"만 짧게 남긴다(설계 확정 아님, 착수 지점 표시).

- **7-8(매입처 캐시/조회간격)**: `app/domains/cache/`를 실제로
  채울지, 아니면 각 조회 대상(가격/재고/판매가능여부)마다
  `*_valid_until` 필드를 개별로 둘지부터 결정 필요. 8-5/8-6과
  같은 설계로 묶어서 한 번에 처리하는 것이 중복을 줄인다.
- **7-11(공급처 반복 사고시 자동일시중지)**: 공급처 단위로
  품절/오배송/취소/배송지연을 집계할 장소가 없다 —
  `CompanySupplierRelation` 또는 신규 테이블에 "최근 N건 중
  실패율" 같은 집계 필드/로직이 먼저 필요. "사용자에게 재사용
  여부를 묻는다"는 승인 플로우(알림 + 응답 API)도 별도 설계 필요.
- **7-16(휴면 공급처 자동점검)**: `last_order_at` 같은 필드가
  공급처 관계 모델에 없다. 스케줄러에 일간/주간 작업이 추가돼야
  "자동"이 성립한다(현재는 수동 트리거만 가능).
- **8-5/8-6(가격/재고 TTL)**: `price_valid_until`은 이미 있지만
  사용자가 수동 입력하는 값이고 자동 계산·설정 화면 연동이 없다.
  "기본값 30분/10분 + 사용자 설정 가능"을 어디(회사별 설정 테이블,
  `user_settings` 등)에 저장할지 결정 필요.
- **8-19(가상재고 0 처리)**: `check_virtual_stock_allows_auto_order()`
  자체는 있다 — "표시 재고" 필드를 판매채널 리스팅 모델에 추가하고,
  주문 접수/조회실패 이벤트에서 이 함수를 실제로 호출하는 배선만
  하면 된다. 9개 중 가장 작은 남은 작업.
- **10-4/10-5(상품속성 불일치 검출+표시)**: `ProductCandidate`에
  options/quantity/size/manufacturer/origin_country 컬럼 추가(+
  Migration) → 비교 유틸리티 → 프론트(console.js) 나란히표시 UI.
  세 단계 다 필요해 9개 중 가장 큰 작업.
- **10-17/10-18(회수·판매중지 자동확인)**: **사용자 확인 필요** —
  어떤 외부 데이터 출처(공식 API/데이터셋)를 쓸지 먼저 정해야
  한다. 출처가 정해지기 전까지는 추측으로 연동을 만들지 않는다
  (이 감사 전체의 원칙). 출처가 정해지면 스케줄러 일간 작업 +
  판정 로직 + 10-18의 즉시중지·알림 액션 순서로 진행 가능.

## 결론

8-16을 완료하고 나머지 9개는 각각 구체적으로 "무엇이 막고 있는지"
를 기록해 다음 라운드가 재조사 없이 바로 시작할 수 있게 했다.
10-17/10-18은 특히 사용자의 명시적 데이터 출처 결정 없이는
착수 자체가 불가능하다.

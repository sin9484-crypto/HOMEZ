# 개발본 vs 설치본 DB — 공식 업무 DB 선택 준비 문서

- 작성일: 2026-09-15 (전면 감사 후속, 11단계 지시문 Phase 7)
- 상태: **읽기 전용 정리 문서 — 이 문서 자체는 아무것도 결정·병합·
  적용하지 않는다.** 실제 DB 파일은 어느 쪽도 전혀 쓰지 않았다(전부
  `mode=ro` 읽기 전용 재확인).
- 목적: 사용자가 "앞으로 실제 검증(온채널 발주, 쿠팡 등록 등)을
  어느 DB 기준으로 계속할지"를 결정할 수 있도록 현재 사실만 정리한다.

## 1. 두 DB는 완전히 다른 파일이다(재확인, 2026-09-15 기준)

| 항목 | 개발본(`C:\Users\Daum pc\Homez-OS\homez.db`) | 설치본(`%LOCALAPPDATA%\HOMEZ\data\homez.db`) |
|---|---|---|
| 파일 크기 | 3,420,160 bytes | 2,953,216 bytes |
| 마지막 수정 | 2026-09-14 20:20 | 2026-08-29 09:02:41 |
| 적용된 Migration 수 | 60 / 64 | 41 / 64 |
| 마지막 적용 Migration | `20260911_01_add_unknown_resolution_and_tracking_refresh.sql` | `20260828_02_add_listing_wizard_soft_delete.sql` |
| 테이블 수 | 143 | 115 |
| `purchase_channel_connections` 존재 | 있음 | **없음** |
| `purchase_order_approvals` 존재 | 있음 | **없음** |

저장소에 있는 Migration 파일은 총 64개다. 개발본은 4개(이번 세션
Phase 2~5가 추가한 `20260915_00`~`03`)가 미적용, 설치본은 23개가
미적용이다 — 이번 세션이 추가한 4개를 포함해 **둘 다 어느 실제 DB
파일에도 적용하지 않았다**(임시 SQLite에서만 검증, 이번 감사
전체의 표준 경계).

설치본은 2026-08-29 이후 완전히 정지 상태다 — 이후 추가된 온채널
연결(`purchase_channel_connections`), 발주 승인(`purchase_order_
approvals`), 옵션 스냅샷, 업무 주문 중복 방지 인덱스, 환불 실행
마커, 백업 암호화(`is_encrypted`) 등 이번 세션까지의 모든 작업이
설치본 스키마에는 전혀 존재하지 않는다.

## 2. 왜 이 선택이 중요한가

`app/desktop/paths.py::is_frozen()`이 개발 체크아웃(`False`)과
PyInstaller 설치본(`True`)을 구분해 서로 다른 DB 파일을 가리킨다.
지금까지 여러 세션의 "실제 검증 완료" 표현은 전부 **개발본 기준**
이었다 — 설치본을 그대로 실행하면:

- 로그인 이후 온채널/쿠팡 연동 관련 화면 다수가 스키마 자체가 없어
  즉시 깨질 가능성이 높다(직접 실행해 확인한 적은 없음 — 아래 3번
  참고).
- 지금 당장 설치본으로 실사용을 재개하면, 이번 세션이 고친
  IA-001~012 방어 로직·백업 암호화 등도 전혀 적용되지 않은 오래된
  코드/스키마 조합으로 동작하게 된다.

## 3. 이 문서가 확인하지 않은 것(추측 금지)

- 설치본 앱(`.exe`)을 실제로 실행했을 때 어떤 화면이 어떻게 깨지는지
  — 이번 라운드에서 설치본을 직접 실행해 확인하지 않았다.
- 설치본 DB 안에 실제 데이터(가입한 회사/사용자/기존 매입 이력 등)가
  남아 있는지, 있다면 그 양과 가치 — 스키마 비교만 했고 실제 행
  데이터는 조회하지 않았다.

## 4. 선택지와 각각의 실행 경로(둘 다 이번 세션에서 실행하지 않음)

### 선택지 A — 개발본을 공식 업무 DB로 계속 사용

- 실행 경로: 별도 조치 불필요, 지금처럼 개발 체크아웃에서 계속
  작업·검증한다.
- 장점: 이미 스키마가 최신(60/64)이고, 이번 세션이 고친 안전장치가
  전부 적용 가능한 상태.
- 단점: 최종적으로 사용자가 실제로 쓸 배포본(설치본)과 계속
  괴리된다 — 언젠가는 설치본도 따라잡아야 한다(선택지 C로 미루는
  것과 같다).

### 선택지 B — 설치본을 최신화한 뒤 설치본 기준으로 전환

- 실행 경로(승인 필요, 이번 세션 미실행):
  1. 설치본 DB 백업(암호화 포함, Phase 5 이후 규칙).
  2. 임시 사본에서 23개 pending Migration 리허설(`MigrationRunner.
     apply_pending()`로 스크래치 복사본에 먼저 적용해 무결성·
     체크섬 확인 — `docs/V7_OPERATING_DB_MIGRATION_PLAN.md`가 남긴
     선례와 동일한 절차, 다만 그 문서는 2026-08-21 기준이라 지금은
     범위가 훨씬 넓다).
  3. 사용자 명시 승인 후 실제 설치본에 적용.
  4. 설치본 앱을 직접 실행해 새로 생긴 기능(온채널 연결, 발주 승인
     등)이 정상 동작하는지 실사용 검증.
- 장점: 실제 사용자가 쓸 파일이 곧 검증 대상이 된다 — 배포본과
  개발본의 괴리가 사라진다.
- 단점: 23개 Migration을 한 번에 실제 DB에 적용하는 것은 이번
  세션이 겪은 규모보다 크다 — 리허설·검증에 상당한 시간이 필요하고,
  설치본에 남아 있을 수 있는 실제 데이터(3번 항목, 미확인) 보존
  여부를 먼저 확인해야 한다.

### 선택지 C — 재설치(Fresh install)로 설치본을 완전히 새로 만듦

- 실행 경로(승인 필요, 이번 세션 미실행): 기존 설치본 DB를 백업만
  해두고, 새로 빌드한 설치 파일로 재설치 → `bootstrap_environment()`
  가 신규 설치 경로를 타면서 최신 스키마로 처음부터 시작.
- 장점: Migration 순서·중간 실패 위험이 없다(새 DB는 처음부터
  최신 스키마).
- 단점: 설치본에 남아 있던 기존 데이터(3번 항목, 있다면)는 자동으로
  이관되지 않는다 — 별도 이관 절차가 필요하거나, 처음부터 다시
  등록해야 한다.

## 5. 이 문서의 결론

**결정하지 않는다.** 세 선택지 모두 장단점이 있고, 선택지 B/C 모두
"설치본에 남아 있는 실제 데이터의 가치"라는 이 문서가 확인하지 않은
사실에 크게 좌우된다. 사용자가 다음을 알려주면 그에 맞는 구체적
실행 계획(백업 절차, 리허설 범위, 승인 지점)을 별도로 수립한다:

1. 설치본에 지금 보존해야 할 실제 데이터가 있는가?
2. 있다면 선택지 B(최신화)와 C(재설치+수동 이관) 중 어느 쪽을
   선호하는가, 아니면 당분간 선택지 A(개발본 유지)로 미룰 것인가?

이 질문에 대한 답이 나오기 전까지, 이번 감사의 기존 규칙(11.7 절)
그대로 **실제 온채널 발주·실제 쿠팡 상품 등록 제출은 차단 유지**
한다.

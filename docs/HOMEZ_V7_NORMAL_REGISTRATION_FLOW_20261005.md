# 정상 상품 등록 흐름 — 매 상품 문의가 필요 없는 구조 (2026-10-05, 설계 정리)

이 문서는 **정리**이며 구현·실행이 아니다. 새 범용 정책 플랫폼을 만들지 않고 기존 저장·검증 기능을 쓴다.
출처 구분: 직접 확인 = 이번 세션에서 코드·DB·화면으로 확인, 기록 = 이전 문서·보고 재사용, 추론, 미확인.

## 1. 원칙

1. 상품마다 달라지는 사실(상품명·옵션·용량·구성수량·가격)은 **상품별 근거**로 관리한다. 공급처 API·상세 화면·정보고시에서 얻을 수 있는 것은 먼저 그것을 쓴다.
2. 공급처 전체에 적용되는 조건(이미지 이용권리·판매채널 제한·포장비 정책)은 **공급처 단위로 한 번** 확인하고, "모든 상품 공통"이라는 근거가 있을 때만 다른 상품에 재사용한다. 근거가 없으면 상품별 예외로 남긴다.
3. 회사 결정(최소마진 18%, 반품준비율, 세금 방침)은 **상품마다 다시 결정하지 않는다.**
4. 누락·충돌이 있는 상품만 "예외 검토"로 보류하고 다른 상품을 막지 않는다.

## 2. 근거 범위 분류표

| 항목 | 적용 범위 | 문의 전에 쓰는 출처 | 현재 저장 위치(직접 확인) | 재사용 규칙 |
|---|---|---|---|---|
| 상품명·옵션 목록·옵션 가격·기본 배송비 | 상품별 | 온채널 상세 조회 `GET seller/product/{코드}` | 속성 비교 run의 공급처 값(`product_attribute_match`) | 조회 시점 값만. 가격·재고는 최신성 필요 |
| 제조사·원산지·사용기한·KC 여부 | 상품별 | 상세 응답 `gosi_info`(기재 확인 수준) | 위저드 정보고시 + `notice_confirmed_*` | 상품별. 실물·인증서 검증이 아님을 기록 |
| 용량·사이즈 | 상품별(옵션별) | 옵션 라벨, `gosi_info.prd_weight`(옵션별 분리 안 됨) | 위저드 구매옵션 | 옵션 라벨 기준이라는 수준을 기록 |
| **구성수량(판매 1개 = 공급 옵션 몇 개)** | 옵션별 | 공급처 응답에 필드 없음 → 상세 설명·공급처 확인 | `supplier_option_links.units_per_sale`(확인자·시각 저장, 현재 0건) | 해당 옵션에만. 다른 옵션·상품으로 추정 금지 |
| 판매신청 상태·발주 가능 | 공급처+상품 | 판매신청 기록 | `purchase_sales_application_attempts` | 상품별 상태 |
| **이미지·상세설명 이용권리** | 공급처 공통 질문(상품 예외 가능) | 온채널 공개 가이드 5페이지에는 조항 없음(기록, 24차) | 구조 없음 — 미디어 자산별 `rights_status`(Wizard#1 자산 1·2는 VERIFIED — 그 근거 유형은 확인하지 못했고 공급처 서면 근거는 없음) | 공급처 회신이 "전 상품 공통"이면 공급처 규칙으로, 아니면 상품별 |
| **판매채널(쿠팡) 제한** | 공급처 공통 + 상품 필드 | 상품 화면 "운영채널분류"(기록, 가격자율) | 구조 없음 | 공급처 회신 근거가 있을 때만 공통 |
| **포장비·별도 처리비** | 공급처 정책 + 상품 예외 | 공급처 회신 | 위저드 경제성 `packaging_cost`(상품·계정별 입력, 현재 null) | 공통 정책이면 입력값을 미리 채우는 기본값으로, 상품 예외만 수정 |
| 채널 수수료 | 카테고리별 | 쿠팡 공개 요율표(사용자 채택 9.6%는 뷰티 기본) | 위저드 경제성 | 카테고리가 다르면 상품별(예: WING에서 확인한 주방 카테고리는 10.8%) |
| 최소마진 | 회사 | 사용자 결정 18% | `company_channel_policy_settings`(0.18, version 1) | 전 상품 공통 |
| 반품준비율·세금 방침 | 회사 | 사용자 결정(3% 채택, 세금 미결정) | 위저드별 입력(회사 기본값 저장소 없음) | 전 상품 공통이어야 하나 현재 상품마다 재입력 |

## 3. 상품 하나의 정상 흐름 (자동 / 사람 / 승인)

1. 후보 등록·공급처 식별(`ONCHANNEL:코드`) — 사람
2. 공급처 상세 조회 1회 → 속성 비교 run(공급처 값) — **승인(외부 조회)**
3. 필수정보 점검: 위 분류표에서 비어 있는 칸만 목록화 — 자동
4. 비어 있는 칸 중 **공급처 공통 조건**은 공급처 규칙이 이미 확인돼 있으면 재사용, 없으면 공급처에 한 번 문의 — **승인(발송)**
5. 비어 있는 칸 중 **상품별 사실**(구성수량 등)만 해당 상품에 한해 확인 — 사람/문의
6. 위저드 입력·경제성(회사 결정 값은 기본값) → 사전검사·18% 판정 — 자동
7. 등록 내용 비교 기록 → 사람이 해소(속성 비교) → 옵션 연결 저장 — **승인**
8. 8단계 승인(재인증) → 전송 직전 점검 — **승인**
9. 쿠팡 생성 POST — **별도 승인**. 결과불명이면 자동 재시도 없이 보류

누락·충돌이 있는 상품은 3~5단계에서 "예외 검토"로 멈추고 다른 상품은 계속된다.

## 4. 현재 구조의 공백 (직접 확인, 구현하지 않음)

> **63차 정정(2026-10-05)**: 아래 G1·G2는 출시 필수 개발이 아니라 **출시 후 개선 후보**다. "공개 가이드에 조항이 없다"는 "권리가 없다"나 "모든 온채널 상품이 회신 대기"가 아니며, 이용권리·판매채널 제한은 코드 차단 조건이 아니다(분류 C). 표 2절의 "공급처 회신이 와야 재사용" 서술은 회신이 *있을 때*의 재사용 규칙이지 대기 조건이 아니다. 우선 기존 정책 문서·상품 근거·설정을 재사용한다.

- **G1. 공급처 공통 조건 저장소 없음.** `supplier_capability_records`는 8개 능력 플래그(상품·옵션·가격·재고·배송비·배송기간·발주·취소)뿐이고(`supplier_capability/constants.py`) 이용권리·채널 제한·포장비 항목이 없다. 이 때문에 공급처 회신이 와도 "다른 상품에 재사용"할 자리가 없다.
- **G2. 회사 경제성 기본값 저장소 없음.** `company_channel_policy_settings`에는 최소마진·한도만 있고 반품준비율·세금·포장비 기본값이 없어 새 위저드마다 입력한다. `clone`은 같은 상품 후보의 위저드를 복제하는 용도라 다른 상품의 기본값 원천이 될 수 없다(`listing_wizard_service.clone`).
- **G3. 구성수량의 확인 기록은 옵션 연결에만 있다.** 연결 저장은 외부 확인 조회를 동반하므로 승인이 필요하다.

선택지(승인 시, 이번에는 구현하지 않음): G1은 능력 플래그 항목 추가, G2는 설정 열 추가(Migration 필요) 또는 가장 최근 승인 위저드의 회사 결정 값을 이어받는 방식. 어느 쪽도 새 플랫폼이 아니라 기존 저장소의 확장이다.

## 5. 회신 기록 템플릿

- 범위: 상품별 / 공급처 공통 / 회사 — 근거: 원문 위치(메시지 ID·날짜)
- 적용 대상: 상품 코드·옵션, 또는 "공급처 전체"라는 문구의 원문
- 예외·조건: 원문 그대로
- 확인 시점·확인자
- 회신이 없거나 읽지 못했으면 "회신 미조회" 또는 "회신 없음(조회 범위: …)"으로 구분해서 쓴다.

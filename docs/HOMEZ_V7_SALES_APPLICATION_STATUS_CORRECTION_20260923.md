## 2. 판매신청 판정 정정

**정정 전(10차)**: "판매신청 게이트... 미충족(코드 기준)".

**정정 후**: **"과거 접수 응답(2026-09-14, HTTP 200)은 있으나, HOMEZ
내부 추적 테이블(`purchase_sales_application_attempts`)에 그 기록이
남아 있지 않다. 온채널 쪽의 현재 판매 가능 상태는 이번 라운드에서
재확인하지 않았으므로 미확인이다. 과거 HTTP 200을 현재도 유효한
판매 가능 상태의 충분한 증거로 단정하지 않는다. 자동 재신청은
금지한다(§3-3 근거)."**

10차의 "미충족"이라는 단어는 **HOMEZ 내부 게이트 함수
(`is_sales_application_confirmed()`)의 반환값**(사실, 정확함)을
마치 **온채널 쪽의 실제 판매 가능 여부에 대한 단정**인 것처럼 읽히게
서술한 것이 문제였다. 이 둘은 서로 다른 사실이며, 아래 §3에서
분리해 재정리한다.

### 3-2. HTTP 성공과 업무 처리 성공의 구분

- **HTTP 200**은 "온채널 서버가 이 요청을 문법적으로 정상 처리해
  응답했다"는 사실만 증명한다.
- **업무적으로 판매신청이 승인됐는가**는 별개 사실이며, 온채널
  공식 답변으로 "승인 상태를 조회하는 API 자체가 없다"고 이미
  확정돼 있다(`HOMEZ_ONCHANNEL_OPENAPI_FINDINGS_20260908.md`) — 즉
  **HOMEZ든 이 문서든, HTTP 200만으로 "지금 판매 가능하다"를 증명할
  방법이 원천적으로 없다.**
- "재조회로 404 해소"는 간접 정황 증거(상품이 최소한 이 계정에
  "보이게" 됐다는 뜻)이지, "판매신청이 승인됐다"는 직접 증거가
  아니다 — 404가 정확히 무엇을 뜻하는지(신청 여부/상품 자체
  유무/다른 사유) 이 저장소는 확정하지 못했다.

### 3-3. 현재 코드가 내부 기록 부재 때문에 실제로 차단하는 것

코드 추적(`sales_application_service.py`) 결과, 내부 기록이 없을 때
막히는 것은 정확히 다음 하나뿐이다:

- `PurchaseOrderSubmissionService.submit_order()`가 발주를 시도할 때
  거치는 `is_sales_application_confirmed()`가 False를 반환 →
  `ensure_sales_application_submitted(confirm_real_submission=True)`를
  **자동으로 다시 호출**하려 한다(발주 코드 경로 자체가 그렇게 짜여
  있다).
- 이 재호출은 `apply_for_sale()`을 **다시** 실행한다 — 즉 **내부
  기록 공백이 실제로 유발하는 위험은 "재신청 자동 유발"이다.**
- 코드 자체의 docstring(`onchannel_client.py::apply_for_sale()`)이
  이미 이렇게 명시한다: **"409는 스펙상 '이미 신청된 상품 재신청'
  정황으로 추정되지만... 공식 답변으로 확정된 사실은 아니다"** —
  즉 **이미 신청된 상품에 재신청했을 때 온채널이 정확히 어떻게
  응답하는지(멱등하게 수용/거부/다른 부작용) 이 저장소 어디에도
  확정된 근거가 없다.**

이번 지시문의 "재요청 처리 방식이 불명확하면 재신청하지 않는다"는
원칙을 그대로 적용해, **이번 라운드도 재신청을 실행하지 않는다.**

## 4. 외부 상태 확인·기록 보완 계획 (설계만, 미실행)

### 4-1. 공식 조회 방법 — 새 엔드포인트를 추정하지 않는다

`docs/HOMEZ_ONCHANNEL_OPENAPI_FINDINGS_20260908.md`(재조사 절)가 이미
확인한 사실: 온채널 상품 상세 스키마의 `status` enum은
`1=판매전, 2=판매, 3=판매중단, 4=일시품절, 5=품절`이며, **"정황상(직접
확인 아님) 판매신청 승인 전 상품은 상태값 1(판매전)에 머물 가능성"**을
시사한다. 이는 새로 추정한 엔드포인트가 아니라, **이미 구현·승인
계획에 포함돼 있던 기존 `GET /openapi/seller/product/{코드}`
(=코드의 `lookup_product()`, D3 §2-3에 이미 기술)**를 그대로 쓰는
것이다 — 승인 상태 전용 API는 없다는 사실은 그대로 유지한다(이
조회가 "확정 답"을 주는 것이 아니라 "정황 신호(status 값)"만 준다는
한계를 그대로 인정).

### 4-2. 인증 조회가 필요할 경우의 계획(실행 안 함 — 승인 대상)

| 항목 | 내용 |
|---|---|
| 대상 | 연결 id=4(`ONCHANNEL`, `sin9**`), 상품 `CH1147184` |
| 목적 | 상품 상태값(`status`)과 응답 가능 여부로 판매신청의 현재 정황을 재확인(직접 증거 아님, 정황 증거로만 취급) |
| 방법 | `GET /openapi/seller/product/{코드}`(기존 `lookup_product()` 경로) — 새 엔드포인트 아님 |
| 최대 호출 수 | 1회(D3 §2-3의 기존 "상품당 1회, 최대 3회" 예산 안에 포함 — 별도 추가 예산 아님) |
| 재시도 | 없음 |
| DB 쓰기 | 기존 `lookup_product()` 경로의 기존 부작용만(연결의 "실조회 성공" 기록 갱신) — 판매신청 관련 테이블에는 **이 조회만으로는 쓰지 않는다**(§4-3에서 별도 설계) |
| 중단 조건 | 4xx/5xx 응답, 한도(1회) 도달 |

**이번 라운드는 이 조회를 실행하지 않았다** — 승인 대상으로만 남긴다.

### 4-3. 외부 상태가 확인됐을 때의 내부 기록 보완 설계(제안만, 구현·반영 안 함)

**하지 않을 것(지시문 금지 사항 그대로 준수)**:
- 2026-09-14 호출을 "방금 실행한 것"처럼 새 행으로 기록하지 않는다.
- 원본 DB에 `purchase_sales_application_attempts` 성공 행을 수동
  `INSERT`하지 않는다(코드 경로를 거치지 않은 값을 신뢰할 근거로
  둔갑시키지 않기 위함).

**제안하는 보완 범위(향후 별도 승인·구현 라운드용, 이번에 구현 안 함)**:

1. `PurchaseSalesApplicationAttempt`에 **정황 기반 재확인**을 표현할
   새 상태(가칭 `RECONCILED_FROM_PRODUCT_STATUS`)를 추가 — "실제
   신청 응답을 다시 받은 것"과 구분되는, "독립적인 조회로 정황상
   신청된 것으로 보인다고 사람이 확인한 것"임을 명확히 구분되는
   상태로 설계한다(추정과 확인을 섞지 않기 위함).
2. 이 상태로의 전이는 **사람의 명시적 확인 행동**(예: 콘솔에서 상품
   상태값을 직접 보고 "확인함" 버튼을 누르는 것)을 전제로 하고,
   `SATISFIES_ORDER_GATE`에 포함할지는 **별도 사용자 결정 사항**으로
   남긴다(포함하면 발주 게이트가 열리므로 신중한 판단이 필요 —
   이 문서는 그 판단을 대신하지 않는다).
3. 새 상태·전이가 생기면 `ensure_sales_application_submitted()`가
   기존 SUBMITTED와 동일하게 취급할지, 별도로 취급할지도 명시적으로
   결정해야 한다(현재는 결정하지 않음).
4. **집중 테스트 범위(제안만)**: `tests/test_purchase_sales_application_service.py`에
   신규 상태 전이 케이스 추가(정황 확인 성공/실패, `SATISFIES_ORDER_GATE`
   포함 여부에 따른 발주 게이트 통과·차단 양쪽), 기존 SUBMITTED
   경로와의 상호작용(신규 상태 → 이후 실제 SUBMITTED 응답을 받으면
   상태가 어떻게 갱신돼야 하는지) 케이스 포함.

## 5. 상품·기존 Wizard 진행점 연결 (읽기 전용 재확인)

### 5-1. 시험상품 추천 상태

CH1147184를 추천 후보로 유지한다. **추천 근거는 확보된 옵션·가격
정보(2026-09-14 이전 과거 API 관측, 최신 아님)일 뿐이며, 수익성·
안전성 검증이 끝났다는 뜻이 아니다** — 재고·현재가·판매신청의
현재 유효성 전부 미확인 상태다. 사용자 확정으로 취급하지 않는다.

### 5-2. 기존 실행 대상이 현재도 동일한지 확인(이번 라운드에 실 DB 재조회)

| 대상 | 확인 결과 |
|---|---|
| `PurchaseTask#1` | `status=SEARCH_REQUIRED`, `channel_connection_id=None`(아직 매입 계정 미배정), `caution_reason`에 "테스트 목적, 실제 쿠팡 주문 아님, 추정치" 명시 그대로 |
| `ProductCandidate#3` | `candidate_key=PRIVATE:1:PRIVATE_MANUAL:COUPANG:ONCHANNEL:CH1147184`, `source_reference=ONCHANNEL:CH1147184`, `status=ANALYZED` — CH1147184와의 연결이 문자열로 명시적으로 저장돼 있음을 이번에 직접 확인(추정 아님) |
| `product_candidate_decisions` | id=3, `candidate_id=3`, `action=APPROVE`, `operator_id=1`, `decided_at=2026-09-14 10:34:20` — 운영자 승인 사실 확인 |
| `ListingWizard#1` | `product_candidate_id=3`(위 후보와 연결 확인), `current_step=CHANNELS`, `status=DRAFT`, `version=6`, `updated_at=2026-09-14 10:56:06` — **9일간 진행 없음** |
| `store_connections#1` | `COUPANG`, `CONNECTED` — 동일 |
| `purchase_channel_connections#4` | `ONCHANNEL`, 계정 `sin9**`, `CONNECTED` — 동일(이번에 §3-1에서 연결 id를 명시적으로 재확인) |

### 5-3. Wizard 정지 단계의 정확한 내용(`draft_json` 등 필드 수준 확인)

- **정지 단계**: 4단계(`CHANNELS`, 판매채널 선택) — `channel_selections_json = []`(빈 배열, 아직 아무 채널도 확정 선택되지 않음).
- **완료된 입력**: 1단계(상품 소스: 후보#3 연결) / 2단계(초안: 상품명·브랜드·카테고리·설명 저장됨, `draft_json.options` **= 빈 배열** — 옵션 4종이 아직 Wizard 초안에 입력되지 않았다) / 3단계(이미지: `selected_media_asset_ids_json=[1]`, 1장 선택).
- **미완료**: 4단계(채널 확정) 자체, 5단계 이후 전부(`economics_input_json`/`economics_result_json`/`validation_result_json`/`approval_package_json` 전부 `None`).
- **외부 상품 생성 여부**: `materialized_listing_ids_json = []` — **비어 있음. 쿠팡 등 외부에 실제로 생성된 리스팅이 없다는 뜻**(9-1절 초안 단계 그대로, 등록 자체는 실행된 적 없음).
- **옵션·SKU 상태**: Wizard 초안 자체에는 옵션이 0개(직접 확인), D3 문서의 옵션 4종 매핑표는 **2026-09-14 이전 과거 API 관측을 근거로 한 별도 문서상의 초안**일 뿐 Wizard DB 행에는 아직 반영되지 않았다 — **신규 등록을 반복하는 대신, 재개 시 이 Wizard(id=1)의 2단계로 돌아가 옵션을 채우는 것이 맞는 다음 행동**이다(새 Wizard 생성 불필요).

### 5-4. `PurchaseOrderApproval#1` — 재사용 금지, 원본 미수정

DB 컬럼은 여전히 `status=ACTIVE`이지만 `expires_at=2026-09-14
10:09:26`로 실제로는 만료된 지 오래다(코드가 지연 평가 구조라 컬럼
자체는 갱신 안 됨 — 2026-09-14 감사가 이미 지적한 것과 동일 사실,
이번에 다시 읽기 전용으로 재확인만 했다). **이 행을 실행에 재사용
하지 않는다.** 원본 값도 수정하지 않았다(코드 실행으로 자연스럽게
`EXPIRED`로 갱신되는 지연 평가 구조를 그대로 둔다). 재개하려면
최신 상품가·포인트·배송비로 `confirm_shipping_cost()` +
`finalize_approval()`을 **새로 다시** 호출해야 한다는 사실만 기록한다.

## 6. DB 적용 준비 연결

기존 업무 DB 결정(9차, 저장소 루트)은 다시 열지 않는다. 이번 라운드
읽기 전용 재확인 결과 새로운 충돌 증거는 없다(§1의 미적용 Migration
재확인 결과 2건, 해시 동일 — §6 승인안과 완전히 일치). **원본 적용
승인이 이번에도 확인되지 않아 적용하지 않는다.** 승인안 목록·해시가
바뀌지 않았으므로 기존 승인안을 그대로 유지하되, 실행은 하지 않았다.

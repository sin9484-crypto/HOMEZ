## 1. 시험상품 선정 기준(확정 아님 — 기준만)

시험상품 자체는 이 문서에서 확정하지 않는다. 다음 기준으로 사용자와
함께 최종 결정한다:

- **옵션이 단순함**: 색상/사이즈 등 선택지가 1~2개 이하 — 옵션 매핑
  오류 가능성을 낮춘다.
- **파손·변질 위험이 낮음**: 액체·유리·냉장 등 배송 중 파손·변질
  가능성이 있는 품목은 위험으로 표시하고 완화책(포장 확인 등)을 함께
  제시한다. 사용자가 제공한 상품은 이 기준만으로 임의로 제외하지 않는다.
- **배송비가 명확함**: 온채널 상품상세에서 배송비가 고정값으로
  확인되고, "배송비 사전 확인 불가"(이전 라운드에서 이미 발견한
  구조적 제약, `docs/audits/...` 참고) 케이스에 해당하지 않는 상품.
- **반품 비용이 명확함**: 반품 시 왕복 배송비·회수 조건이 온채널
  상품상세 또는 공식 정책에서 확인 가능한 상품.
- **금액이 작음**: 시험 성격상 실제 손실 가능 금액을 최소화한다.

**참고(확정 아님, 2026-09-19 정정)**: 이번 대화 이전에 실행 주체
Codex가 실제로 `page=1, page_size=100, status=1`로 조회한 결과
`total_cnt=1, last_page=1`, 상품 CH1147184 "레이펄스 워터리스 샴푸/
바디워시" 1건이 응답됐다(감사 문서 30절 — 이전에 "page_size=1이라
1건만 나왔다"고 적었던 것은 실제 호출값을 확인하지 않은 채 코드
기본값으로 추측한 오류였고, 지금 정정한다). `page_size=100`이
`total_cnt=1`보다 훨씬 크므로 이 1건은 페이지 크기의 한계가 아니라
**"이 연결 계정의 status=1(정상판매) 상품이 정확히 1개"**라는
서버 자신의 보고다.

이 상품은 액체(샴푸/바디워시)라 누출·동결 가능성이 위험 요소이지만, 사용자 상품이므로
임의로 제외하지 않고 2-1절에서 다른 상품과 같은 기준으로 비교한다. 다만 "정상판매 상품이
1개"가 곧 "온채널 전체 상품이 1개"라는 뜻은 아니다 — `status` 파라미터는 1(정상판매)~5(품절)
중 하나만 거르는 필터이며, 단종·판매중단·일시품절·품절 상태의 상품 유무는 이번 조회로 알 수 없다.

## 2. 온채널 상품목록 실제 확인이 필요하면(별도 승인 대상)

정상판매(status=1) 외 다른 상태의 상품이 있는지 보려면 `status`
파라미터를 생략하거나 2~5 값으로 각각 다시 조회해야 한다 — 이는 이번
문서 작성 시점까지 실행하지 않은 **추가 실 API 호출**이다(`page_size`
는 이미 최대값 100으로 조회됐으므로 더 늘릴 필요는 없다). 필요하면
목적("정상판매 외 상태 상품 존재 여부 확인")·경로(동일
`GET seller/product`)·최대 횟수(생략 조회 1회 우선 시도, 안 되면
상태값별 최대 4회 추가)·재시도 없음을 명시해 별도로 승인을 요청한다.
(참고: status=2~5 조회는 "단종/판매중단/일시품절/품절" 여부 확인일
뿐, 정상판매 후보 발굴의 우선 작업이 아니다 — 지시문에서 명시적으로
구분함.)

### 10-5. 판매신청(발주 전제조건) 게이트 — 정밀 확인 결과 "미충족"(코드 기준)

2026-09-14 감사 문서는 `POST /openapi/seller/product/apply`(CH1147184)
실제 호출 1회가 HTTP 200으로 접수 확인됐고 재조회로 404가 해소됐다고
기록한다. 그러나 이번에 `purchase_sales_application_attempts` 테이블을
읽기 전용으로 직접 조회한 결과 **CH1147184에 대한 행이 0건**이다.

코드(`sales_application_service.py::is_sales_application_confirmed()`)는
오직 이 테이블에 `SUBMITTED`(류) 상태 행이 있을 때만 True를 반환한다 —
**추측으로 통과시키지 않는 설계**다. 즉:

- 2026-09-14의 실제 접수 자체는 사실로 남아 있다(온채널 서버 쪽에서는
  접수됐을 가능성이 높다 — 당시 재조회로 404 해소까지 확인됨).
- 그러나 그 호출이 이 테이블에 기록되는 공식 경로
  (`ensure_sales_application_submitted()`)를 거치지 않고 서비스 계층을
  직접 호출하는 방식으로 이뤄졌기 때문에, **현재 코드의 판매신청 게이트
  기준으로는 "미충족"**이다.
- `submit_order()`를 이 상품·연결로 다시 호출하면, 코드는 이 사실을 모른
  채 `ensure_sales_application_submitted(confirm_real_submission=True)`를
  **다시** 시도한다 — 온채널이 이미 접수된 신청에 대해 재요청을 어떻게
  처리하는지(멱등 응답/중복 거부/오류)는 **미확인**이다.

지시 원문대로 **미충족이면 자동으로 판매신청하지 않고 실제 발주를
보류한다** — 이번 라운드는 이 사실을 기록만 하고 재신청을 실행하지
않았다. 재신청 여부(또는 2026-09-14 접수를 "이미 충족"으로 수동
인정할지)는 별도의 사용자 결정 사항으로 남긴다(§10-6 실행 순서의
"판매채널 상품등록" 이전 단계에 위치).

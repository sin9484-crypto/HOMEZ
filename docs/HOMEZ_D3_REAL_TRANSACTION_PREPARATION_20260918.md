## 1. 시험상품 선정 기준(확정 아님 — 기준만)

시험상품 자체는 이 문서에서 확정하지 않는다. 다음 기준으로 사용자와
함께 최종 결정한다:

- **옵션이 단순함**: 색상/사이즈 등 선택지가 1~2개 이하 — 옵션 매핑
  오류 가능성을 낮춘다.
- **파손·변질 위험이 낮음**: 액체·유리·냉장 등 배송 중 파손·변질
  가능성이 있는 품목은 1순위에서 제외한다(반품 발생 시 원인 규명이
  어려워짐).
- **배송비가 명확함**: 온채널 상품상세에서 배송비가 고정값으로
  확인되고, "배송비 사전 확인 불가"(이전 라운드에서 이미 발견한
  구조적 제약, `docs/audits/...` 참고) 케이스에 해당하지 않는 상품.
- **반품 비용이 명확함**: 반품 시 왕복 배송비·회수 조건이 온채널
  상품상세 또는 공식 정책에서 확인 가능한 상품.
- **금액이 작음**: 시험 성격상 실제 손실 가능 금액을 최소화한다.

**참고(확정 아님, 2026-09-19 정정)**: 이번 대화 이전에 실행 주체
Codex가 실제로 `page=1, page_size=100, status=1`로 조회한 결과
`total_cnt=1, last_page=1`, 상품 CH1147184 "레이펄스 워터리스 샴푸/
바디워시" 1건이 응답됐다(감사 문서 30절 — 이전에 "page_size=1이라
1건만 나왔다"고 적었던 것은 실제 호출값을 확인하지 않은 채 코드
기본값으로 추측한 오류였고, 지금 정정한다). `page_size=100`이
`total_cnt=1`보다 훨씬 크므로 이 1건은 페이지 크기의 한계가 아니라
**"이 연결 계정의 status=1(정상판매) 상품이 정확히 1개"**라는
서버 자신의 보고다.

이 상품은 **액체(샴푸/바디워시)**이므로 위 "파손·변질 위험이 낮음"
기준에서 다른 후보와 비교가 필요하다 — 포장 방식(펌프형 용기, 밀봉
여부)에 따라 배송 중 누출 위험이 달라질 수 있으므로, 이 상품을 최종
후보로 쓸지는 사용자 확인 후 결정한다. 다만 "정상판매 상품이 1개"가
곧 "온채널 전체 상품이 1개"라는 뜻은 아니다 — `status` 파라미터는
1(정상판매)~5(품절) 중 하나만 거르는 필터이며, 단종·판매중단·
일시품절·품절 상태의 상품 유무는 이번 조회로 알 수 없다.

## 2. 온채널 상품목록 실제 확인이 필요하면(별도 승인 대상)

파라미터를 생략하거나 2~5 값으로 각각 다시 조회해야 한다 — 이는 이번
문서 작성 시점까지 실행하지 않은 **추가 실 API 호출**이다(`page_size`

목적("정상판매 외 상태 상품 존재 여부 확인")·경로(동일
`GET seller/product`)·최대 횟수(생략 조회 1회 우선 시도, 안 되면
상태값별 최대 4회 추가)·재시도 없음을 명시해 별도로 승인을 요청한다.

## 2-4. Migration 원본 적용 준비(재확인 2026-09-20, 읽기 전용)

실제 `homez.db` 적용 73건 / 저장소 74개 → **미적용 정확히 1개**
`20260918_00_create_order_collection_test_budget_usage_schema.sql`
(1,762바이트, SHA-256 `93ca072401873e920365f1974fd70116626544c81cfd9ff0fc880597a481b4b1`,
저장소에만 있고 DB에 없는 파일·DB에만 있는 파일 없음). 대상 DB는 저장소 루트의
`homez.db`(3,702,784바이트). 변경 내용은 신규 테이블 1개 + 인덱스 3개(기존
테이블 ALTER 없음, 롤백은 파일 하단 주석의 `DROP TABLE IF EXISTS`). 절차:
① 기존 `BackupService`로 백업 → 무결성·SHA-256 검증 → ② 복사본에서 리허설
(적용·재적용 실패·데이터 보존·`integrity_check`·FK) → ③ **명시 승인 후** 원본
적용 → ④ 무결성·ORM·기존 기능 확인. 이번 라운드 코드 변경(한도 보호)은
스키마를 바꾸지 않으므로 새 Migration은 없고, 미적용 상태의 최신 코드는 기존
기능을 깨지 않음을 이전에 격리 서버로 확인했다(신규 시험예산 엔드포인트만
`503 SCHEMA_UPDATE_REQUIRED`로 안전하게 거절). 원본 적용은 실행하지 않았다.

## 3. D3 실행 순서 (생략 없이 순서대로)

각 단계는 이전 단계가 사용자 승인과 함께 완료된 뒤에만 진행한다.

| # | 단계 | 실행 주체 | 승인 필요 여부 |
|---|---|---|---|
| ① | 시험상품 후보·공급가·배송비·재고·반품조건 확인 | 사용자+Claude(공개 정보·기존 API 응답 조사) | 후보 확정에 사용자 확인 필요 |
| ② | 판매채널(쿠팡) 시험 거래 정책 및 필요한 사용자 승인 확인 | 조사 | 정책 자체는 조사만, 실행 없음 |
| ③ | 온채널 판매신청 및 처리 결과 확인 | 실 API(`PurchaseSalesApplicationService.ensure_sales_application_submitted()`, `confirm_real_submission=True`) | **실행 전 별도 승인 필요** |
| ④ | 쿠팡 상품등록 및 실제 판매 가능 상태 확인 | 실 API(기존 상품등록 플로우, 이번 세션에서 새로 만들지 않음) | **실행 전 별도 승인 필요** |
| ⑤ | HOMEZ에서 쿠팡 상품·옵션 ↔ 온채널 상품·옵션·SKU 연결 | HOMEZ 내부 작업(`OrderSkuResolution` 등 기존 구조 재사용) | 실제 DB 쓰기 — 승인 필요 |
| ⑥ | 연결계정·배송지·총액·현재 잔액·발주 승인 조건 확인 | 사용자가 앱에서 직접 확인(배송지 원문은 채팅 요구 안 함) | 사용자 확인 |
| ⑦ | 허용된 방식으로 실제 주문 생성 | 사용자가 쿠팡에서 직접 주문(HOMEZ가 대신 주문하지 않음) | 사용자 실행 |
| ⑧ | 제한된 예산으로 주문 수집·동일 주문 재조회 | `run_test_budget_collection()`(3-2절, 최대 GET 2회) | **실행 전 별도 승인 필요**(연결 ID 고정) |
| ⑨ | 사용자 승인 후 온채널 발주·예치금 차감 확인 | 실 API(`submit_order()`, `confirm_real_submission=True`) | **실행 전 별도 승인 필요** |
| ⑩ | 송장·배송·매입비용·정산 대조 | 실 API 조회(`lookup_tracking()`) + 수동 대조(25절 — 자동 정산 연결 없음) | 조회는 읽기 전용, 별도 승인 있으면 실행 |
| ⑪ | 별도 승인된 두 번째 주문의 반품·환불 검증 | 실 거래 | **완전히 별도의 승인 필요, ①~⑩ 완료 후에만** |

**엄수 사항**:
- 상품등록(④)과 매핑(⑤) 완료 전에는 ⑦(실제 주문) 단계로 넘어가지
  않는다.
- 실제 거래는 허위 실적·리뷰 조작 방식으로 진행하지 않는다.
- 반품 시험(⑪)은 플랫폼·공급처의 실제 정책에 맞게 진행하며 허위
  불량 사유를 만들지 않는다.
- 개인정보(수취인 정보 등)·자격증명은 채팅이나 로그에 원문으로
  남기지 않고 앱의 보호된 입력 경로(Console UI)만 사용한다.

## 4. 이번 라운드에서 구분해 보고하는 두 가지

- **"D3 준비 작업 가능"**: 위 ①·②의 조사, 계획 문서 작성, 코드
  레벨 필수 결함 수정(D2에서 완료)은 지금 진행 가능한 범위다.
- **"실제 주문 실행 준비 완료"**: ③ 이후(실제 판매신청·상품등록·
  주문·발주)는 **아직 아니다** — 상품 확정·정책 승인·실제 API 호출
  승인이 각각 남아 있다.

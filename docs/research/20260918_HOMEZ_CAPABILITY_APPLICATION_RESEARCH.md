## 1. 조사 범위와 증거 한계

CLAUDE.md, .cursor/rules, 프로젝트 상태, 확정 결정, V8 이미지 리딩 설계, 도메인 목록과 아래 핵심 코드의 선언·일부 본문을 읽었다. 전체 함수 실행·테스트·운영 DB 조회를 수행하지 않았다. 소스에 기능이 있다는 것과 실제 운영에서 검증됐다는 것을 구분한다. 전 기능의 완전한 감사를 했다고 주장하지 않는다.

조사 시작 시 channel_adapter.py, order_submission_service.py, test_purchase_order_submission_service.py에 다른 작업의 미커밋 변경이 있었다. 이를 보존하고 제품 코드는 수정하지 않는다. 이번 신규 보고서와 연구 색인만 수정 대상으로 삼는다. 사용자 확정 지침의 외부 자료 CTO 분석 보관 규칙에 따라 문서만 커밋·push한다.

## 3. 데이터 전략

사용자 확정: 네이버 트렌드·검색은 NAVER API HUB, 무료 범위, 추천 1시간 갱신, 상품군→구체 모델 비교의 2단계다. 본인 스마트스토어 주문·상품·정산은 별도 커머스 API다.

API HUB 분야별·키워드별 쇼핑인사이트는 상대 클릭 지수를 제공한다[S1,S2]. 이를 상품 실제 조회수나 시장 전체 판매량으로 표시하지 않는다. 서로 다른 요청에서 정규화된 지수는 비교 조건을 맞추지 않고 직접 순위를 매기지 않는다. 카테고리 전수 인기 순위도 후보군을 실제로 포괄하지 않으면 주장하지 않는다.

1시간은 HOMEZ 재계산 주기다. 원천이 일 단위면 시간별 신규 수요가 생긴 것으로 표현하지 않는다. 무료 API의 호출 한도와 모델 실행비는 별개이며, 생성·분석 모델이 무료라고 가정하지 않는다. 무료 사용이 확인되지 않은 서비스는 기본 비활성으로 둔다.

현재 네이버 공식 문서는 별도 API데이터솔루션의 통계·트렌드 영역과 구독별 quota를 안내한다[S3,S4]. API HUB와 혼동하지 않는다. 가입·가격·현재 계정 접근 조건을 확인하지 않았으므로 무료 기능 목록에는 포함하지 않는다. 전체 시장 상품 검색을 제공하던 구형 쇼핑 검색 API는 종료 공지 대상이다[S8].

## 5. 비용 대비 우선 개발 조합

### 먼저: 한 화면에서 손실·처리 지연 줄이기

E01 예외 통합함 + E05 SKU 연결 제안 + F01 마진차이 + B05 예치금 부족을 우선 검토한다. 이미 쌓이는 내부 데이터로 시작할 수 있고 외부 전체 시장 자료 의존성이 낮다. 현재 반자동 필수 흐름 완성과 중복되는 항목은 별도 신규 프로젝트로 만들지 않고 기존 작업에 연결한다.

### 다음: 사용자 지정 2단계 상품추천

A01+A06+C05를 결합한다. 한 시간마다 자료 신선도와 무료 예산을 점검하고 상품군을 추천한다. 사용자가 선택하면 공급처의 모델·옵션·가격을 비교한다. 관심도가 높아도 공급 정보가 없으면 관심 후보로 남긴다. 모델 비교 상품 수나 가중치는 사용자 확정값이 아니며 변경 가능한 설정으로 설계한다.

### V8: 이미지 읽기와 운영 AI

C01~C04를 V8 기존 설계에 연결한다. 신규 이미지 생성보다 사양 충돌 검출과 편집 필요성 판정을 먼저 평가한다. G02는 근거를 찾는 조회 보조부터 시작한다. G03은 표본 개수만으로 모델 성능을 보장하지 말고 기간별 평가와 기존 규칙 대비 손실·처리시간 개선을 확인한다.

개발 기간은 이 보고에서 약속하지 않는다. 각 묶음의 실제 Provider 연결 여부와 내부 데이터 완결성이 기간을 좌우한다. 연구 항목 42개를 현재 V7 5영업일 목표에 일괄 추가하지 않는다.

## 6. 결합 시나리오

1. 무선청소기 관심도 상승: A01로 상품군 추천 → A06으로 공급가·배송비 확인 → C05로 등록 준비도 확인 → 사용자 검토. 공급 가능한 LG 모델이 없으면 모델을 만들어 추천하지 않는다.
2. 주문이 늘었지만 돈이 부족: F03으로 미정산 매출과 승인된 매입자금 구분 → B05 예치금 부족 경고 → 사용자가 운영자금 계획 조정. 매출을 당장 쓸 수 있는 현금으로 계산하지 않는다.
3. 발주 직전 가격 인상: F04로 마진 재계산 → 기존 가격변경 정책에 따라 중지·통지 → B03 대체 공급처 제안. 원래 발주가 UNKNOWN이면 대체 구매하지 않는다.
4. 고객이 배송 전 취소: E03으로 취소요청과 공급처 출고 상태 확인 → 담당자 작업 생성 → 취소·환불 확정값을 F01에 반영. 온채널 취소 API가 있다고 가정하지 않는다.
5. 크기 관련 반품 증가: E07로 원인 후보 추출 → C01로 상세 이미지 치수와 실제 옵션 비교 → C03 수정안 → 승인 후 반영 → 이후 반품률 변화를 관찰한다. 변화만으로 인과관계를 단정하지 않는다.
6. API 장애: G01이 마지막 자료 시각·누락 범위를 표시 → 과거 데이터로 한정한 추천 표시 또는 중지 → 주문/결제 UNKNOWN은 별도 보류. 자료 없음은 판매량 0이 아니다.

## 7. 공통 기술 설계

기존 Modular Monolith와 Service/Repository/Router 패턴을 유지한다. 우선 별도 대형 AI 서버를 만들지 않는다.

- 입력: Provider별 수집 결과, 출처, 기준시각, 수집시각, 완료 여부.
- 식별: company·channel·supplier·model·option 단위 매핑. 동일 상품명만으로 병합 금지.
- 판단: 결정적인 비용 계산·실행 게이트와 AI 설명·추천 분리.
- 결과: 추천 근거·결측·신뢰도·모델/규칙 버전·운영자 결정 보존.
- 평가: 선택된 상품만 관측하는 편향, 시즌, 가격·광고 변화 등을 기록.
- 실행: 기존 승인·한도·Emergency Stop 경로 재사용. 추천 클릭으로 거래 실행하지 않음.
- 운영: 매시간 추천 계산과 주문감지·배송조회 주기는 분리한다.

사용자에게 보여줄 핵심 지표는 등록 준비시간, SKU 오연결률, 발주 전 차단한 적자 금액, 정산 차이 해결률, 실제 마진, 예외 처리시간, API 사용량이다. 수익 개선 수치는 운영 전에는 예측값으로도 단정하지 않는다.

## 8. 보류할 가정

- 시장 전체 실제 조회수·경쟁사 판매량을 현재 키로 조회 가능하다는 가정.
- API HUB 이미지 검색이 이미지 생성 모델이라는 가정.
- 관심도 100이 검색 100건이라는 해석.
- 카드·PayPal 계약 폴더가 있으므로 실결제가 지원된다는 판단.
- 판매량만 높으면 좋은 공급처·상품이라는 판단.
- 고객 주문의 배송정보가 결제 직후부터 불변이라는 가정.
- 은행 연결 없는 Funding 장부가 실제 은행 잔액이라는 판단.
- MFDS 식품 리콜 자료만으로 청소기 등 전상품의 안전성을 확인했다는 판단.
- 학습 관리 화면·최소 표본 충족이 실제 학습 성공을 의미한다는 판단.

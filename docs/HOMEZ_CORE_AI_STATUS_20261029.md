## 1. 트렌드 탐색 AI (Trend Discovery AI, V3)

- **위치**: `app/domains/trend_discovery/` (`service.py` 점수, `adapter.py` 자료원). 진입점은 후보 라우터 `POST /product-candidates/{id}/refresh-trend-analysis` → `product_candidate/trend_analysis_refresh_service.py`.
- **하는 일**: 후보 상품의 검색 추세(증가율·관심도·경쟁도)를 가중치로 합산해 `trend_score`·신뢰도·근거를 만든다. 같은 입력이면 항상 같은 점수.
- **자료원**:
  - 네이버 검색어 트렌드 공식 API(NAVER API HUB). 자격증명 **저장됨**(✅ 존재만 확인).
  - 시험용 Fixture.
  - 무료 한도는 월 30,000회이고, 넘으면 호출하지 않는다(유료 전환 없음).
- **실제 사용**: 2026-09-07에 실제 호출 2회('무선청소기' 200 OK, 13주 시계열). 그 뒤 기록 없음.
- **한계**:
  1. **"탐색"이 아니라 "점수 매기기"다.** 이미 있는 후보의 상품명을 그대로 검색어로 넣는다. 유행하는 키워드나 상품을 스스로 찾지 않는다.
  2. 긴 상품명은 네이버에 검색량이 없어 NO_SIGNAL로 끝난다(오류가 아니라 정직한 '모름'). 검색어를 상품명에서 뽑는 단계가 없다.
  3. 쿠팡 판매·검색 데이터는 쓰지 않는다(공식 API 없음).
  4. 정기 자동 실행(S4)은 보류 상태다. 사람이 버튼을 눌러야 돈다.

## 2. 신제품 탐색 AI (New Product Discovery AI, V3)

- **위치**: `app/domains/new_product_discovery/service.py`.
- **규칙** (`docs/HOMEZ_DECISIONS.md` 확정):
  - 출시일 기준 0~15일이면 신제품이다. 시간대는 Asia/Seoul(UTC+9 고정).
  - 미래 날짜는 오류이고 자동으로 고치지 않는다.
  - 출시일을 모르면 신제품으로 판정하지 않는다.
  - 외부 호출은 없다.
- **실제 사용**: 실제 DB 후보 12건(전부 사람이 넣은 PRIVATE_MANUAL)이 **모두 출시일이 비어 있어** 신제품 판정이 한 번도 나오지 않았다.
- **한계**:
  1. 이것도 **"탐색"이 아니라 "판정기"**다. 새로 나온 상품을 찾아오는 기능이 없다.
  2. 출시일을 가져오는 자료원(공급처 등록일, 쇼핑몰 출시일)이 연결되지 않았다. 지금은 사람이 넣어야 한다.

## 3. 의사결정 AI (Decision AI, V4)

- **위치**: `app/domains/decision/` (`service.py` 1,098줄, `router.py` `/decisions`·`/decision-policies`).
- **흐름**: 후보(V3 결과) → 평가 정책 로드(없으면 중단) → 긴급 중지 확인(최우선) → 축별 결정적 평가 → 평가·점수 저장 → **사람이 승인·보류·거절·덮어쓰기**.
- **지키는 것**:
  - AI 결과만으로 승인 상태가 되지 않는다.
  - 정책 위반·긴급 중지는 점수로 상쇄하지 않는다.
  - 금액은 Decimal로 계산한다.
  - 같은 요청은 한 번만 처리한다(멱등). 회사별로 격리한다.
- **판정 순서**(상품 선별 화면): 정책 → 권리 → 공급 → 운영 → 수익성 → 위험 → 사용자 승인.
- **화면**: 콘솔에 판매 판단 대기 목록, 평가 상세(점수·리뷰 이력), 승인·보류·거절·덮어쓰기가 있다.
- **실제 사용**: 평가 0건, 정책 0건. **평가 정책이 하나도 없어서(VERIFIED 필요) 평가를 시작하지 않도록 막혀 있다** — 설계대로의 안전 차단이다.
- **별도로 쓰이는 것**: 후보 화면의 같은 상품 판별(S1)과 사전 평가(S2: 후보 가능·보류·제외 권고)는 규칙으로 동작한다. 마진 스냅샷이 없으면 '후보 가능'이 되지 않는다.
- **한계**:
  1. 평가 정책(축 가중치·임계값·유효기간)을 사용자가 정해 VERIFIED로 만들어야 쓸 수 있다.
  2. 재판매 권리 도메인이 없어 권리 축은 항상 '자료 필요'다.
  3. 생성형 AI 평가기는 계약(`evaluator_protocol.py`)만 있고 연결되지 않았다.

### 4-2. 권고 설계

**역할**
1. **매일 운영 브리핑**: 주문·반품·문의 마감(고객센터 24시간 등)·허용 만료·정산을 한 화면·한 알림으로.
2. **상품 발굴 파이프라인 조율**: 키워드 후보 → 트렌드 점수 → 신제품 판정 → 의사결정 평가 → **사람 승인 대기열**까지 자동으로 이어 준다(승인은 사람).
3. **할 일 우선순위**: 마감·금액·위험 순으로 정렬하고 "왜 먼저인지"를 함께 보여 준다.
4. **승인 준비**: 필요한 허용을 미리 채운 창과 요약(이번에 만든 기능)으로 준비만 한다. 비밀번호·허용은 사람이 한다.
5. **질문 답변**: "이번 주 반품 몇 건?" 같은 질문에 실제 데이터로 답한다(2단계부터 Claude 선택).

**지키는 선**
- 비서는 **직접 쓰기·구매·결제·승인을 하지 않는다**. 실행은 기존 경로(승인 센터 + 확인창 + 작업 장부)로만 한다.
- 자동화 수준은 L2(초안·준비)까지다. 숫자·판정은 규칙이 하고, AI는 설명만 한다. 모르는 값은 '모름'으로 둔다.
- 긴급 중지·운영자 승인 모드를 그대로 따른다.

**단계**
- **1단계 — 규칙 비서(Claude 없이, 비용 0)**: 브리핑 통합, 발굴 파이프라인 자동 연결, 우선순위 대기열. 기존 조각을 묶는 일이 대부분이다.
- **2단계 — 대화형 비서(Claude 선택)**: 질문 답변, 원인 설명. 월 한도와 승인 센터 허용 안에서만 쓴다.
- **3단계 — 정해진 시간 실행**: 앱 안 일정으로 아침 브리핑과 파이프라인 실행. 허용 범위 안의 읽기만 한다.

### 4-3. 사용자가 정해야 할 것
1. 의사결정 평가 정책 기준값: 축 가중치, 최소 마진, 제외 기준. 정해지면 의사결정 AI가 실제로 동작한다.
2. 트렌드 키워드를 어디서 가져올지: 사람 입력 / 공급처 카테고리 / 네이버 쇼핑 인사이트 등 공식 API 검토.
3. 신제품 출시일 자료원: 공급처 상품 등록일 사용 여부.
4. 2단계 Claude 사용 여부·월 비용 한도(이미지 생성 AI와 별개).
5. 비서 알림 받을 곳: 앱 안 / 이메일.

## 6. 통합 계획 v2 (규칙 AI + 운영 비서 + Claude AI)

### 6-1. 원칙 (모든 단계 공통)
- **규칙이 판정하고, AI는 읽고·설명하고·초안을 쓴다. 사람이 확인한다.** 금액·마진·승인 여부는 AI가 정하지 않는다.
- 외부 쓰기·구매·결제·승인은 비서·AI가 하지 않는다. 승인 센터 + 확인창 + 작업 장부 경로로만 나간다.
- 모르는 값은 '모름'으로 둔다. 개인정보는 가리고 보낸다. Claude 호출은 월 한도·허용 횟수 안에서만.
- 각 단계는 시작 전에 **세부 설계서(만들·고칠 파일 Whitelist, 시험, 완료 기준)** 를 따로 써서 확인받는다 — 이 문서는 순서·범위 계획이다.

### 6-2. 0단계 — 사용자 결정 한 번에 모으기 (코드 없음)
| # | 결정 | 쓰이는 단계 |
|---|---|---|
| D1 | 의사결정 평가 기준(축 비중·최소 승인 점수·최소 신뢰도·제외 조건) — Claude가 초안 제시 | 1 |
| D2 | Claude 사용 여부·모델·월 비용 한도, Anthropic API 키 발급(키 입력은 사용자가 앱에서) | 2·5 |
| D3 | 트렌드 키워드 출처(사람 입력 / 공급처 카테고리 / 공식 API 검토) | 3 |
| D4 | 신제품 출시일 자료원(공급처 상품 등록일 사용 여부) | 3 |
| D5 | 비서 알림 받을 곳(앱 안 / 이메일) | 4 |

### 6-3. 단계별 계획

**1단계 — 의사결정 AI 가동 (Claude 없음, 비용 0)**
- 할 일: 평가 정책은 API(`POST /decision-policies`)만 있고 **화면이 없다** → 쉬운 보기에 "평가 기준" 화면(보기·초안·확정)을 만든다. D1 값으로 정책을 VERIFIED로 등록하고, 실제 후보 1건을 평가해 판매 판단 대기 화면에서 사용자가 승인·보류·거절한다.
- 완료 기준: 실제 평가 1건 저장 + 사용자 검토 1건 기록, 정책 없음·만료 시 평가가 막히는 것 유지 확인.

**2단계 — Claude '높음' 2종 가동 (비용 발생)**
- 대상: 등록 도우미 초안, 고객 응대 답변 초안.
- 할 일: 사용자가 키 등록·모델·한도 설정(D2) → 승인 센터 AI_DRAFT 허용 → 각 1회 실제 호출로 응답 형식·토큰·비용·품질 확인.
- 고객 응대 초안은 쿠팡 쓰기 4·6번(문의·고객센터 답변) 화면에 연결한다: 초안 → 사용자가 고침 → 사용자가 보냄. 24시간 마감이 남은 문의를 먼저 보여 준다.
- 완료 기준: 두 기능 실제 1회씩 성공·사용 기록·월 한도 차감 확인, 초안이 그대로 자동 발송되지 않는 것 확인.
- 진행(2026-10-31, 코드만 — 실제 호출 0회): 쉬운 보기 '더보기 · 설정'에 **AI 사용 설정**(키·모델·월 한도·단가 저장, 이번 달 사용 기록 표 — 위저드 없이 `/ai-settings`), 상품 문의·고객센터 답변 화면에 **AI 답변 초안** 버튼(확인 창 → 답변 칸에 넣기만, 보내기는 지금처럼 사람), 문의를 **오래된 순 + 받은 지 몇 시간**으로 표시(24시간 넘으면 강조 — 쿠팡 공식 기한은 🔴 미확인이라 '기한'이라 쓰지 않음), 초안의 `[확인 필요 …]` 자리가 남은 답변은 서버·화면 모두 보내기 차단. 남은 것: 사용자 D2(키·모델·한도·단가 입력) → 승인 센터 'AI 초안' 허용 → 각 1회 실제 호출. 주의: 최신 모델은 생각(thinking)이 켜진 채로 동작해 출력 상한(고객 응대 700·등록 도우미 1,500 토큰)을 생각에 먼저 쓸 수 있다 — 첫 실제 호출에서 응답이 잘려 '버림'이 나오는지 확인해야 한다(🔴 미확인).

**3단계 — '판정기'를 '탐색기'로 (트렌드·신제품 + URL 분석)**
- 트렌드: 상품명에서 핵심 검색어를 뽑는 규칙(브랜드·용량·수량 제거) + D3 키워드 출처 연결.
- 신제품: D4 자료원에서 출시일(등록일)을 가져와 15일 규칙에 넣는다(없으면 '모름').
- URL 상품 분석(Claude, 중간): 새 상품 URL → 분석 → 후보 생성의 입구로 쓴다(키·허용 있을 때만, 없으면 사람이 읽고 입력).
- 연결: 후보 → 트렌드 점수 → 신제품 판정 → 의사결정 평가 → 승인 대기열.
- 완료 기준: 실제 후보 몇 건이 이 흐름을 끝까지 지나 승인 대기열에 오른다(승인은 사람).
- 진행(2026-10-31, 비용 0 부분만 — 실제 네이버 호출 0회): **검색어 규칙**(`trend_discovery/keyword_rule.py` — 괄호·상품코드·용량·수량·묶음·홍보 문구·색상·브랜드를 지우고, 단어가 3개를 넘으면 '길어요'로 표시만 하고 핵심 단어를 스스로 고르지 않음), **트렌드 갱신이 검색어를 씀**(규칙 제안 또는 사람이 고친 검색어 — 근거에 '규칙'/'사람 확인' 표시, 검색어가 비면 호출하지 않음), **15일 신제품 규칙을 후보에 연결**(`POST /product-candidates/{id}/evaluate-new-product` — 출시일 없음은 '모름'으로 아무것도 저장하지 않음, 미래 출시일도 저장 안 함), **탐색 흐름 화면**(쉬운 보기 분석 → '탐색 흐름' 탭, `GET /product-candidates/discovery-flow` — 후보마다 검색어·트렌드·신제품·판매 판단과 다음 할 일 버튼). URL 분석은 이미 후보를 만든다(기존 `create_draft` → `register_private_candidate`) — 키·허용만 있으면 됨, 이번에 바꾸지 않음. 남은 것(사용자 몫): D3 키워드 출처, D4 출시일 자료원(그 전까지 출시일 있는 후보만 판정), 네이버 키 실제 조회 1회.

**4단계 — 운영 비서 1단계 (규칙, 비용 0)**
- 기존 조각(오늘 브리핑·우선순위 집계·시스템 점검·승인 센터·쿠팡 감시·쿠팡 쓰기 9종)을 비서 화면 하나로 묶는다.

- 반려가 오면 반려 사유 설명(Claude, 중간) 버튼을 그 자리에 둔다(키 있을 때만).

- 진행(2026-10-31, 규칙만 — 외부 호출 0회): 새 화면을 만들지 않고 **'오늘 할 일'의 오늘 브리핑을 비서 브리핑으로 넓혔다**(같은 일을 두 화면에 나누지 않기 위해). ① 가장 먼저 볼 것: 받은 지 24시간 넘은 고객 문의를 맨 앞(반려보다 앞), 문의끼리는 오래된 것부터 — 24시간은 HOMEZ의 '오래됨' 표시이고 쿠팡 기한이라고 쓰지 않음. ② 각 항목 밑에 **'왜 먼저'** 규칙 문구(문의는 받은 지 몇 시간, 모르면 '모름'). ③ **상품 발굴 칸**: 3단계 탐색 흐름의 다음 할 일 개수(검토·평가·신제품·트렌드) + '탐색 흐름 보기'. 읽지 못하면 '읽지 못했어요'(0으로 보이지 않음). ④ 문의 행에 경과 시간, 24시간 넘으면 빨간 칩. ⑤ 브리핑 머리에 '비서는 보여 주고 준비만 해요. 보내기·승인·결제는 직접 해요.' — 오늘 할 일 화면은 읽기(GET)만 한다(시험으로 고정). 이미 있던 것: 승인 준비(승인 센터 일괄 연장·허용 요청), 반려 사유 설명 버튼(키 있을 때만), 시스템 점검 원인 설명. 남은 것: 서버 쪽 브리핑(6단계 정해진 시간 실행·알림에 필요), 알림 받을 곳(4-3의 5번, 사용자 결정).

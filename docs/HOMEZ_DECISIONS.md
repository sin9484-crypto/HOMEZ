# HOMEZ 확정 결정 사항 (사용자/ChatGPT 확정)

이 문서에 기록된 항목은 Claude가 임의로 변경하지 않는다. 변경이 필요하다고
판단되면 이유를 보고하고 사용자 재확인을 받는다.

## 시장/데이터

- 국내 마켓 우선.
- 쿠팡·네이버 스마트스토어를 우선 고려 대상으로 한다.
- 공식 API와 공개 데이터를 우선 사용한다(비공식 크롤링/스크래핑을 기본값으로
  삼지 않는다).
- 기존 금지상품 정책을 유지한다(별도 확장 없이 그대로 적용).

## 신제품 판정 기준

- 출시일(또는 공식 등록일) 기준 0일 이상 15일 이하를 신제품으로 본다.
- 기준 시각과 timezone은 **Asia/Seoul**로 명확히 처리한다.
- 미래 날짜(아직 출시되지 않음)는 오류 또는 별도 검토 대상으로 처리하고 신제품으로
  자동 판정하지 않는다.
- 출시일이 불명확하면 신제품으로 자동 판정하지 않는다(모른다는 사실 자체를 근거에
  남긴다).

## 자동화/운영자 승인

- V3와 V4에서는 운영자 승인이 필수다. AI는 추천만 하고 실제 실행은 운영자 승인
  이후에만 이루어진다.
- 자동화 순서: 추천 → 승인 → 제한된 자동화(단계적으로 확대, 급격한 전면 자동화
  없음).
- Emergency Stop과 자금/수량 한도(Safety Layer)는 V3(발견 AI) 이전에 구현한다.
- V3에서는 실제 상품 등록·구매·주문을 자동 실행하지 않는다(추천/승인 상태 전이만).

## Architecture

- V4까지 FastAPI 기반 Modular Monolith를 유지한다.
- AI Domain은 `ProductCandidate` 계약과 Event를 통해서만 기존 금융/주문 Model과
  연결한다(직접 Model 수정 금지).
- 수집 원본 · AI 판단 · 운영자 결정을 분리해서 저장하고, 서로 덮어쓰지 않는다.

## ProductCandidate 상태 의미 (정책 A, 2026-08-19 CTO 확정)

- `ProductCandidate.status` 값의 이름·DB 컬럼·API 계약은 변경하지 않는다.
- `ANALYZED`는 "AI 분석 완료"가 아니라 **"시스템 검토 단계를 완료하여
  관리자의 판단(승인/보류/거절)이 가능한 상태"**로 공식 정의한다. 실제
  AI/시장 분석을 거쳤는지, 수동 등록 후보의 기본 정보 확인만 거쳤는지는
  evidence_type과 trend_score/novelty_score의 존재 여부로 구분하며,
  상태 이름 자체로는 구분하지 않는다.
- `RECOMMENDED`는 실제 점수 또는 검증된 추천 근거가 있을 때만 도달해야
  한다 — 근거 없이 이 상태로 전환하는 API 호출은 차단한다.
- 전체 상태별 공식 의미는
  `app/domains/product_candidate/constants.py::CandidateStatus`
  docstring이 단일 진실 공급원이다.

## 매입 실행 통합(V7, 2026-09-07 사용자 확정)

상세 목표·설계 기준은
`docs/HOMEZ_V7_INTEGRATED_PROCUREMENT_GOALS_20260907.md` 참고. 여기는
핵심만 요약한다.

- HOMEZ의 목표는 매입처·계정·결제수단·운영 조건을 사용자가 설정하면
  판매 주문 수집부터 매입·결제·배송·취소·환불·정산 대조까지 HOMEZ가
  연결해 처리하는 것이다. 정상 주문마다 사용자가 쇼핑몰을 직접
  방문해 반복 구매하는 흐름은 이 목표를 충족하지 않는다.
- 지원 범위는 국내 위탁판매·국내 구매대행·해외구매대행·병행수입을
  함께 고려한다. 온채널 한 곳만 전제로 설계하지 않는다.
- 구매 실행 방식(HOMEZ 자체 구매대행 / 구매대행 업체 연결 / 사용자
  매입처 계정 연결)과 결제수단(카드·PayPal·계좌·가상계좌·공급처
  예치금·구매용 가상카드)은 서로 배타적 선택지가 아니며, 별도로
  모델링한다.
- "매입 운영 설정"에서 매입처·연결계정, 기본·대체 구매 방식, 지원
  결제수단과 연결 상태, 건별·일별 매입 한도, 최소 예상이익·가격
  상승 허용범위, 배송기한, 자동 실행 범위·예외 처리 조건을
  관리하도록 설계한다. 카드 한 번 등록으로 모든 쇼핑몰 결제가
  가능하다고 가정하지 않는다.
- 공통 거래 흐름은 판매 주문 → 상품·옵션 매칭 → 가격·재고·배송 확인
  → 구매 방식 선택 → 주문·결제 → 배송 → 취소·환불 → 손익 대조이며,
  전 과정에 판매 주문·공급처 주문·결제·배송·환불 식별자를 연결한다.
  결제 성공과 주문 성공은 별도로 확인하고, 결과 불명확 시 재결제나
  대체 매입처 구매를 바로 실행하지 않는다.
- 후속 개발 순서(확정): 현재 작업 완료 → 공통 매입 장부·상태 처리
  감사 및 보완 → 확보한 공식 API의 실제 지원 범위 연결 → 국내
  쇼핑몰 계정 기반 구매 흐름 검증 → 외부 구매대행 업체 연동 → 자체
  구매대행·가상카드의 적용 조건 확보 및 확장.
- 이 목표 설정은 실제 결제·발주 실행 승인이 아니다. 가격·재고
  Model/Migration, 실제 SKU 연결 등 기존 명시적 보류는 이번 목표
  설정만으로 해제되지 않는다. 반복 재설치는 하지 않고 최종 통합
  테스트 시 진행한다. Cursor는 사용하지 않는다.

## UI/브랜드

- UI는 업무용 운영자 Console을 우선한다(소비자용 쇼핑몰 UI가 아님).
- 캐릭터(마스코트)는 onboarding, empty state, AI 분석 중 상태에만 제한적으로
  사용한다.
- 금융, 위험, 보안(사고/경고) 화면에는 캐릭터를 사용하지 않는다.
- 브랜드 디자인(색상·로고 등)은 추후 변경 가능한 것으로 간주하고, 지금 확정하는
  것은 기능/데이터 계약이지 비주얼 디테일이 아니다.

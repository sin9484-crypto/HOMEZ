## 2. 기존 업무 DB 결정 확인 — 재질문하지 않는다

**결론: "업무 DB" = 저장소 루트 `C:\Users\Daum pc\Homez-OS\homez.db`.
이것은 새 결정이 아니라 8차가 놓쳤던 기존 결정을 다시 적용한 것이다.**

8차 문서는 "어느 쪽이 공식 업무 DB인지 단정하지 않는다"며 이 질문을
다시 열었다 — 이것이 이번 라운드가 바로잡아야 할 핵심 오류다. 실제로는
서로 다른 두 질문에 대한 **두 개의 독립된, 서로 모순되지 않는 기존
결정**이 이미 있었다:

### 2-1. 코드 자체의 설계 — "업무 DB"는 애초에 실행 모드에 따라 자동으로 갈린다

`app/desktop/paths.py::get_data_dir()`/`get_homez_db_path()`는 **하나의
함수**가 `is_frozen()`(패키징 여부)에 따라 다른 파일을 가리키도록
설계돼 있다:

| 실행 모드 | `is_frozen()` | 반환 경로 |
|---|---|---|
| 개발 모드(`start_homez.ps1`, `python -m uvicorn app.main:app`) | False | 저장소 루트 `homez.db` |
| 패키징 모드(설치된 `HOMEZ.exe`) | True | `%LOCALAPPDATA%\HOMEZ\data\homez.db`(`HOMEZ_DATA_ROOT`로만 격리 가능) |

즉 두 파일은 "경쟁하는 두 후보" 관계가 아니라 **같은 개념("지금 이
프로세스가 쓸 homez.db")이 실행 방식에 따라 결정되는 서로 다른 값**이다.

### 2-2. 2026-08-31 Preflight 8-A — "패키징 배포본의 공식 운영 DB" 확정 (여전히 유효, 무효화하지 않음)

`docs/HOMEZ_PROJECT_STATE.md`(2026-08-31, "Preflight 8-A(canonical
DB·DB 경로 계약 감사)" 절)에 기록된 사실: 사용자가 Claude의 패키지
가상화 환경 밖(일반 PowerShell)에서 읽기 전용 진단 스크립트
(`HOMEZ_Canonical_DB_Check.ps1`)를 직접 실행해 **"후보 A
(`%LOCALAPPDATA%\HOMEZ\data\homez.db`)를 공식 운영 DB로 확정"**했다.
이것은 **패키징(설치) 배포본이 실행됐을 때 어느 파일을 써야 하는가**에
대한 결정이며, 지금도 유효하다 — 이번 라운드가 이 결정을 무효화하지
않는다.

### 2-3. 2026-09-21 6차(`HOMEZ_V7_TEST_ISOLATION_20260921.md` §7) — "이번 V7 Migration 적용 작업의 업무 DB"를 저장소 루트로 명시적으로 확정 (더 최근, 더 구체적)

같은 문서 §7 원문: **"대상: 코드 저장소 `C:\Users\Daum pc\Homez-OS`
(브랜치 `main`), 업무 DB `C:\Users\Daum pc\Homez-OS\homez.db`."**,
그리고 바로 다음 줄: **"설치본 DB(...)는 별도 대상이며 이 계획에
포함되지 않는다 — 같은 절차를 별도 승인으로 밟아야 하고 그 DB의
미적용 상태는 확인하지 않았다."**

이 결정은 2-2보다 **20일 더 최근**이고, "패키징 배포본 실행 시 어느
파일을 쓰는가"가 아니라 **"지금 진행 중인 V7 옵션 연결 Migration
적용 작업이 어느 DB를 대상으로 하는가"**라는, 이번 라운드와 정확히
같은 질문에 답한다. 7차 문서(`HOMEZ_V7_OPTION_LINK_V2_ADOPTED_20260923.md`
§6-1)도 "이 계획은 저장소 DB를 기본 대상으로 한다(6차 §7 확인 근거
그대로)"라며 같은 날 이 결정을 재확인했다.

### 2-4. 두 결정이 충돌하지 않는 이유

2-2는 "설치된 .exe가 스스로 여는 파일"에 대한 결정이고, 2-3은 "지금
Claude가 실제로 Migration을 적용해야 할 파일"에 대한 결정이다. 8차는
이 둘을 하나의 질문("어느 게 진짜 DB냐")으로 뭉뚱그려 이미 답이 있는
질문을 다시 열었다 — 이것이 정정 대상이다. 과거 설치본이 "운영 DB"로
불렸다는 사실(2-2)만으로 2-3의 더 최근·더 구체적인 결정을 무효화하지
않았고, 반대로 저장소 루트가 코드의 기본 경로라는 사실만으로 2-3을
근거 없이 정당화하지도 않았다(2-3 자체가 이미 명시적 결정문이므로).

### 2-5. 2-3 결정 이후 설치본에 신규 업무 데이터가 쌓였는지 재확인(읽기 전용, 값 미노출)

수정시각만으로 판단하지 않기 위해, 두 DB의 **주요 업무 테이블 콘텐츠의
최대 타임스탬프**(개인정보·자격증명 값은 전혀 조회하지 않고 `COUNT`·
`MAX(created_at 계열 컬럼)`만)를 이번에 직접 읽기 전용으로 대조했다:

| DB | 콘텐츠 최대 타임스탬프(전 테이블 중 최댓값) | 파일 mtime |
|---|---|---|
| 설치본(`%LOCALAPPDATA%\HOMEZ\data\homez.db`) | **2026-08-29**(모든 조사 대상 테이블이 이 날짜 이하) | 2026-08-29 21:02:41 |
| 저장소 루트(`homez.db`) | **2026-09-17**(`audit_logs`·`platform_alert_delivery_logs`·`order_auto_collection_states` 등) | 2026-09-17 19:25:02 |

설치본은 2-3 결정(2026-09-21)보다 **23일 전**인 2026-08-29 이후
콘텐츠 수준에서 완전히 정지해 있다 — 즉 2-3 결정 이후 설치본에 새로
쌓인 업무 데이터는 없다(파일 mtime이 아니라 각 테이블의 실제 타임스탬프
컬럼 최댓값으로 확인한 결과다). 반대로 저장소 루트는 2-3 결정 이후에도
2026-09-17까지 계속 활동이 있었다 — 이 사실은 저장소 루트가 실제로
V7 개발·검증 작업 내내 쓰여 온 DB라는 2-3 결정과 일치하며, 결정을
다시 열 만한 새로운 충돌 신호가 없다.

**결론(재질문 아님, 기존 결정 재적용)**: 이번 라운드를 포함해 앞으로의
V7 Migration 적용 작업의 "업무 DB"는 **저장소 루트 `homez.db`**다.
설치본은 여전히 "별도 대상, 별도 승인" — 이번 승인안(§6)에 포함하지
않는다.

  증명하지는 않는다(지시 원문 그대로 인정).

## 4. 남은 격리 검증 보완

### 4-1. 승인 생성 → 공급처 연결 변경 → 기존 승인으로 실행 시도

기존 `tests/test_purchase_order_submission_service.py::OrderSubmissionServiceTestCaseBase`

1. **대조군**(`test_stale_snapshot_still_reaches_adapter_when_options_unchanged`):
   승인 시점과 실행 시도 시점의 옵션이 같으면(연결이 안 바뀐 정상
   경우) 실제 발주 함수(Fake `submit_order`, 실제 코드에서는
   `OnchannelChannelAdapter.submit_order`)가 정확히 1회 호출되고
   성공 처리됨을 먼저 확인했다 — 이 대조군이 통과해야 아래 "0회
   호출"이 차단 때문인지 픽스처 결함 때문인지 구분할 수 있다.
2. **본 시나리오**(`test_link_change_blocks_execution_without_touching_snapshot`):
   `PurchaseOrderApprovalService.confirm_shipping_cost()`+
   `finalize_approval()`로 옵션 `[{"id":"OPT-BLACK","qty":1}]`(단가
   10000, 총액 10000)에 대한 ACTIVE 승인을 실제로 생성 → 공급처
   옵션 연결이 바뀌어 재조회하면 나올 값을 대입(`[{"id":"OPT-GRAY2",
   "qty":1}]`, **총액은 동일하게 10000으로 맞춰 "금액이 같아도
   옵션 구성이 다르면 차단되는가"를 가격 차이와 분리**) → 그 새
   옵션으로 `submit_order()` 실행을 시도 → `ConflictException`

   횟수는 정확히 0회**(스파이 `call_log == []`로 확인) → DB를

   `status` 필드만 바꾸고 스냅샷 자체를 덮어쓰는 코드 경로가 없음을
   실행으로 재확인).
3. **재승인 경로**(`test_reapproval_with_new_options_then_succeeds`):

   명시적 사람 행동으로만 복구됨을 확인했다.

반환하는가" 자체는 이번에 다시 검증하지 않았다 — 이는 8차 라운드에서
이미 실제 브라우저로 저장→하드 리로드→API 재조회까지 실증된 사실이다
(§5의 표현 정정 참고). 이번에 새로 검증한 것은 그 다음 단계, 즉
"연결이 바뀌어 새 옵션이 나온 뒤 그것으로 기존(연결 변경 전) 승인을

옵션 연결 기능과 기존 승인 스냅샷 기능이 실제로 맞물리는 지점이다.

## 5. "실제 DB 재조회" 표현 정정

8차 문서 §6-3 표의 AD-1 행: **"클라이언트 캐시가 아니라 실제 DB
재조회로 검증"**이라는 문구는 부정확했다 — 여기서 재조회한 DB는
실제 업무 DB(저장소 루트 또는 설치본) 어느 쪽도 아니고, 이번
채택본 화면 검증 전용으로 새로 만든 **격리 합성 DB**
(`adopted_e2e.db`, 저장소 밖 스크래치 경로)였다. "클라이언트 캐시가
아니다"라는 주장 자체는 정확하다(하드 리로드로 서버를 다시 거쳐
API를 재호출했으므로) — 다만 "실제 DB"라는 단어가 마치 업무용 실제
DB를 뜻하는 것처럼 오독될 수 있었다.

**정정**: "클라이언트 캐시가 아니라 **격리 DB(`adopted_e2e.db`) 저장
후 하드 리로드·API 재조회**로 검증" — 이 라운드(§4-1)에서 사용한
임시 파일 SQLite, 8차의 사본 리허설 WORKCOPY, 8차의 화면 검증용
`adopted_e2e.db` **전부 동일하게 격리·합성 DB**이며 실제 업무 DB가
아니다. 실제 업무 DB(저장소 루트)에 대한 조사는 항상 읽기 전용으로만
이뤄졌고(§1·§3), 이번 라운드까지 어떤 쓰기도 없었다.

## 1. 최종 목표

사용자 범위 재확인(2026-09-21): 판매채널 추가, 공급처 추가, 상품 URL 등록·검색은 V8 개발 범위에 포함한다. 개별 채널·공급처 선정은 미확정이다. 아래의 테무 등 개별 후보 조사와 기능 자체의 개발 목표를 구분한다.

URL 등록·검색 흐름: 사용자 URL 입력 → 지원 출처·접근 조건 확인 → 상품명·이미지·옵션·가격·배송정보 수집 → 누락·충돌·수집시각 표시 → 후보 저장·기존 후보 검색·비교 → 승인된 등록 준비로 연결. URL에 없는 값은 추측해 확정하지 않는다. 외부 검색을 통한 후보 탐색과 저장한 URL 후보 검색은 구분하며 실제 지원 범위는 데이터 접근권한에 맞춘다. API뿐 아니라 허용된 페이지 자료를 이용하되 로그인·CAPTCHA·이용제한을 우회하지 않는다. 서버 URL 요청은 내부망·로컬주소·리다이렉트 접근을 검증하고 외부 콘텐츠의 지시를 실행하지 않는다.

HOMEZ가 근거 있는 상품 후보를 추천하고, 등록 자료를 검사하며, 확인된 상품 연결을 반복 사용한다. 운영자는 정상 주문을 묶어 검토하고 예외에 집중한다. 판매 이후에는 실제 이익과 자금 회전으로 추천과 운영 방식을 개선한다.

목표 흐름:
자료 수집 → 대분류 추천 → 세부 상품 비교 → 공급처 검토 → 이미지·상품 사실 대조 → 등록 초안·승인 → 옵션 연결 → 주문 분류·승인 → 공급처 처리 → 배송·환불·정산 대조 → 추천 평가.

수익이나 완전 무인 운영을 보장하지 않는다. 성공 기준은 작업시간·오류·실이익·유지비의 측정 가능한 개선이다.

## 2. 확정 기준과 제안의 구분

버전 경계: **V7 개인 반자동 실사용 완성 → V8 채널·공급처·상품 분석/등록 효율 확대 → V9 자동화 완성 → V10 타인도 사용하는 서비스**. V8에서 필요한 수집·계산은 자동으로 할 수 있으나, 새 상품등록·발주·결제까지 무인 실행하는 것을 V8 완료 조건으로 삼지 않는다.

| 구분 | 내용 |
| --- | --- |
| 기존 사용자 기준 | V7 반자동 실사용을 먼저 완성하고 운영하면서 사업성을 분석 |
| 기존 사용자 기준 | 상품 추천은 1시간 간격 갱신, 대분류와 세부 상품·비교 상품의 2단계 |
| 기존 사용자 기준 | 네이버클라우드 허브 API 활용 방향. 실제 상품명·API 권한·데이터 제공 범위는 별도 확인 |
| 기존 사용자 기준 | V8 이미지 리딩: 편집 필요성 판단, 사실 대조, 필요한 수정안 제시 |

| 이번 계획의 제안 | 공급처 파일 연동, 묶음 승인, 예외 작업함, 자금 회전 예측과 단계별 출시 순서 |
| 미확정 | 테무 입점·API 계약, 식품 취급 범위, 추가 공급처, 요금제, 개발 일정·예산 |

검색결과 순위·쇼핑 클릭지수·실제 조회수·판매량은 다른 데이터다. API가 주지 않는 수치를 추측해 실제 수치처럼 표시하지 않는다. 매시간 갱신은 스케줄 목표이며 데이터 원천의 실제 갱신 주기를 보장하지 않는다.

## 3. V7과 개발 환경 경계

- V7 옵션 연결 채택, 현재 안전결함 해결, 승인된 실거래 검증은 V7 작업으로 유지한다. 이 계획을 새 출시 조건으로 추가하지 않는다.
- V8은 별도 브랜치와 작업 디렉터리, 가상환경, 포트, 설정, DB, 미디어·백업 경로로 개발한다.
- Git worktree만 나누어도 외부 DB·자격증명 경로가 같을 수 있으므로 자원별 실제 분리를 검증한다.
- 기본 개발 환경은 합성 데이터와 가짜 Provider를 사용하고 운영 자격증명·실거래 전송은 차단한다.
- 실제 데이터 사본이 필요하면 별도 승인·최소화·보호·삭제 계획을 세운다. 실제 DB나 개인정보를 Git에 올리지 않는다.
- 운영 V7을 V8 실험 환경으로 쓰지 않는다. 안전 수정의 양쪽 반영은 변경 단위와 테스트 근거를 남긴다.

## 4. 기능별 설계

### V8-01. 근거 기반 2단계 상품 추천

- 입력: 허용된 API·페이지 자료, 계절성, 관측 시각, 공급가·배송비, 자체 판매 결과.
- 1차: 대분류 후보와 추천 이유·데이터 부족을 표시한다.
- 2차: 브랜드·규격·수량·가격대가 명확한 상품과 비교 후보를 제시한다. 브랜드는 분류 단계 자체가 아니라 상품 속성으로 취급한다.
- 공급 가능성·배송·예상 이익·반품 위험을 함께 비교한다. 단일 인기 점수로 결론내리지 않는다.
- 동일 이미지 중복은 화면에서 묶되 원본 출처와 서로 다른 옵션 증거는 보존한다.
- 매시간 작업은 캐시·증분 갱신·호출 예산을 사용한다. 수집 실패 시 마지막 성공 시각과 오래된 자료임을 표시한다.
- 완료 기준: 데이터 출처 추적, 미제공 지표의 정직한 표시, 호출량 제한, 실패·중복·오래된 자료 처리 시험.

### V8-02. 국내외 공급처 추가와 적합성 평가

- 국내 API 우선 후보: 도매매/도매꾹. 파일 후보: 비셀러. 오너클랜은 계정용 API 조건을 확보해 비교한다. 스페셜오퍼의 상품등록 파일을 주문파일 지원으로 오인하지 않는다.
- 해외 기술 우선 후보: CJdropshipping. AliExpress·1688·Alibaba.com은 계정 자격·구매 API·총비용·한국 배송을 확인한 후 선정한다. 이 순서는 제안이며 입점/거래 승인이 아니다.
- 공급처 추가는 목록에 이름을 넣는 일이 아니다. 상품·옵션 식별 → 비용/배송 → 승인 → 주문 결과 대조 → 송장/클레임의 지원범위를 실제로 연결한다.
- 주문 생성이 결제를 포함하는 API는 금전 실행으로 분류한다. CJ sandbox는 명시 설정하고, 도매매의 예치금 차감 주문을 테스트 조회처럼 호출하지 않는다.

- API 유무가 아니라 실제 가능한 상품조회·발주·결제·송장·취소·환불 기능을 각각 기록한다.
- 공식 API, 승인된 CSV/XLSX, 사용자 보조 브라우저, 수동 처리를 구분한다.
- 사업자·거래조건·배송비·마감시간·판매채널 제한·이미지 이용권·반품 절차와 확인 근거를 보존한다.
- 식품은 원산지·중량·등급·보관·온도대·소비기한 관련 자료와 지역별 배송 가능성을 추가 확인한다. 법적 필수항목은 품목별 공식 근거를 따로 조사한다.
- 게시판 글이나 영상 추천만으로 검증된 공급처로 승인하지 않는다.
- 완료 기준: 지원하지 않는 기능은 실행 불가, 근거 만료·조건 변경 표시, 초기 확인과 이후 변경 감지를 분리.

### V8-03. API 없는 공급처 주문서 연동

- 파일 가져오기 → 열·규격 매핑 → 미리보기 → 검증 → 사용자 승인 → 파일 생성/승인된 전달 → 결과 대조.
- 식별키는 회사·판매채널·외부 주문·품목·공급처를 포함해 설계한다. 이름만으로 중복이나 옵션을 판정하지 않는다.
- 템플릿 버전, 수량 단위, 인코딩, 필수값, 개인정보 열, 스프레드시트 수식 주입을 검증한다.
- 파일 생성·업로드는 주문 성공이 아니다. 공급처 주문번호나 사람이 확인한 근거가 필요하다.
- 부분 성공 시 성공 건은 재전송하지 않는다. 결과불명 건은 확인 대기, 자동 대체 발주 금지.
- 완료 기준: 중복 파일, 부분 실패, 프로세스 재시작, 템플릿 변경, 결과 파일 중복 반영 시험.

### V8-04. 이미지 리딩과 등록 준비

- 기존 V8 이미지 리딩 설계를 확장하지 않고 공통 설계로 재사용한다.
- 공급처 원본·상품 사실·선택 옵션·이미지 문구를 비교한다.
- 수정 불필요 / 기술적 수정 / 설명 보완 / 사실 충돌 / 근거 부족으로 분류한다.
- 원본·변경 영역·근거·사용권을 표시하고 수정안 승인 후 등록 초안에 반영한다.
- 임의 중량·원산지·효능·할인율·실물 구성을 만들지 않는다. 음식 이미지의 연출과 실제 포함 구성도 구분한다.
- 완료 기준: 알려진 사실 충돌 검출, 원본 보존, 승인 전 게시 금지, 변경 후 옵션 일치 검증.

### V8-05. 묶음 검토와 예외 작업함

- 정상 주문은 공급처별로 모으고 가격 상승·품절·배송비 미확인·옵션 충돌·결과불명은 분리한다.
- 승인은 전체 총액뿐 아니라 각 주문의 상품·수량·비용·정책 버전을 고정한다.
- 실행 직전 변경 여부와 한도를 다시 검사한다. 묶음 한 번 승인으로 변경된 다른 주문까지 허용하지 않는다.
- 공급처별 부분 성공을 허용하되 행별 실행 결과를 보존한다. 묶음 전체 재시도로 중복을 만들지 않는다.
- 예외에는 원인, 현재 증거, 다음 행동, 담당자, 처리 이력을 제공한다.
- 완료 기준: 동시 클릭·다중 프로세스·일부 실패·재시작·승인 만료·설정 변경 시험에서 중복·한도 우회 방지.

### V8-06. 실제 이익과 자금 회전

- 예상/확정 매출, 매입비, 배송비, 수수료, 할인 부담, 반품 비용을 같은 주문·품목 근거로 연결한다.
- 세전 주문 기여이익과 고정비·세금까지 고려한 사업 순이익을 구분한다.
- 고객 결제, 판매채널 정산, 운영자금, 예약, 공급처 지급, 환불은 기존 도메인 경계를 유지한다.
- 공급처 지급일, 배송 예상일, 정산 자격일·실입금일, 카드 만기와 지급 보류를 구분한다.
- 정산 지연·반품 증가 시 필요한 자금을 시나리오로 보여준다. 추정 입금은 실제 사용 가능 잔액에 넣지 않는다.
- 완료 기준: 부분환불·추가배송비·정산 지연·다중 품목·혼합 결제에서 중복 비용 반영 없음과 근거 추적.

### V8-07. 판매채널 추가

- 1차 제안: 네이버 스마트스토어. 2차 후보: G마켓·옥션(ESM). 11번가·롯데ON·테무는 현재 권한과 공식 계약 확인 후 비교한다. Cafe24는 자사몰 필요가 있을 때 선택한다.
- API HUB 키와 커머스 API 키는 별개다. 등록·수정·옵션ID·주문·배송·취소/환불·정산을 각각 지원표로 관리한다.
- 채널별 계정·외부번호·상태·옵션·세금/배송 규격을 공통 모델에 억지로 맞추지 않는다. 공통 계약과 채널 특수 필드를 구분한다.

- 테무는 판매채널 후보이며 공급처로 혼동하지 않는다.
- 한국 계정 입점·식품 허용 범위·등록 규격·수수료·정산·광고 지원·API 접근을 공식 계약으로 확인한다.
- 상품등록, 옵션번호 연결, 주문, 송장, 취소/환불, 정산 기능별 지원표를 먼저 만든다.
- 영상의 무료 광고·배송 완료 후 7일 정산을 영구 계약으로 하드코딩하지 않는다.
- API가 없거나 접근 권한이 없으면 허용된 파일/수동 보조를 평가한다. 인증·CAPTCHA 우회 금지.
- 완료 기준: 계약 확인 → 격리 검증 → 별도 승인된 최소 실조회 → 상품·실거래 단계 검증. 불가한 기능은 명시적으로 미지원.

### V8-08. URL 등록·탐색·저장 후보 검색

- 외부 키워드 탐색, 공급처 카탈로그 검색, 저장 후보 검색을 별도 기능으로 구현한다.
- API·구조화자료·허용 HTML·사용자 보조 브라우저를 출처별로 지원한다. 모든 URL 지원을 약속하지 않는다.
- 상품명·제조사·모델·원산지·규격·옵션·수량단위·통화·가격·배송비·재고·반품·이미지 사용권을 필드별 근거와 함께 저장한다.
- URL의 옵션 식별자를 보존하고 같은 이미지/이름만으로 다른 상품을 합치지 않는다. 수집 실패·로그인 필요·근거 부족 상태를 제공한다.
- SSRF, 악성 리다이렉트, 프롬프트 주입, HTML/파일 주입, 고객정보 유출을 방어한다. 접근권한과 재사용권은 별도 확인한다.
- 완료 기준: 지원 출처별 상품 하나를 URL → 후보 → 비교 → 승인된 등록 초안까지 연결하고, 옵션 누락·가격 변경·접근차단·악성 입력을 검증한다.

## 7. 모드별 목표

- 수동: 사람이 입력·실행하고 HOMEZ가 기록·대조를 돕는다.

## 8. 가상 운영 시나리오

계절 신호로 사과를 추천하고 3kg·5kg, 등급·원산지·배송 조건이 맞는 후보를 비교한다. 공급처 원본 이미지와 상품 규격을 대조해 승인된 초안을 만든다.
등록 후 옵션을 최초 연결한다. 주문 20건이 들어오면 정상 17건을 검토 대상으로 묶고 예외 3건은 따로 표시한다. 승인된 주문만 공급처로 전달하고 결과불명 1건은 재전송하지 않는다.
배송·환불·정산 결과로 실제 이익과 사용자 개입 시간을 비교해 다음 추천을 평가한다. 숫자는 설명용이며 실제 거래·합격 기준이 아니다.

## 12. 실제 개발 패키지와 우선순위

### P0: 공통 기반과 범위 확정

- 대상: V7에서 검증된 상품·옵션·주문·승인·비용 모델의 재사용 대조표, 독립 V8 실행환경, Provider 지원표.

- 종료 조건: 개발 부팅·테스트·예약 작업에서 V7 자원 접근이 차단되고, 실제 쓰기 없는 한 가지 전체 흐름이 실행됨.

### P1: 상품 검토 작업대

- 화면: 후보 목록 → 상품별 근거·비교·이미지 문제 → 등록 초안.
- 구현 단위: V8-08 URL/카탈로그/저장 후보 검색 → API HUB 조회/캐시 → 2단계 추천 → 사실-관측값 분리 → 옵션·이미지 충돌 검출 → 수정 승인 이력. 먼저 수집·후보 계약을 만들고 추천을 붙인다.
- 네이버 쇼핑 상품 검색의 구형 API를 새 상품 발굴 기반으로 쓰지 않는다. 공식 종료 공지를 반영해 상품 후보는 지원 공급처/URL에서, 관심 신호는 HUB에서 가져온다.
- 추천 근거: 관심 신호, 공급 가능성, 비용 완전성, 배송 조건을 각각 표시. 미확인 값은 0점/0원으로 대체하지 않음.
- 종료 조건: 동일 상품의 규격 불일치·중복 이미지·자료 만료·소스 충돌을 재현하고, 승인되지 않은 생성물이 등록되지 않음.

### P2: 신규 판매채널·공급처 연결과 주문 예외 작업대

- 화면: 처리 가능 / 확인 필요 / 결과불명으로 분리한 주문 목록과 공급처별 검토 합계.
- 구현 단위: 네이버 판매채널과 국내 공급처를 우선 후보로 계약 확정 → V7 옵션 연결 재사용 → 등록 결과·주문·공급처 연결 → 행별 승인 → 결과 대조. 파일 연동은 실제 템플릿이 확보된 공급처에만 적용한다.
- 종료 조건: 묶음 일부 성공 후 재실행해도 이미 처리한 주문은 전송하지 않으며, 사용자에게 남은 행동이 명확함.
- 범위: 신규 채널/공급처 연결은 V8 핵심이다. 묶음 승인·파일 자동 전달의 세부 깊이는 V7 병목을 근거로 조정한다.

### P3: 실제 수익과 추천 평가

- 화면: 상품별 예상/확정 비용, 예외 처리시간, 입금 예상/확정, 추천 당시 근거와 실제 결과.
- 구현 단위: 기존 비용·정산 연결 검증, 미확정 비용 표시, 설명 가능한 평가 업데이트, 정산 지연 시뮬레이션.
- 종료 조건: 비용 누락이 있는 상품을 확정 고수익으로 표시하지 않으며, 추천 변경의 근거와 버전을 재현할 수 있음.
- 초기 방식: 집계·규칙·비교 평가부터 시작. 자체 학습 모델이나 복잡한 학습 파이프라인은 데이터와 효과 근거가 생긴 후 판단.

### P4: 검증된 채널 확대

- P2의 첫 연결 이후 해외 공급처·추가 판매채널을 공식 조건·실제 업무 수요·개발 및 유지비로 비교해 하나씩 선택한다.
- 최소 범위: 상품/옵션 식별 → 주문 수집 → 공급처 연결 → 배송·정산 대조. 미지원 취소/환불은 수동 경로를 명시.
- 채널 수보다 끝까지 운영 가능한 연결을 우선한다. 외부 조건이 막히면 P1~P3 중간 출시가 가능하지만, 신규 연결·해외 지원이 미완료인 상태를 V8 전체 범위 완료라고 부르지 않는다. 채택할 정확한 플랫폼 수는 착수 범위에서 고정한다.

## 13. 모듈별 배포·운영 원칙

- 각 패키지는 수동/반자동으로 먼저 사용하고 기능별 자동화 권한은 별도로 개방한다.
- 그림자 실행은 추천·계획 생성까지만 비교하고 외부 쓰기는 하지 않는다. 실제 데이터 사용도 기존 승인 범위를 따른다.
- 브라우저와 파일은 API 부재를 보완하는 수단이다. 비밀키·고객정보를 AI 프롬프트나 로그에 무분별하게 넣지 않는다.
- 모델 선택은 고정 브랜드보다 사실 오류율·지연·호출비용을 비교한다. 계산·권한·한도 판정은 모델 출력에 맡기지 않는다.
- 신규 스키마는 구버전 호환과 복구 절차를 검증한 뒤 별도 승인으로 적용한다. 운영 V7 자동 업데이트 금지.
- 문서·회귀·실조회·실거래의 완료 여부를 분리하고, 미검증 기능은 기본 비활성으로 남긴다.

## 14. 당장 만들지 않을 것과 후속 조사

만들지 않을 것: 전용 범용 챗봇, 자체 결제망, 무제한 크롤러, 모든 판매채널 동시 연동, AI가 가격·발주를 무제한 결정하는 구조, 국내 조건 미확인 UCP 결제 연동.

공개 공식 자료 조사 결과와 계정/계약/운영 확인이 남은 항목은 [조사대장 R01~R32](research/20260921_V8_CHANNEL_SUPPLIER_URL_FEASIBILITY.md)에 통합한다. 같은 질문을 반복해 계획을 늘리지 않는다.
착수 시 기능 V8-01~08마다 요구사항 → 데이터 출처 → 화면/API/저장/Provider → 집중시험 → 격리화면 → 승인된 실검증을 연결한 추적표를 만든다.
출시 전 미확인 비용·권리·반품·해외배송이 남은 상품은 자동 '판매 가능'으로 바꾸지 않는다. 기능 추가보다 이 추적표의 끊긴 연결을 먼저 해결한다.
기존 42개 응용 아이디어는 조사대장 §7에 필수 통합/선택/V9/V10으로 분류했다. 연구 아이디어 전부를 V8 필수 구현으로 승격하지 않는다.

## 15. 두 영상 시각 재분석 반영 (2026-09-22)

[시점별 증거와 CTO 평가](research/20260922_TWO_VIDEOS_VISUAL_CTO_REANALYSIS.md)를 기존 V8-01~08의 세부 요구사항으로 반영한다. 새 V7 범위나 별도 기능 도메인을 만들지 않는다.

- 공급처 수집 필드, 내부 갱신 필드, 판매채널 전송 필드를 구분한다. 부분 수정/전체 전송 계약을 채널별로 확인하고 승인된 수동 편집값을 보호한다.
- URL 목록은 건수 상한·수집 범위·옵션 누락·부분 실패를 미리 보여준다. 등록 성공은 로그인이나 요청 수락이 아니라 외부 상품/옵션 식별자와 결과 대조로 판정한다.
- 이미지 편집은 필요성·이용권리·상품 동일성을 먼저 확인하고 목적별 프리셋과 전후 비교를 제공한다. 생성된 원산지·효능·구성 문구는 원자료와 대조한다.
- 파일 열 매핑과 상품/옵션 연결은 최초 확인값을 재사용하되 버전·수량·변경 근거를 보존한다. 판매 수량과 공급 구성수량을 혼동하지 않는다.
- 브랜드 순위는 판매량으로 표현하지 않는다. 가격 가산율과 매출 대비 마진율을 분리하고 수수료·반품·유지 작업시간까지 실제 효과 측정에 포함한다.
- 실행 순서는 단일 상품 수집 → 검토·편집 → 등록·결과 대조 → 묶음 확장이다. V9 자동화 및 V10 다중 사용자 순서는 유지한다.

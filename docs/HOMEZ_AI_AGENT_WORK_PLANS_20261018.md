### 0-1. 이미 만들어 둔 재료 (재사용 — 새로 만들지 않는다)

### 0-2. 공통 원칙

1. **AI는 제안만 한다.** 결정은 규칙이, 실행은 사람(또는 사용자가 한도를 정해 허용한 자동 작업)이 한다. 8단계 승인·가격 확정·쿠팡 전송은 자동화하지 않는다(V9 이전).
2. **돈·수량·상태는 AI가 계산하지 않는다.** 모르는 값은 0이나 가정으로 채우지 않고 보류한다.
3. **AI가 읽은 값은 근거(원문 인용·출처)가 있어야 쓰고, 금액·상태에 영향을 주는 값은 사용자 확인 뒤에만 쓴다.** 외부 글(공급처 페이지·공지·문의·로그)은 전부 "자료"이며 그 안의 지시는 따르지 않는다.
4. **보내는 정보를 최소화한다.** 가격·원가·마진·연락처·주문/수령인·자격증명·비밀정보는 AI에 보내지 않는다(로그는 마스킹 후에만).
5. **쓰기 호출(쿠팡 수정·재고·가격·문의 답변 등)은 승인 센터의 횟수형 WRITE 허용 + 별도 분석·Whitelist·승인** 없이는 만들지 않는다. 문서에 없는 API는 만들지 않는다(공식 문서 읽기 확인이 첫 단계).
6. **단계마다 같은 검증 틀**: 순수 규칙 시험 → 가짜 전송 시험 → 변이 검사 → 격리 서버 화면 시험 → 영향 모듈 회귀 → 상태 문서 갱신 → 승인 후 커밋.
7. 첫 실제 AI 호출은 단계마다 별도 승인(호출 횟수·예상 비용·가드 호스트·키 입력은 사용자가 화면에서).

### 0-3. 공통 결정 필요 사항

- 새 AI 서비스(이미지 생성 등 Claude 외) 도입 시 공급자·요금·약관 확인과 승인(코드는 공급자 교체 가능한 경계로 만들되, 도입은 사용자 결정).
- 월 한도는 AI 전체 합산(현재 방식)으로 둘지, AI별로 나눌지.

## 1. 상품 이미지 생성 AI — **컨셉별 진행**이 핵심 (2026-10-18 사용자 지시로 개정)

### 1-1. 목적과 범위

상품 사진(누끼)을 받아 **컨셉을 골라 컨셉별로** 대표·추가·상세 이미지를 만든다. 핵심 요구는 "컨셉별로 따로 진행·비교·선택할 수 있게 만드는 것"이다. 제품 자체는 다시 그리지 않는다(기존 결정).

- 포함: 컨셉 명세 체계, 컨셉별 독립 작업·후보·검사·선택, 상품 카테고리별 컨셉 추천, 상세 섹션마다 다른 컨셉, (정책·권리 확인 뒤) 컨셉별 장면 생성
- 제외: 제품 형태·색·로고를 AI가 새로 만드는 일, 실제 사진이 아닌 것을 실제 사진처럼 표시하는 일, 이미지 자동 업로드·등록

### 1-2. 현재 상태 (코드 확인)

- 지금의 "컨셉"(`image_concepts.py`)은 **색 묶음 6종**(흰 배경·베이지·민트·핑크·그레이·미드나이트: 배경 + 글자색 + 포인트색)이다. 대표(MAIN)는 흰 배경 컨셉만, 추가·상세는 전부 허용. 컨셉 목록 API(`GET /concepts`)와 섹션별 컨셉 지정(`section_concepts`)이 있다.
- 형식 분석, 섹션 분할, 적응형 배경 제안, 상세페이지 생성, 누끼(rembg 로컬), 이미지 검증, 작업 큐(`job_queue_service`), 권리 증빙이 있다.
- **생성 Provider는 Fake뿐**(Disabled 기본). 컨셉 선택 **화면(UI)은 아직 없다**.
- 부족한 점: 컨셉이 "색"만 담아 장면·소재·구도·조명·어울리는 상품 같은 **컨셉의 성격**을 표현하지 못하고, 컨셉별로 진행 상태·비용·검사 결과를 따로 관리하지 않는다.

### 1-3. 설계: 컨셉 = 명세 + 규칙 + 파이프라인

컨셉을 색 묶음에서 **명세(Spec)** 로 확장한다(기존 6종은 하위 호환으로 이관).

| 명세 항목 | 내용 |
|---|---|
| 기본 | 코드, 이름, 설명, 미리보기, 용도(MAIN/ADDITIONAL/DETAIL), 버전 |
| 장면 | 배경 종류(흰/단색/그라데이션/소재 질감/생활 장면/스튜디오 조명/계절·행사), 분위기, 소품 허용 여부 |
| 제품 배치 | 제품 비율·여백·중심 규칙, 그림자·반사 방식 |
| 처리 수준 | **L0** 로컬 합성(색·그라데이션) / **L1** 로컬 보정(그림자·반사·질감 — 생성 아님) / **L2** 생성 배경(정책·권리 확인과 별도 승인 뒤에만) |
| 어울림 | 어울리는·피해야 할 상품 카테고리(규칙), 대표 이미지 허용 여부 |
| 검사 | 제품 보존율, 배경 대비(ΔE), 대표 이미지 규격, 금지 요소(문구·로고·워터마크), 쿠팡 정책 적합 플래그 |
| 상세 테마 | 섹션 색·글자색·포인트색(기존 ConceptTheme), 문구 톤 |
| 표시 | "생성 배경" 표기 필요 여부 |

**컨셉별 진행 흐름** (한 컨셉의 실패·폐기가 다른 컨셉에 영향을 주지 않는다):

1. 제품 입력(누끼 소스) → 2. **컨셉 선택(복수)** — 상품 카테고리에 따른 추천은 규칙이 정하고 AI는 추천 이유만 설명 → 3. **컨셉별 작업**(작업 큐, 컨셉마다 독립 상태: 대기·진행·후보 있음·검사 실패·선택됨·폐기) → 4. **컨셉별 후보 N장 + 자동 검사 결과** → 5. 사용자가 후보를 **컨셉별로 비교·선택·재생성**(컨셉별 재시도 횟수 한도) → 6. 상세 섹션마다 다른 컨셉 지정 → 7. 저장(사용권 선언은 기존 사용자 책임 선언 흐름).

비용·기록: 생성형(L2)은 컨셉 작업마다 사용 기록(컨셉 코드·후보 수·비용)을 남기고 월 한도·승인 센터 허용(횟수형)을 `call_llm`과 같은 틀로 쓴다. L0·L1은 외부 접촉·비용이 없다.

### 1-4. 단계 (바로 시작 가능한 것부터)

| 단계 | 내용 | 산출물 / 검증 | 외부 접촉 |
|---|---|---|---|
| I1 | **컨셉 명세 모델·레지스트리**: 기존 6종을 명세로 이관(동작·API 하위 호환), 처리 수준·어울림·검사 항목 필드, 명세 검증(대표는 흰 배경만 등) | 순수 함수 시험, 기존 시험 유지 | 0 |
| I2 | **컨셉별 작업·검사·화면**: 컨셉별 독립 상태, 컨셉별 후보·검사 결과, 위저드 3단계에 컨셉 선택·비교 화면 | 격리 서버 화면 시험 | 0 |
| I3 | **로컬 장면 컨셉(L1) 추가**: 그림자·반사·질감 기반 컨셉 6~10종(생성 아님), 카테고리 추천 규칙 | 골든 이미지 시험(제품 보존율) | 0 |
| I0 | **정책·권리 조사**(생성 도입 전 필수): 쿠팡 이미지 가이드(대표 이미지·합성·AI 생성물 표기), 공급처 이미지 이용 조건, 공급자별 약관 | 조사 문서 | 공식 문서 읽기(승인) |
| I4 | **생성 Provider(L2) 컨셉별 연결**: 공급자 선정(로컬 vs 외부 비교표 → 사용자 결정), 누끼 원본 + 생성 배경 합성만 허용, 제품 보존율 미달은 자동 폐기 | 가짜 전송 시험, 변이 검사 | 실제 호출은 별도 승인 |
| I5 | 상세 섹션 문구는 결정적 텍스트 합성(오탈자·효능 표현 방지, 기존 검사 재사용) | 시험 | 0 |
| I6 | 역량 등록부 IMAGE_PROCESSING 정직하게 갱신, 상태 문서 | — | 0 |

→ **I1~I3은 외부 접촉 없이 컨셉 체계와 화면을 먼저 완성**하고, 생성형(I0·I4)은 정책·권리·공급자 결정 뒤에 컨셉에 꽂는다.

### 1-5. 위험·미확인

- 생성 이미지가 실제 제품과 달라 **반품·민원**이 날 수 있음 → 제품 보존율 기준과 "실제 제품 사진 필수" 규칙.
- 공급처 이미지 권리·쿠팡 AI 생성물 정책은 **아직 모른다**(I0 전에는 L2 도입 결정을 하지 않는다).
- 로컬 생성 모델은 이 PC(RAM 4GB 기록)에서 실행이 어려울 수 있다 → I4에서 실측 전에는 가정하지 않는다.
- 컨셉이 늘면 검수 부담이 커진다 → 컨셉별 자동 검사와 "추천 컨셉만 먼저" 기본값.

### 1-6. 결정이 필요한 사항

1. 컨셉 처리 수준을 L0·L1(비생성)로 먼저 완성하고 L2(생성)는 조사 뒤로 미뤄도 되는지(권고)
2. 초기 컨셉 목록(기존 6종 + 추가 후보: 예 — 생활 장면, 소재 질감, 계절·행사 등)에서 우선 만들 것
3. 대표 이미지에는 계속 흰 배경 컨셉만 쓸지

## 2. 마케팅 AI

### 2-1. 목적과 범위

등록한 상품이 **잘 노출·판매되도록** 키워드, 상품명, 가격 전략, 경쟁 상황을 분석해 제안한다. (이전 결정: 경쟁 가격 분석은 이 AI에서 다룬다.)

- 포함: 검색어·상품명 개선 제안, 경쟁 가격 비교(사용자가 준 경쟁 URL), 가격 구간·마진 시나리오 제안, 성과(주문·반품) 기반 학습 기록
- 제외: 가격 자동 변경, 광고 집행·광고비 지출(광고비는 현 정책상 초기 이익 계산에서 제외), 쿠폰·프로모션 자동 발행, 소비자 대상 메시지 발송

### 2-2. 현재 상태 (코드 확인)

- `keyword/`는 파일만 있고 **내용이 비어 있다**(0줄). `ai_memory/`, `crawler/`도 비어 있다.
- 트렌드: 네이버 데이터랩 어댑터(코드·API HUB 대응 완료, 격리 시험 통과) + 결정론적 점수 규칙(`trend_discovery`), 신제품 규칙(`new_product_discovery`). 실제 호출 검증 여부는 상태 문서 확인 필요.
- 가격: `pricing/`(3,755줄, 가격 자문 서비스 포함)와 마진 계산기(결정적). 가격 변경은 **요청→승인** 별도 경로.
- 학습: `ai_learning/`은 실제 결과 기록·표본 크기 판정·후보 모델 상태기계까지만 있고 **실제 적용 코드는 없다**(의도된 경계).
- 이번에 만든 것 중 재사용: Phase B(글 초안), Phase E(URL을 읽어 값+근거+계산 — 경쟁 URL에도 같은 파이프라인 적용 가능).

### 2-3. 설계 방향

- **데이터 원천을 먼저 확정**한다(합법·약관 안에서): 네이버 데이터랩(공식 API), 사용자가 입력한 경쟁 URL, HOMEZ 내부 성과(주문·반품). 쿠팡 검색 결과 대량 수집(크롤링)은 하지 않는다.
- 통계(최저·중앙값·분포)와 마진 계산은 코드가, AI는 **해석·설명·문구 제안**만 한다. 가격 제안은 항상 "필요 판매가(마진 기준) vs 시장 구간" 두 값을 같이 보여 준다.
- 성과 학습은 `ai_learning` 상태기계를 쓴다 — 표본 부족이면 "판단 불가"를 표시하고, 모델·규칙 자동 적용은 하지 않는다.

### 2-4. 단계

| 단계 | 내용 | 산출물 / 검증 | 외부 접촉 |
|---|---|---|---|
| M0 | 데이터 원천 조사: 데이터랩 실사용 상태, 쿠팡 광고·검색 관련 공식 API 존재 여부와 약관, 공급처 데이터 | 조사 문서 | 공식 문서 읽기(승인) |
| M1 | **검색어·상품명 제안**: Phase B를 확장 — 입력 키워드·트렌드 신호로 후보를 만들고 쿠팡 상품명 규칙(옵션 반복·효능 표현)으로 검증 | 시험·화면 | AI 호출(승인 후) |
| M2 | **경쟁 가격 비교**: 사용자가 넣은 경쟁 URL 2~5개를 Phase E 파이프라인으로 읽고(근거 인용·확인 게이트) 최저·중앙값 계산 | 결정적 통계 시험, 격리 화면 시험 | 페이지 읽기 + AI 호출 |
| M3 | **가격 전략 제안**: "마진 하한가 / 시장 구간 / 권장 구간"과 민감도 표(수수료·반품률), 변경은 기존 가격 변경 요청 경로로만 | 시험 | 0 |
| M4 | **성과 기록·학습 보고**: 노출·주문·반품 결과를 기록해 제안의 적중을 사후 평가(표본 크기 판정 포함) | 시험 | 0 |
| M5 | 역량 등록부(신규 MARKETING 항목) 정직하게 등록, 상태 문서 | — | 0 |

### 2-5. 위험·미확인

- 경쟁 가격은 **표시가일 뿐 실제 판매 실적이 아니다**(할인·쿠폰·배송비·옵션 차이). 결과에 출처·시각·한계를 고정 표시한다.
- 가격 인하 경쟁을 부추겨 마진이 깎일 수 있다 → 마진 하한(max(회사 설정, 18%))은 어떤 제안도 넘지 못하게 코드로 막는다.
- 쿠팡 판매 성과·광고 데이터를 API로 받을 수 있는지는 **미확인**(M0).

### 2-6. 결정이 필요한 사항

1. 경쟁 가격 비교 입력 방식: 사용자가 URL을 넣는 방식으로 시작해도 되는지
2. 광고(CPC) 관련은 이번 계획에서 계속 제외할지(현 정책 유지)
3. 학습 결과를 제안 규칙에 반영하는 단계(자동 적용)는 V9 이후로 미룰지

## 3. 상품 서칭 AI

### 3-1. 목적과 범위

**팔 만한 상품 후보를 찾아 큐에 올린다.** 트렌드·공급처 데이터를 모아 마진·위험을 사전 계산하고, 사용자가 후보를 보고 승인한다. (V8 범위: 판매채널·공급처 추가, 상품 URL 등록·검색 포함)

- 포함: 트렌드 신호 + 공급처 카탈로그 매칭, 마진·위험 사전 필터, 중복 상품 묶기, 후보 점수화·설명, 정기 서칭 작업(허용 센터 한도 안에서)
- 제외: 후보 자동 승인·자동 등록·자동 발주, 로그인이 필요한 사이트 접근, 대량 크롤링

### 3-2. 현재 상태 (코드 확인)

- 후보·선별: `product_candidate/`, `product_selection/`(519줄), `new_product_discovery/`, `trend_discovery/`(규칙 점수).
- 공급처: `supplier/`(1,461줄), `supplier_capability/`(655줄). 역량 등록부상 **공급처 추천은 Fake/CSV/Manual 3종뿐, 실제 B2B 공급처 API는 없다**. 단 온채널은 공식 OpenAPI(상품·주문 조회, 판매신청, 발주 — 반품·환불 요청 API는 문서상 없음)로 별도 연동돼 있다.
- URL 읽기·분석: 완성(이번 Phase E). 위저드 초안 생성까지 이어짐.
- 조사 문서(미커밋): `docs/research/`에 BigBuy, CJ, Domeme, Ownerclan, Specialoffer, Syncee, Zendrop, HyperSKU, 1688, AliExpress 등의 API·결제·취소 경계 기록이 있다 — S0에서 정리해 재사용한다.
- `crawler/`는 비어 있다(0줄).

### 3-3. 설계 방향

- 후보 생성의 뼈대는 **API·사용자 제공 URL·CSV**다. 크롤링은 하지 않는다(약관·차단 위험).
- 규칙이 점수·필터(마진 ≥ 기준, 금지 품목, 상표 단어, KC·규제 분류 신호)를 내고, AI는 **상품명·사양 정규화, 중복(같은 상품 다른 이름) 묶기, "왜 이 후보인가/무엇이 위험인가" 설명**을 맡는다. 후보 점수에 AI 숫자를 섞지 않는다(기존 PRODUCT_ANALYSIS 금지 조항과 동일).
- 서칭 결과는 항상 "후보 큐"까지만 — 승인은 기존 후보 승인 화면에서 사람이.

### 3-4. 단계

| 단계 | 내용 | 산출물 / 검증 | 외부 접촉 |
|---|---|---|---|
| S0 | 공급처·채널 조건 정리: 기존 조사 문서 통합, 공식 문서 재확인(API 유무·재판매 허용·결제·취소/반품 조건), 우선 연동 후보 1~2곳 비교표 | 비교 문서 | 공식 문서 읽기(승인) |
| S1 | **후보 정규화·중복 묶기**: 상품명·옵션·사양을 구조화(근거 인용 검증), 같은 상품 군집 | 규칙·가짜 전송 시험 | AI 호출(승인) |
| S2 | **후보 사전 평가 v2**: Phase E 계산(수수료율 출처 필요) + 위험 규칙으로 "후보 가능/보류/제외"와 이유, 후보 큐 화면 | 시험·격리 화면 | 0 |
| S3 | **공급처 어댑터 1곳 추가**(S0 결정 후, 읽기 전용부터): 상품·가격·재고 조회, 호출 예산은 승인 센터 허용 | 가짜 전송 시험 | 읽기 호출(승인) |
| S4 | **정기 서칭 작업**: 스케줄러 job이 허용 한도 안에서 후보를 갱신하고 변화만 알림(승인 센터 허용 만료·가드 문제를 사전 안내) | 시험 | 허용 범위 안 |
| S5 | 역량 등록부(PRODUCT_DISCOVERY·SUPPLIER_RECOMMENDATION) 사실대로 갱신 | — | 0 |

### 3-5. 위험·미확인

- 공급처가 재판매·API 사용을 허용하는지, 취소·반품 조건(온채널은 반품 API가 문서상 없음)은 공급처마다 다르다 → S0 전에는 연동을 시작하지 않는다.
- 후보 이미지·설명의 저작권·상표 문제 → 위험 규칙과 사용자 확인 유지(이미지 AI와 같은 권리 조사 필요).
- "잘 팔릴 것 같다"는 AI 의견은 **근거 없는 숫자**가 되기 쉽다 → 점수·순위는 규칙·데이터로만.

### 3-6. 결정이 필요한 사항

1. 우선 추가할 공급처·채널(S0 비교표를 보고 결정할지)
2. 정기 서칭 작업의 주기·호출 한도
3. 후보 큐에 올리는 최소 조건(예: 마진 하한, 최소 주문 수량)

## 4. 상품 관리 AI

### 4-1. 목적과 범위

**이미 등록·판매 중인 상품의 운영**을 돕는다: 심사 반려, 재고·가격 이상, 리콜·정책 이슈, 고객 문의, 일일 점검. (이번 대화의 연동 C단계가 출발점)

- 포함: 반려 사유 해석→수정 제안, 재고·가격 이상 감지와 설명, 리콜·금지 품목 차단, 고객 문의 답변 초안, 일일·주간 운영 브리핑
- 제외: 판매중지·재고·가격·상품 수정을 AI가 직접 실행하는 일(승인 센터 쓰기 허용 + 사용자 확인 없이는 불가), 고객에게 메시지 자동 발송

### 4-2. 현재 상태 (코드 확인)

- 상품 상태·반려 사유 자동 확인과 쉬운 보기 표시(C단계, 쿠팡 GET 읽기 전용), 상품 등록 도우미(규칙 기반 + Phase B 글 초안).
- `inventory/`(3,284줄), `pricing/`(3,755줄), `price_stock_safety/`(1,335줄), `price_monitoring/`(242줄), `recall_notice/`(1,102줄), `listing` 상태 동기화, `notification_center/`(2,917줄), `orchestration/`(우선순위·대시보드).
- 역량 등록부상 PRICING_INVENTORY·OPERATIONS_COORDINATION은 **AI 없이 순수 계산·규칙**이며 실행은 별도 CRUD로 분리돼 있다.
- 쿠팡 **쓰기**(재고·가격·상품 수정·문의 답변·반품 수령확인)는 아직 없다 — 계획상 B단계로 남아 있고 별도 분석·Whitelist·승인 대상이다.
- 알려진 한계: 상태 이력은 첫 쪽만 읽음, 정산 응답은 대개 비어 있음, 쿠팡 반품 1건·콜센터 문의 1건이 WING에서 사용자 처리 대기.

### 4-3. 설계 방향

- 이상 **감지는 규칙**(재고 임계, 마진 이탈, 상태 변화, 리콜 일치), **설명·수정안·답변 초안은 AI**. 감지 결과는 기존 "오늘 할 일"에 올린다(새 화면을 늘리지 않는다).
- 반려 사유 → 수정 제안은 "사유 문구 → 규칙 매핑(예: 옵션 중복·이미지 다운로드 실패·효능 표현) + AI 요약"으로, 수정 *실행*은 상품 수정 쓰기 API가 승인될 때까지 **WING에서 직접 하도록 안내**한다.
- 문의 답변은 초안만 만든다(개인정보·주문정보는 마스킹해 AI에 보냄).

### 4-4. 단계

| 단계 | 내용 | 산출물 / 검증 | 외부 접촉 |
|---|---|---|---|
| P0 | 갭 조사: 실제 운영에서 자주 막히는 일(반려 유형, 품절, 가격 이탈, 문의) 빈도 집계, 쿠팡 쓰기 API 문서 확인 | 조사 문서 | 공식 문서 읽기(승인) |
| P1 | **반려 사유 → 수정 제안**: 사유 분류 규칙 + AI 설명, 쉬운 보기 "반려 사유 보기"에 제안 추가 | 시험·격리 화면 | AI 호출(승인) |
| P2 | **재고·가격 이상 감지 + 설명**: 공급처 재고·가격 변동(읽기), 마진 이탈, 임계치 설정, 알림 | 규칙 시험 | 읽기(허용 센터) |
| P3 | **문의 답변 초안**: 상품 문의·콜센터 문의 읽기(이미 있음) 위에 초안, 사람이 복사·수정해 WING에서 답변 | 마스킹 시험 | AI 호출(승인) |
| P4 | **일일 운영 브리핑**: 오늘 할 일·이상·예정(허용 만료 등)을 한 장으로 | 시험 | 0 |
| P5 | **(별도 승인 후) 쓰기 기능**: 재고·가격·상품 수정·문의 답변 — 횟수형 WRITE 허용, 사용자 확인, 결과 재조회 검증 | 별도 계획서 | 쓰기 호출(승인) |

### 4-5. 위험·미확인

- 자동 수정·재제출은 반려를 반복하거나 판매를 멈출 수 있다 → P5 전에는 실행하지 않는다.
- 공급처 재고 정보가 늦거나 틀릴 수 있다 → "마지막 확인 시각"을 항상 표시하고 품절 판단은 사람이 확인.
- 문의 답변 초안의 사실 오류(배송·반품 조건) → 상품·정책 사실만 쓰고 모르면 "확인 필요"로 남기게 검증.

### 4-6. 결정이 필요한 사항

1. P0~P4(읽기·제안만)를 먼저 하고 쓰기(P5)는 나중에 할지
2. 재고·가격 이상 임계값(예: 재고 N개 이하, 마진 N%p 하락)
3. 문의 답변 초안에 쓸 정책 문구(반품·교환·배송 안내)의 기준 문서

## 5. 플랫폼 이용 약관 및 서버 관리 AI

> 이 항목은 두 갈래로 해석했다. 의도와 다르면 알려 달라: **(A) 약관·정책**(HOMEZ 자체 약관 + 판매 플랫폼의 이용약관·정책 변경 대응) **(B) 서버·운영 관리**(앱·DB·스케줄러·백업·업데이트의 상태 점검). "서버"가 지금의 Windows 데스크톱 앱 운영을 뜻하는지, V10의 클라우드 서버를 뜻하는지도 확인이 필요하다.

### 5-1. 목적과 범위

- **(A) 약관·정책**: ① 판매 플랫폼(쿠팡·온채널)의 정책·공지 변경을 읽어 요약하고, 영향을 받는 HOMEZ 규칙(채널 정책 규칙 카탈로그, 상품명·이미지 규칙)의 갱신을 *제안*한다. ② HOMEZ 이용약관·개인정보 처리방침 **초안** 작성 보조(V10 적용 — 법률 자문 아님, 법무 검토 필수).
- **(B) 서버·운영**: 앱이 멈췄는지, 감지·스케줄러가 돌고 있는지, 백업·DB 무결성·마이그레이션 상태가 정상인지 **읽기 전용으로 진단**하고 원인과 조치를 설명한다.
- 제외: 서버 재시작·마이그레이션 적용·복구·설정 변경을 AI가 직접 하는 일, 운영 DB 쓰기, 법적 판단·약관 효력 보증

### 5-2. 현재 상태 (코드 확인)

- 서버 운영 재료: `diagnostics/`(진단 내보내기 — DB `integrity_check`, 마이그레이션 진단, 마스킹한 로그 tail, 전부 읽기 전용), `backup/`(856줄), `update/`(업데이트 **공지**를 사람이 등록 — 자동 확인·서명 검증은 설계 문서만), `platform_alert/`(서버 관리자 알림 배송, best-effort), `scheduler/`(job들), `automation_safety/`(긴급 중지·실행 모드), 승인 센터의 허용 만료 요약.
- 오늘 실제로 겪은 문제(주문 감지가 가드 막힘으로 조용히 멈춤, 허용·가드 만료)는 **A단계에서 규칙으로 분류·연장·안내**하도록 고쳤다 — 이 AI는 그 위에서 "원인 설명"을 맡는다.
- 약관: 이용약관 문구는 코드에 사실상 없다. **약관의 앱 적용 시점은 V10으로 이관**된 결정이 있다(그 전에 약관 작업을 우선순위로 올리지 않는다). 플랫폼 정책은 `channel_policy`의 정적 규칙 카탈로그(공식 문서 기반)로만 존재한다.
- `monitor/`, `version/`, `license/`는 비어 있다(0줄).

### 5-3. 설계 방향

- **(B) 진단 AI**: 입력은 마스킹을 통과한 진단 묶음(상태 요약, 로그 tail, job 실행 이력, 허용 만료 목록)뿐. 출력은 "무엇이·왜·무엇을 하면 되는지" 설명과 점검 순서. **AI에 비밀정보·원문 로그를 보내기 전 마스킹 통과를 시험으로 고정**한다. 조치 실행은 항상 사용자.
- **(A) 정책 감시**: 공식 공지 페이지를 읽기 전용으로 가져와 **변경 여부를 결정적 비교(해시·차이)로 감지**하고, 변경이 있을 때만 AI가 요약·영향 규칙 후보를 제안한다. 규칙 카탈로그 수정은 사람이 검토해 반영(자동 반영 없음).
- **약관 초안**: 구조(필수 조항 체크리스트)는 규칙, 문장 초안은 AI. 출력에 "법률 자문이 아니다" 고정 표시, 초안은 문서로만 저장.

### 5-4. 단계

| 단계 | 내용 | 산출물 / 검증 | 외부 접촉 |
|---|---|---|---|
| T0 | 범위 확정: "서버"의 의미, 감시할 플랫폼 정책 페이지 목록, 약관 필요 조항(판매·위탁판매 기준 포함) | 합의 문서 | 0 |
| T1 | **운영 상태 진단 요약(B)**: 진단·job 이력·허용 만료·가드 막힘 분류를 한 번에 모아 규칙으로 "이상 후보" 산출 → 쉬운 보기/승인 센터에 표시(AI 없이도 동작) | 규칙·격리 화면 시험 | 0 |
| T2 | **AI 원인 설명(B)**: 마스킹된 진단 묶음을 AI에 보내 설명·조치 순서 생성 | 마스킹 시험(비밀·개인정보 미포함 확인), 가짜 전송 시험 | AI 호출(승인) |
| T3 | **플랫폼 정책 변경 감시(A)**: 공식 공지 읽기(허용 센터 읽기 목적), 변경 감지, 변경 시에만 AI 요약, 영향 규칙 후보 알림 | 결정적 비교 시험 | 공지 페이지 읽기(승인) |
| T4 | **약관·방침 초안 보조(A, V10 연계)**: 조항 체크리스트 + 초안 + 법무 검토 요청 표시 | 문서 | AI 호출(승인) |

| T6 | 역량 등록부(OPERATIONS_COORDINATION 확장 또는 신규 항목) 사실대로 갱신 | — | 0 |

### 5-5. 위험·미확인

- **로그·진단에 비밀·개인정보가 섞일 위험**이 가장 크다 → 마스킹 통과 전에는 AI로 보내지 않고, 시험으로 계속 감시.
- 플랫폼 공지를 읽는 것이 약관상 허용되는지(자동 수집 제한)는 **미확인**(T0/T3 전 확인).
- 약관 문구는 법적 효력이 달린 문서 → **AI 초안만으로 적용하지 않는다**(법무 검토 필수, 결정 기록의 V10 시점 준수).
- AI 진단이 틀려 불필요한 조치를 권할 수 있음 → 모든 조치는 사용자 확인이고, 규칙이 낸 "이상 후보"를 근거로 먼저 보여 준다.

### 5-6. 결정이 필요한 사항

1. "서버"의 범위: 현재 데스크톱 앱 운영만 / V10 클라우드 서버까지
2. 감시할 정책·공지 페이지 목록과 확인 주기
3. 약관·방침 작업의 시작 시점(결정 기록은 V10 적용) — 초안 보조를 지금 시작해도 되는지
